## 01 为什么需要企业级 AI 原生架构

主流 AI 原生叙事是"Agent + 记忆 + 工具 + 规划器"，强调 LLM 在运行时动态生成一切。这套范式在消费级场景如鱼得水，但放到强监管、强合规的企业场景却处处碰壁，因为它有几个隐含预设：任务开放、容忍错误、无需严格审计、没有复杂的组织权限约束——**这些前提在企业场景里全部失效**：

- **合规是硬约束**：HSE、设备、生产管理中每个操作要有依据、每个决策可追溯。审批流程不能每次都不同，合规检查不能"大模型觉得可以"。
- **组织是刚性框架**：企业有层级、岗位、职责分离。AI 必须在组织架构里有位置、有权限、有问责路径，"临时工式" Agent 无法纳入企业治理体系。
- **数据是核心资产**：必须能精确回答"这条数据从哪来、经过了什么处理、谁批准的"。
- **知识需要沉淀**：企业核心能力不能随员工离职而消失。

### 六个范式转移

企业级 AI 原生架构是六个独立演化多年的趋势在同一节点汇合：

```grid
以人为中心 → 以机器为中心 | 系统默认执行者是 AI，人退到监督与决策，从机械执行中解放出来。
以技术为中心 → 以任务为中心 | 系统关注"完成业务目标"而非技术模块跳转，直接收益是开发成本下降。
数字员工引入 | RPA 是脚本没有判断力；Agent 是临时工没有组织身份。数字员工有岗位、技能白名单、权限边界、绩效记录，与人类员工同一组织模型并存。
数据与业务统一建模 | 所有业务对象用同一套本体描述，所有规则用同一套语义表达。新系统接入只增映射，不改流程。
计算机真正理解业务 | 本体把业务概念形式化，AI 才能做多跳推理、跨域关联。
AI Coding + 自迭代运维 | 运维智能体：持续监控、小问题立即修复、大问题降级报警、需求整理成提案、AI Coding 生成代码、人类审核后部署。
```

六个转移指向同一结论：**企业级 IT 的核心矛盾正从"算力不够"转向"语义不清"**。云计算解决了算力，大模型解决了通用智能，但"如何让 AI 理解具体的企业业务并在合规边界内行动"需要新架构来填。

## 02 总体架构设计：1 + 4 + N

一个智能调度层，四个平台能力层，N 个垂域应用。**关键原则：应用在上，平台在下**——应用是平台的消费者，不是被管理的对象。

- **1 · 智能调度层**：AI 助手入口，负责工具注册（MCP）、数字员工调度协调、运维智能体运行。接收用户意图、分解任务、调度下层能力。
- **4 · 平台能力层**：
  - **Foundation**：组织、用户、角色、权限（ABAC/OPA）、审计。零业务逻辑，是所有上层的单一权威源。
  - **ONTO（数据语义层）**：本体定义、Schema Mapping、知识底座。回答"**是什么**"。只读边界，不处理业务流程。
  - **BM（业务语义层）**：七星框架承载者——流程、规则、组织、能力。回答"**然后呢/凭什么**"。唯一有权调用外部系统的平台层。
  - **Analytics**：数据洞察、报告、决策支持。从 BM 导入分析模型，不从零定义。
- **N · 垂域应用**：HSE、设备物资、生产、经营等行业应用 + 穿透监管、智能运营等横切应用，**同级并列**。假设数字员工的载体是一个机器人，它大概率不需要这些应用。

各层关系的比喻：Foundation 是**地基**（身份、权限、审计的来源），ONTO 是**字典**（数据是什么意思），BM 是**语法**（业务怎么运转），应用层是**文章**，智能调度层是**读者**。

基础设施选型原则是**每个组件只做一件事，做到极致**：Neo4j（图存储推理）、PostgreSQL（审计/策略）、ClickHouse（时序）、Kafka（异步解耦）、OPA（策略评估）、Temporal（长流程编排），全部容器化。

### 每层的关键纪律

分层架构的价值取决于每层"不该做什么"：用户层不直连数据库；应用层不维护独立业务语义、不自建认证；BM 不绕过 Foundation 权限、不自定义本体；ONTO 不处理业务流程、不调用外部系统写接口；Foundation 不含业务逻辑。**违反任何一条，分层就会退化成臃肿的单体。**

四件横切关注点贯穿所有层：**OPA 鉴权**（每个跨层调用无例外）、**Kafka 事件**（Schema 强制注册，不允许自由格式消息）、**审计日志**（append-only 不可篡改，携带 trace\_id）、**OpenTelemetry 全链路追踪**。

协同示例——安全员问"二车间上个月有哪些重大风险"：智能调度层理解意图 → Foundation 确认身份与权限 → BM 理解风险数据、按单位属地制定计划 → ONTO 查"风险点"属性与字段映射 → Schema Mapping 找到外部数据源执行查询 → BM 确认业务规则 → 知识库补充法规上下文 → AI 助手组织成自然语言回答。每层只做自己的事，用户感知到的只是和一个"懂业务"的助手对话。

## 03 关键创新与差异点

### "宏观刚 · 中观准 · 微观活"

主流强调"LLM 运行时现场生成执行计划"，在企业场景站不住。本架构选择**分层确定性**：

- **宏观刚**：核心业务流程（审批链、合规检查、财务结算）由人类审核固化，AI 不可动态改写；
- **中观准**：业务规则通过 DMN 决策表和 OPA 策略精确表达，变更走审批、版本化管理；
- **微观活**：流程框架内 AI 可自主分解子任务、选择最优路径、调用合适的 Skill。

大流程不可变，具体任务执行有灵活性。这不是限制 AI，而是让 AI 在企业场景真正可用。

### 创新一：双语义层分离

- **L4 ONTO（数据语义）**：回答"是什么"，只读边界；
- **L5 BM（业务语义）**：回答"然后呢/凭什么"，有权调用外部系统。

两层通过**版本绑定的语义契约**协同，各自独立演进。传统系统把"理解数据"和"理解业务"混在一起，改一个字段可能影响十个流程；双语义层还让数据团队（本体/映射）和业务团队（流程/规则）并行工作、互不阻塞——从架构上消除了"你改了这个字段我的流程就断了"的冲突。

### 创新二：七星框架

BM 层用七星框架完备覆盖业务语义七个维度：①组织（谁在做）②员工（谁能做，含数字员工）③流程（怎么做）④规则（凭什么）⑤事件（发生了什么）⑥能力（能做什么，Skill 注册）⑦集成（和谁对接）。

**价值不在七个维度本身，而在维度之间的关联**——跨维度影响分析："这个变更会影响 3 个岗位的能力模型、2 条规则、1 个外部接口"。例如 HSE"隐患整改流程"调整，传统系统改了 BPM 引擎，却不知道要同步调整安全员岗位能力模型（员工语义）、整改规则触发条件（规则语义）、外部回调接口（集成语义）——改了一处、漏了三处。七星框架让"隐性关联"变成"显性模型"。

### 创新三：数字员工作为企业编制

数字员工：有岗位、技能白名单、权限边界、绩效记录，与人类员工同一组织模型并存，问责路径一致。权限模型（ABAC）里与人类平等，但约束更严格：只能调用注册过的 Skill、只能访问授权数据域、每次动作留痕、**不能有"全部可见"的数据权限**。

### 创新四：统一规则 + 统一映射 + 统一权限

**统一规则**：业务规则（DMN）、合规规则（OPA/ABAC）、算法规则（Skill + 沙箱）三层分离；每条规则走完整 **S4L 闭环**——AI 抽取（只是"候选"）→ 沙箱验证（历史数据 + 边界情况仿真）→ 专家审核（**不可跳过**）→ 发布反馈（命中率、误判率回流）。

**统一映射**：Schema Mapping 一次定义、所有应用共享（ERP 的 `MATNR` → "物料编号"），新系统接入只增映射不改流程。映射之上的知识底座四个特点：

1. **本体驱动、自主构建**：LLM 根据本体发现实体候选 → 网络检索 + 文档检索富化 → 抽取实体关系 → 语义消歧合并 → 结构化入库。知识主动从文档中"长"出来。
2. **本地小模型优先**：意图分类、消歧、合并用 local-small，只在 SQL 生成、答案合成用大模型——降成本、数据不出域。
3. **多级回退，总有答案**：结构化检索（SQL+向量+图谱）→ 外部 LLM 通用知识 → 网络检索 → 固定提示词兜底，每级标注来源。
4. **兼具结构化与非结构化**：本体把结构化数据、文档分块、原始文档关联起来。

**统一权限**：所有权限判定走 Foundation 的 OPA 引擎（ABAC），一次评估看四个维度——主体（Who）、资源（What）、动作（How）、环境（When）。人点的按钮和 AI 调的工具走同一条路径。

### 创新五：AI 是核心，不是插件

"加 AI"是现有系统附加 AI 功能；"AI 加"是以 AI 为核心重新设计——AI 是默认执行者，语义体系是 AI 行为的边界，确定性逻辑是 AI 决策的压舱石。本架构选择"AI 加"，但核心不等于无约束——**有约束的自主，才是企业级 AI 原生的真正含义**。

### 差异总结

| 方面 | 通用 AI 原生 | 企业级 AI 原生（本架构） |
| --- | --- | --- |
| 核心 | Agent 为中心 | 本体为中心 |
| 资产 | LLM 为核心（会过时） | 双语义层为核心（会增值） |
| 执行者 | Agent 为临时工 | 数字员工为企业编制 |
| 流程 | 运行时动态生成 | 宏观刚 · 中观准 · 微观活 |
| 合规 | 事后审计 | 内建合规（OPA + 审计链） |
| 知识 | RAG 读文档回答 | 结构化知识 + 本体推理 |

## 04 实施方法论

### FDE 靠前实施模式

FDE（Field Deploy Engineer，借鉴自 Palantir）常驻客户现场，把咨询、开发、实施合为一体：

1. **第一周·摸底**：和各岗位聊业务概念、流程、痛点；把制度文档喂给系统，AI 先抽一轮知识候选；
2. **第二到四周·建模**：ONTO 层定义本体，BM 层配七星框架，Schema Mapping 接入现有数据；
3. **第五周起·试运行+迭代**：调整大多是配置级；需要新功能时用 AI Coding 辅助写 Skill，沙箱验证后上线。

约三个月稳定运行。传统做法需半年到一年。前提是 FDE 同时懂业务、懂技术、懂工具；本架构通过降低工具门槛，逐步让客户团队承担部分 FDE 工作，最终"自主运营"。

### 三层开发协同

| 层 | 适合的工作 | 执行者 |
| --- | --- | --- |
| 配置层 | 表单布局、字段显隐、流程节点调整、规则参数 | 业务人员 / FDE |
| 低代码层 | 新报表、简单流程、数据视图、简单 Skill | FDE + AI Coding |
| 全代码层 | 复杂算法、系统集成、本体扩展 | 开发者 + AI Coding |

关键约束：配置层和低代码层的变更**不能破坏平台层的语义一致性**（如不能绕过七星框架的职责分离规则），通过 BM 层规则引擎校验。AI Coding 是加速器，不能直接改生产环境。

### 无感使用

用户不需要知道数据在哪、流程怎么走、权限怎么算。AI 助手受数据语义约束（知道"这是什么"）、业务语义约束（知道"然后能做什么"）、具备企业知识。不同岗位问同样的话得到不同回答——不是权限不同，而是岗位关注的东西不一样（安全员看隐患清单，车间主任看风险趋势），由 BM 层岗位能力模型实现。

与通用对话 AI 的区别：靠**结构化知识 + 本体推理**而非实时检索；受 ABAC 实时鉴权；能调用 Skill、触发流程、写入数据；每条回答**有出处、有依据、可追溯**。

### 自迭代运维

运维智能体被动响应（小问题立即修复、大问题降级报警）+ 主动巡检（性能调优、需求整理成变更提案）。**AI 发现问题 → 提出方案 → 人类决策 → AI 执行**；所有代码变更必须走沙箱验证 + 人工审核 + 灰度发布。AI 负责"提效率"，人负责"把方向"，这条红线贯穿系统整个生命周期。

## 05 收益与预期效果

- **系统真正"懂"业务**：定义新智能体不再是"写一套新代码"，而是"在七星框架里配置一组能力"。
- **数字员工与人类结伴**：日常巡检/比对/校验 AI 独立完成；需要判断、协调、担责时人类决策。
- **自感知与自主运维**：Skill 变慢自动调优、数据质量下降触发清洗、答不上的问题标记为知识盲区。
- **需求闭环 + AI Coding**：需求从发现到上线从数周压缩到数天。
- **实施简化为两步**：数据源 → 本体（数月压缩到数周）；规章制度 → 业务模型（知识构建管线自动抽取，专家审核）。

| 维度 | 传统做法 | 本架构 |
| --- | --- | --- |
| 实施周期 | 6-12 个月 | 2-3 个月（FDE 模式） |
| 新需求响应 | 周级 | 天级（配置 + AI Coding） |
| 知识传承 | 依赖个人，人走知识丢 | 知识库沉淀，组织资产 |
| AI 运行成本 | 全依赖外部大模型 | 本地小模型优先，降一个量级 |
| 新系统接入 | 数月适配 | Schema Mapping 数天 |
| 合规审计 | 事后准备材料 | 内建审计链，一键导出 |
| 检索质量 | 单一关键词 | 多级回退 |

## 06 写在最后

企业级 AI 原生不是一次技术升级，而是一次方法论的重构。本架构的答案：**以本体为中心，以双语义层为基石，以数字员工为组织形态，以确定性逻辑为压舱石**。

企业级 AI 原生架构要解决的不只是技术问题，更是**组织和知识的问题**——通过本体和七星框架把企业核心知识（怎么设计产品、怎么管控风险、怎么组织生产）形式化、数字化，让它们成为可查询、可推理、可传承的组织资产。这是比"降本增效"更深远的价值：**让组织的知识不再依赖个人，而是沉淀为系统能力**。
