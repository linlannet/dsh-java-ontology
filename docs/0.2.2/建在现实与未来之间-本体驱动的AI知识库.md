## 01 从一个考倒大模型的问题说起

前年，作者拿一个问题去考市面上的大模型："北京雍和宫里有哪些建筑是乾隆年间改建的？现在分别是什么保护等级？"

模型一本正经地列了一串建筑，文风流畅、言之凿凿。逐条去查，一半是对的，另一半是编的——年代张冠李戴，保护等级凭空捏造。

这个问题看起来简单，但需要跨三个知识维度：**建筑实体 → 建造年代属性 → 保护等级属性**。通用大模型靠"记忆"作答，传统 RAG 检索文档碎片，都做不好这种跨维度的组合查询。

后来作者用业余时间搭了一套实验系统重新测试：先通过本体定位"建筑"实体类型，再用属性过滤锁定年代，最后关联保护等级字段——一条 SQL 搞定，必要时让 Agent 规划迭代执行。**0.4 秒完成检索，每一条都能点开看到出处。**

## 02 什么是知识库？四个时代的建设路线

知识库的价值，就是把"人脑里的知识"变成"系统里的资产"——**可检索、可推理、可传承、不流失**。建设路线经历了四个阶段，每个阶段都在解决上一阶段的问题，又带来新的问题：

```grid
第一代 · 专家系统 | 1980s | 用 IF-THEN 规则编码专家知识。确定性强、可解释；但规则脆弱，维护成本随规模指数增长——数万条规则改一条牵一发动全身。
第二代 · 知识图谱 | 2010s | 用实体和关系组织知识。结构化、支持推理；但构建成本太高——人工定义 Schema、标注数据、训练模型，周期以月计，中小团队玩不起。
第三代 · RAG | 2023 | 文档切块、向量化，检索相似片段丢给大模型生成答案。部署快、门槛低；但检索不准、幻觉严重、无法多跳推理。
第四代 · 本体驱动 | 2025 | 用本体定义知识骨架，大模型自动抽取知识，多路融合检索 + 语义推理。核心突破是"自动构建"——知识从文档中"长"出来。受 Palantir 本体论启发。
```

一句话总结：**从人编规则，到人建图谱，到模型兜底，再到知识自动生长。**

## 03 踩过所有坑之后想清楚的八件事

1. **知识库的核心不是"大模型"，而是"知识的组织方式"**。大模型是嘴，知识才是脑子。脑子没想清楚，嘴再能说也是胡说。
2. **知识图谱的强项不是结构化数据管理和查询**。它有灵活的推理能力，但缺乏语义检索能力，也不如关系数据库的属性检索灵活。
3. **检索不能只靠向量**。向量擅长"模糊语义"，知识库很多问题需要"精确匹配"。最好方案是确定性检索与语义检索融合，并实现来源追溯。
4. **知识库不应是一次性项目，而是可复用的底座**。知识管理有跨行业共性，没人愿意每次从零开始。
5. **私有化部署不是可选项，而是必选项**。组织的核心知识资产不可能放到公有云上。
6. **构建和使用成本决定生命力**。首先不能依赖人工构建；其次要减少使用中的算力消耗——Agent 每做一次决策就多一次 LLM 调用，延迟和成本都上去了。
7. **找准大模型的位置**。不要让它当"大脑"，让它当"嘴巴"。大脑应是结构化、可验证、可追溯的知识库，大模型只负责理解问题和组织语言。
8. **本体！还是本体！** 知识库的骨架应该是本体。本体给知识以结构和语义，给检索以方向，给推理以路径，给答案以边界。本体定义好、文档上传后，解析、索引、抽取、消歧、去重全部交给系统自动完成。

## 04 一个"能自己想明白"的知识库

有没有一种知识库：既有知识图谱的结构化推理能力，又有关系数据库的灵活检索与扩展，又能自动构建？既精确快速、少幻觉、来源可溯，又能语义理解？既通用灵活、又可私有化部署、还省 Token？

作者的答案是：**本体驱动的知识底座**。

### 什么是"本体驱动"

> 传统 RAG 像是把图书馆所有的书撕碎，按关键词分类放到一堆箱子里，用户问问题时从箱子里抓几片出来拼答案——快，但不准。
> 知识图谱像精心整理的档案馆，每份资料有编号、分类、关联索引——准，但整理成本太高，用起来不如关系数据库方便。
> **本体驱动，像是先画好一张"知识地图"**：标明领域有哪些核心概念（实体类型）、每个概念有哪些特征（属性）、概念之间有哪些关系（关系类型）。所有知识按这张地图组织和检索，并利用 LLM 的规划能力。

本体不是数据，而是数据的骨架。有了骨架，数据各归其位，检索有的放矢。

### 与传统知识图谱的关键区别：关系可以有多属性

传统知识图谱的关系是"边"，边上只能有一个标签（如"位于"）。但现实中关系本身有属性：故宫"建于"永乐四年——"建于"这个关系有一个"年代"属性。传统图谱很难表达这种"关系的关系"。

作者的方案用**关系数据库存储**：实体是表中的行，可挂载任意多的属性字段；关系就是外键关系。支持时间、空间（坐标）、向量检索及混合检索，加上基于外键的关联检索——类似知识图谱的多跳推理，还能做知识推荐和关联拓展。

| 维度 | 传统知识图谱 | 本体驱动知识底座 |
| --- | --- | --- |
| 建模方式 | 图数据库 + 属性图 | 关系数据库 + 本体抽象层；支持多属性关系，比属性图更灵活 |
| 构建成本 | 3-6 个月（人工标注 + 训练） | 1-2 周（LLM 自动抽取 + 审批） |
| 知识更新 | 重新训练 / 批量导入 | 实时增量（数据变更监听 + 自动索引） |
| 检索方式 | 图遍历为主 | SQL 精确 + 向量语义 + 图谱推理 三路融合 |
| 领域适配 | 每个领域重建图谱 | 配置新本体即可，零代码 |

## 05 八个核心技术特点

### 特点一：多跳推理——不只查一层

用户问"水泵振动异常可能是什么原因？怎么修？"系统沿本体定义的关系链推理：

> 水泵振动异常（故障现象）→ 可能导致 → 轴承磨损（原因）→ 需要更换 → 对应型号轴承（备件）

技术实现：本体定义关系类型和方向，系统把自然语言问题解析为本体上的起始节点和推理方向，在关系图上做**受限遍历**——只走合法的关系类型，不会"跳"到不存在的关联上。这比大模型自己"联想"靠谱多了。

### 特点二：预构建减少幻觉——先把知识"钉死"

核心思路：**答案来自数据库，不是来自模型的"记忆"**。大模型只负责把取出的结构化数据组织成自然语言。四层约束：

- **实体约束**：答案中提到的实体必须在数据库中存在，不允许编造；
- **属性约束**：属性值必须来自数据库字段，不允许推测；
- **关系约束**：关系路径必须符合本体定义，不允许臆造关联；
- **溯源标注**：每条答案标注数据来源，可点击查看原始记录。

四层约束下来，幻觉率约等于你的数据质量。

### 特点三：多垂域自由扩展——一套底座，多个知识库

一个大集团下文旅、设备、安全三条业务线，知识结构完全不同。传统方案要建三套系统。此方案：**一套底座，配置多个域模型**，每个域有自己的本体、数据、权限，共享基础设施但数据完全隔离。所有业务表带域标识字段，查询时自动注入域过滤条件；Text2SQL 也把当前域的本体信息注入提示词，避免跨域查询。

### 特点四：关系也是"一等公民"

传统图谱中关系是"胶水"。但真实业务中关系本身有丰富语义：设备 A"发生故障"故障 B——这条关系带有发生时间、维修人员、维修耗时、使用备件、维修结果等属性，属于"关系"而非任何一端的实体。

传统图谱要么把属性塞到实体上（破坏模型），要么创建"维修事件"实体（增加复杂度）。此方案里**关系本身就是表中的记录，直接加字段**——系统在知识构建时自动抽取、问答时自动参照。关系可以有自己的审批流程、版本历史、权限控制。

### 特点五：全自动知识构建——从网络到知识库

流水线：定义本体 → 指定收集目标 → 网络信息自动收集 → 文档自动解析分块 → 实体关系自动抽取 → 语义消歧 + 去重 → 人工审批 → 正式入库。全程无需编码，一键启动。

实测"北京历史文化"知识库（本体：景点、人物、事件、文物），指定"北京地坛"为收集目标：自动收集几十篇文档 → 解析分块、建立三路索引（全文 + 向量 + 图谱）→ 抽取上千条实体与关系 → 语义消歧（"玄烨"与"康熙帝"合并）→ 提交审批入库。**全程约 2 小时，纯人工至少 2 周。**

### 特点六：运行中增量学习——知识自动生长

用 CDC（数据变更捕获）机制：数据库表一有变更，自动触发增量索引，无需停机重建。而且**问答过程本身也是学习过程**：答不上的问题记为知识盲区，下次收集重点补充；用户纠正的答案作为反馈信号优化后续检索和生成。

### 特点七：确定性检索 + 语义检索融合——两条腿走路

通过意图分类模型自动判断问题类型，选择检索路径：

- **精确查询**（"地坛建于哪一年？"）：Text2SQL 直接查数据库，毫秒级响应，零幻觉；
- **语义查询**（"地坛的建筑风格有什么特点？"）：向量检索 + BM25 全文检索融合排序；
- **关联查询**（"和地坛同期的皇家祭祀建筑有哪些？"）：图谱多跳遍历，发现隐含关系；
- **兜底**：文档库多路检索融合（全文 + 向量 + 图谱证据互补）。

这些路径**逐级回退**：精确查询无结果自动降级语义检索，语义置信度不够自动升级图谱推理。用户不需要知道系统用了哪种方式。

### 特点八：Text2SQL + SQL 审核——从问答中学习

用户问题被转化为 SQL 时系统自动记录：查询有结果说明知识覆盖了这个问题；返回空结果说明存在知识盲区。管理员可审核生成的 SQL，**审核通过的查询成为后续生成同类查询的参考范例（Few-shot）**——用得越多，SQL 生成越准，系统有自我改进能力。

## 06 完整架构的关键设计决策

1. **用关系数据库 + 扩展，不用专门的向量/图数据库**。关系库加向量扩展即可做向量检索，避免单独维护向量数据库；数据同库，没有同步问题，事务一致性有保证（超大规模可再加专用组件）。
2. **分级 LLM 路由**。简单任务用本地小模型（免费、快），核心任务用本地大模型（质量高），高难度任务才走外部大模型，按复杂度自动路由，成本质量兼顾。
3. **全容器化部署**。十几个容器一键拉起，从零到可用不超过半小时。

## 07 愿景：新一代知识底座

作者的初衷不是做一个"更好的 RAG"，而是验证一件更根本的事：**让知识库可以"自己长出来"**——一个没有 AI 背景的业务团队，也能在一两周内构建起自己领域的高质量知识库。知识库不再是 AI 团队的专利，而是每个业务团队的基础设施。

> \[!NOTE\] 四步，从零到可用
>
> 1. **定义你的本体**（领域有哪些核心概念和关系、提示词）
> 2. **上传你的文档**（手册、指南、报告、论文），提供外部蒸馏/检索账号
> 3. **等待系统自动构建**（三路索引、实体抽取、关系发现）
> 4. **开始使用**（问答、检索、语音对话）

为什么说"建在现实与未来之间"？因为根据当前技术手段做了很多权衡和妥协，在不完美中追求相对可用。作者认为最好的实现方式，是将来基于他的 **DIKA 神经符号数据库**（参见《DIKA：从内存关系模型出发，构建可推理的智能数据引擎》）。
