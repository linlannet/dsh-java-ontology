企业 AI 缺的不是能力，缺的是一个让它可以理解、判断、行动、验证的企业业务世界——这就是 Ontology 想要站的位置。

做企业软件的人，应该都很熟悉 ER、DDD 和 Workflow。

设计数据库的时候，我们画 ER 图，定义表、字段、主键和外键；开发复杂业务系统的时候，我们用 DDD，把业务逻辑封装进领域模型；处理审批、订单、采购、生产等业务时，我们又会引入 Workflow，把一个个业务步骤串起来。这些方法都很成熟，也各有各的用处。

但当企业开始真正使用 AI Agent 时，一个以前不那么突出的问题，突然变得重要起来——如果 AI 不只是回答问题，而是要理解业务、判断状态、调用系统、修改数据，甚至推动业务执行，那么，它究竟应该依据什么来理解企业？

我们可以给 Agent 接入数据库，让它查询订单；可以给它接入 RAG，让它检索业务文档；可以给它配置 MCP，让它调用 CRM、ERP 等系统；还可以设计复杂的 Workflow，规定它应该按照什么步骤完成任务。看起来，工具已经足够多了。可当你让它处理一个真实的业务问题时，麻烦就来了。

比如，销售人员问：

“客户 A 的订单已经延迟三天了，能不能优先发货？如果仓库库存不足，就从其他仓库调货，但不要影响已经承诺给其他客户的订单。”

这句话听起来并不复杂。但一个真正能够执行任务的 Agent，需要回答一连串问题：

客户 A 到底对应哪个客户对象？有没有多个系统使用不同的客户 ID？

这笔订单当前处于什么状态？延迟的原因是什么？

订单中的商品存放在哪些仓库？哪些库存已经被其他订单占用？

什么叫“优先发货”？企业有没有明确的业务规则？

调拨库存是否需要审批？谁有权批准？

如果库存可以调拨，应该修改哪个系统中的哪些数据？

执行之后，如何确认库存真的发生了变化，订单真的进入了正确状态？

你会发现，这已经不是简单的数据库查询问题，也不只是调用几个 API 的问题。它涉及数据、业务语义、对象关系、业务规则、状态变化、执行动作、权限控制，以及执行后的结果验证。

过去，这些东西散落在不同的系统、代码、流程和文档里。熟悉业务的员工可以凭经验把它们串起来，但 AI 并不会因为接入了这些系统，就自动理解企业的运作方式。这也是我越来越关注 Ontology 的原因。

ER 在描述数据结构，DDD 在组织领域代码，Workflow 在编排执行过程，而 Ontology 试图把企业中的业务对象、关系、状态、规则、动作和权限统一起来，让软件和 AI 能够在同一个业务世界里工作。

这不是说过去的建模方法过时了，而是企业开始需要一种能够连接它们的、更贴近业务运行本身的模型。

## 企业已经有这么多建模方法，为什么还需要 Ontology？

先把几个概念放在一起看：

Ontology 企业世界如何被理解、约束、推理与执行

统一业务语义、状态与动作

Workflow 流程怎么运行

DDD 领域代码怎么组织

ER / DB 数据怎么组织和存储

知识图谱贯穿对象与关系的建模，API、服务和权限系统则提供连接、执行与控制能力。

它们不是被 Ontology 取代，而是可以在统一的业务语义下协同工作。

这张图表达的是抽象层次上的区别，不是严格的技术依赖关系。Ontology 不一定建立在 Workflow 之上，DDD 也不是数据库之上的一个固定技术层。实际工程中，它们可以相互映射、组合，甚至在同一套系统中共同存在。

真正需要回答的问题是：每一种建模方法究竟在描述什么，又没有描述什么？我们先从一个最常见的业务对象——订单——说起。

1、同一个订单，在不同系统里是不同的东西

在数据库设计人员眼里，订单是一组结构化数据。

Order

├── id

├── customer_id

├── amount

├── status

└── created_at

ER 图关心订单与客户之间是什么关系，主键如何定义，外键指向哪里，一对多还是多对多，哪些字段允许为空。这些问题非常重要。没有清晰的数据模型，业务系统很难可靠运行。

但数据库中的 status = 2 到底意味着什么？订单处于待支付、待审核，还是待发货状态？仅凭字段类型和字段值，不一定能回答。

在 DDD 的设计中，订单可能是一个 Aggregate（聚合），内部包含订单明细、金额计算、取消条件等业务规则。

Order Aggregate

├── Order

├── OrderItem

├── calculateAmount（）

├── confirm（）

└── cancel（）

DDD 关注的是领域模型如何组织，以及业务规则如何得到保护。

到了 Workflow，订单又变成了一条流程中的业务对象。

创建订单

↓

检查库存

↓

支付

↓

拣货

↓

发货

Workflow 关心的是任务执行的顺序、条件分支、异常处理和人工审批。如果再看知识图谱，订单可能成为一个节点，与客户、商品、仓库、物流单建立关系。于是，同一个订单，就有了四种不同的表达方式。

建模方法

它主要回答的问题

ER / 数据库 Schema

数据如何组织、关联和存储？

DDD

业务概念如何进入代码，领域规则如何组织？

Workflow / BPM

一项业务任务按照什么步骤执行？

Knowledge Graph

实体之间存在什么关系，知识如何关联？

Ontology

这些业务对象究竟是什么，它们处于什么状态、受到什么规则约束，又允许执行什么动作？

最后这一行，才是 Ontology 要重点解决的问题。Palantir 在其官方文档中，将 Ontology 定义为组织的 operational layer（业务运行层）：它把企业数据映射为现实世界中的对象和关系，同时纳入动作、函数以及动态权限等能力。

这里有一个容易被忽略的区别。过去，我们经常从系统出发思考问题：数据库怎么设计，服务怎么拆分，流程怎么编排，权限怎么配置。现在，如果 AI Agent 要参与实际业务，我们还需要从业务世界出发思考：客户、订单、商品、仓库究竟是什么？它们之间的关系意味着什么？一个对象处于某种状态时，可以做什么、不能做什么？

「过去，我们主要给系统建模；今天，我们开始需要给业务世界建模。」

这不是要推翻过去的技术体系，而是需要把原本分散在不同技术体系中的业务含义重新组织起来。

## Ontology 与 ER：从数据结构到业务世界

ER 是理解 Ontology 最好的起点，因为两者都涉及对象、属性和关系，但关注点并不相同。

1、ER 关心的是数据结构

假设我们正在建设一个订单系统。数据库里可能有以下几张表：

Customer

│

│ customer_id

▼

Order

│

│ order_id

▼

OrderItem

│

│ product_id

▼

Product

这套模型可以清楚地表达客户、订单、订单明细和商品之间的数据关联。但在实际企业中，情况通常比图上复杂。订单系统有自己的客户编号，CRM 使用另一套客户编号，财务系统又可能按照结算主体管理客户。仓储系统使用商品编码，采购系统还可能维护供应商物料编码。

数据库之间能够通过某些字段建立关联，不代表企业已经形成了统一的业务语义。例如，CRM 中的 Customer A 和 ERP 中的 Customer 00128，究竟是不是同一个客户？如果只是把两张表关联起来，这个问题仍然没有得到解决。它需要统一标识、业务定义、映射规则，必要时还需要人工确认。

同样，一个订单的 status 字段，即使在所有系统中都叫 status，也不代表它们具有相同的含义。ERP 的订单状态可能表示订单处理进度，仓储系统的状态表示拣货进度，物流系统的状态则表示运输进度。

字段名称相同，不等于业务概念相同。

2、Ontology 关心的是业务对象及其含义

如果使用 Ontology 的思路重新组织订单业务，首先需要定义的不是表，而是企业世界中的业务对象。

Customer

客户身份、客户等级、信用状态

Order

订单金额、订单状态、承诺日期

Product

商品编码、规格、可售属性

Warehouse

仓库位置、库存、作业能力

业务关系（Link）

客户拥有订单；订单包含商品；库存存放于仓库；订单关联发货单

规则与动作

能否取消、能否调拨、谁能批准、执行后如何更新业务状态

这时候，模型不再只是描述哪些表通过什么字段关联，而是把这些数据解释为企业中的业务对象，并明确对象之间的业务关系。Palantir 的 Object Type 用来定义现实世界中某类实体或事件的结构，Property 描述其特征，Link Type 则定义对象类型之间的关系。它们可以映射到已有的数据源，而不是要求企业把所有数据重新存储一遍。

这一区别很重要。引入 Ontology，不意味着必须废弃现有的数据库，也不意味着所有数据都要搬进一个新的数据库。完全可以保留原来的 ERP、CRM、WMS 和其他业务系统，通过映射、关联和必要的数据治理，让它们在统一的业务语义下被理解和使用。

3、从“字段关联”到“业务事实”

假设数据库里有这样一条关系：

Order．customer_id = Customer．id

从数据层面看，它表示订单记录引用了某个客户记录。但在业务语义层面，我们希望表达的是：

这笔订单属于某个客户，订单的交付、付款、取消等行为，都可能受到这个客户的业务属性和双方约定的影响。

两者并不矛盾。后者是在前者的基础上增加业务含义。再往前一步，系统就需要回答：

客户是否具有特殊交付约定？

订单是否已经进入不可取消的状态？

取消订单是否会产生退款义务？

取消后是否需要释放已分配库存？

哪些操作必须经过审批？

注意，这些问题并不是简单地在 ER 图上多画几条线就能解决的。它们涉及业务规则、状态变化、动作定义和权限控制。ER 告诉我们数据之间如何关联，Ontology 则进一步尝试让这些关联成为软件能够理解的业务事实。

不过，这并不意味着 ER 完全不关心约束，数据库当然也可以定义完整性约束、触发器和业务字段。区别在于建模的主要目标不同：ER 的核心是数据结构，而 Ontology 的目标是让业务对象及其语义能够被多个应用和执行主体共同使用。

## Ontology 与 DDD：两者不是竞争关系

如果说 ER 与 Ontology 的区别主要在于数据结构和业务语义，那么 DDD 与 Ontology 的关系就更值得工程师深入研究。因为 DDD 本身已经在做业务建模了。

既然 DDD 已经有 Entity、Aggregate、Domain Service 和 Bounded Context，为什么还需要 Ontology？难道 Ontology 只是换了一套术语？我认为不是。

「关键区别在于：DDD 更关注领域内部如何正确地表达和执行业务规则，Ontology 更关注这些业务概念如何跨系统、跨应用地被共同理解和使用。」

1、DDD 解决的是领域复杂性

以订单系统为例。在一个合理的 DDD 设计中，订单不是任意修改的普通对象，而是包含业务规则的领域模型。

class Order {

void cancel（） {

if （！isCancellable（）） {

throw new IllegalStateException（

“当前订单状态不允许取消”

）；

}

this．status = OrderStatus．CANCELLED；

}

这段代码表达了一个重要思想：取消订单不能仅仅意味着把数据库中的状态字段改成 CANCELLED，而应该通过领域行为来完成，并由领域模型保护业务不变量。真实项目中，领域规则还可能涉及金额计算、库存预留、支付状态、退款条件等。

DDD 通过聚合、领域服务、仓储和限界上下文等方法，帮助团队控制复杂性，让代码结构尽可能贴近业务语言。这一点不会因为 AI 的出现而失去价值。相反，Agent 越是能够参与业务执行，越需要清晰、可靠、可测试的领域规则。

2、DDD 的边界在哪里？

问题不在于 DDD 不能表达业务，而在于一个复杂企业的业务模型，往往分散在多个限界上下文中。订单团队有自己的订单模型；库存团队有自己的库存模型；物流团队有自己的发货模型；财务团队有自己的结算模型。

这些模型不一定应该合并。DDD 恰恰强调，不同上下文可以拥有各自的模型和语言。例如：

订单领域中的“已完成”，可能意味着订单业务流程已经结束

仓储领域中的“已完成”，可能意味着拣货任务已经结束

财务领域中的“已完成”，可能意味着结算已经完成

它们可能都使用“完成”这个词，但对应不同的业务含义。如果为了统一而强行把它们合并成一个巨大的领域对象，反而可能破坏原有的领域边界。然而，当企业需要构建跨领域应用，或者让 Agent 同时理解订单、库存、物流和财务时，一个新的问题出现了：这些领域模型之间，如何形成统一的业务视图？这正是 Ontology 可以发挥作用的地方。

3、从代码中的模型，到平台共享的模型

可以把两者的典型使用方式做一个对照：

DDD：领域模型驱动业务实现

领域概念与业务规则

↓

Entity / Aggregate / Domain Service

↓

代码实现、测试、部署与运行

Ontology：业务语义供多个执行主体共享

企业业务对象、关系与状态

↓

Ontology：语义、逻辑、动作与权限

↓

Application / Workflow / Agent

这里有两点需要说清楚。第一，DDD 模型并不只是存在于代码里。领域模型也可以通过 API、事件、契约和其他机制被外部系统使用。因此，不能简单地说 DDD 只能服务于单一应用。第二，Ontology 也不是一套完全脱离代码的魔法模型。它需要数据映射、业务逻辑、动作执行接口、权限机制和工程基础设施来支撑。

两者真正不同的，是各自承担的主要职责。DDD 让某个领域内部的业务逻辑保持一致；Ontology 则可以为多个领域和应用提供共享的业务对象与语义，并将这些对象与相应的逻辑、动作和权限联系起来。

例如，一个跨越订单、库存、物流三个领域的 Agent，可以通过共享的业务语义理解：

哪个订单正在等待发货

哪些库存已经被分配给其他订单

哪张发货单对应这笔订单

哪些动作可以执行，哪些必须经过审批

底层的订单取消、库存预留、物流创建等操作，依然可以交给各自领域的服务完成。因此，我更倾向于这样理解两者的组合：

Ontology 负责跨领域的语义统一，DDD 负责领域内部的规则实现。它们可以协同，而不是互相替代。

4、一个容易走偏的地方

有些团队听到 Ontology 后，会想把所有领域对象、所有业务规则和所有操作都集中到一个平台里。这未必是正确方向。

如果某项规则涉及复杂的订单状态转换、库存一致性、并发控制和事务边界，那么它可能仍然应该由领域服务负责。Ontology 可以暴露这项业务能力、描述它的业务含义，并为上层应用或 Agent 提供受控的调用方式，但不一定需要重新实现所有底层逻辑。

！踩坑提示 🕳

如果把 Ontology 做成另一个庞大的业务应用平台，重复实现已有的领域逻辑，最后很可能只是增加了一层维护成本。我们真正需要的是明确的职责边界，而不是再建一套系统来复制旧系统。

## Ontology 与 Workflow：一个描述世界，一个编排过程

这可能是理解 Ontology 最关键的一组对比。因为很多企业在引入 AI 之后，第一反应就是：既然 Agent 需要完成业务任务，那我们给它设计一套足够完善的 Workflow，不就行了吗？

在某些场景下，确实可以。如果任务路径相对稳定、步骤清晰、异常情况有限，Workflow 是非常有效的工程工具。但如果业务状态复杂、业务条件不断变化，单纯依靠流程编排就容易遇到问题。

1、Workflow 的思路：规定事情怎么做

假设我们要设计一个订单处理流程：

创建订单

↓

检查库存

↓

检查支付

↓

生成拣货任务

↓

安排发货

↓

完成订单

遇到库存不足时，可以添加分支：

检查库存

├── 库存充足 → 继续处理

└── 库存不足 → 申请调拨

↓

审批

↓

执行调拨

这种方式有明确的优势。流程可视化，执行路径可以追踪，任务能够分配给具体的人或系统，异常分支也可以通过显式配置处理。对于审批、结算、报销、采购等标准化程度较高的业务，Workflow 往往是不可缺少的基础设施。问题出在另一种情况——现实中的业务变化，远比一张流程图复杂。

2、为什么流程会越画越复杂？

假设订单业务新增了几个条件：

VIP 客户允许优先处理

紧急订单可以走快速审批

库存不足时允许跨仓调拨

高价值订单需要额外审批

特殊商品不能跨仓调拨

某些仓库只能处理特定商品

调拨库存不能影响已经承诺给其他客户的订单

这些条件分别来自客户管理、库存管理、仓储作业和企业风控。如果把每一个业务条件都直接写进流程，流程就可能逐渐变成这样：

检查订单

↓

判断客户等级

├── 普通客户

流程本身没有错。真正的问题在于：如果每个业务对象的规则都被重复写进不同流程，业务变化就会不断传导到所有相关流程中。客户等级规则调整了，订单流程要改，售后流程可能也要改；库存分配规则调整了，发货流程、调拨流程和紧急订单流程可能都要改。

最后，团队花费越来越多的精力维护流程分支，却很难确认所有流程使用的业务规则是否一致。当然，成熟的 Workflow 引擎可以通过子流程、规则引擎、共享组件和动态路由减少这种复杂性。问题并不是 Workflow 天生无法处理复杂业务，而是流程编排不应该成为所有业务语义和规则的唯一承载位置。

3、Ontology 改变的，是规则的组织方式

考虑同样的库存问题。在一个以流程为中心的设计里，系统通常会在某个流程节点判断库存是否足够，然后选择下一步。在一个以业务对象为中心的设计里，我们可以把相关事实和规则组织在订单、库存、仓库等业务对象及其关系周围。例如：

Order

├── status

├── priority

├── promised_delivery_date

└── allocated_inventory

Inventory

├── available_quantity

├── reserved_quantity

└── warehouse

Warehouse

├── supported_products

└── transfer_capability

接下来，系统不只是问“现在应该进入哪个流程节点”，而是可以根据当前业务状态判断：

订单是否具备发货条件

是否存在可用库存

某仓库是否支持目标商品

调拨后是否会破坏其他订单的库存承诺

当前用户是否有权发起调拨

哪些条件不满足，应该采取什么措施

可以把核心差异概括为：

比较维度

Workflow

Ontology

主要关注

任务如何推进

业务对象及其状态、关系和规则

典型表达

对象、属性、关系、逻辑、动作

主要价值

典型问题

当前业务事实是什么？哪些动作在什么条件下允许执行？

需要强调，Ontology 并不意味着所有规则都必须放进本体定义中。复杂计算可以由函数或领域服务实现，审批也可以交给 Workflow 处理。它的意义是让流程能够基于统一的业务对象、状态和规则工作，而不必在每条流程里重新解释一遍企业的世界。

4、过程性规则与声明性规则

这里可以引入一个更有用的概念。过程性规则关注如何完成一件事，例如：

先检查库存

再检查信用

然后申请审批

最后生成发货任务

声明性规则关注什么条件成立、什么状态符合要求，以及哪些约束必须满足。例如：

订单满足发货条件，当且仅当：

- 订单状态允许发货；

- 所需库存已得到有效分配；

- 必要的质量检查已经通过；

- 相关业务约束得到满足。

前者描述执行过程，后者描述业务条件。实际系统中，两者需要结合：声明性规则不能替代任务调度、重试、超时和人工交接，Workflow 也不能代替所有业务规则。更合理的架构是：业务对象和规则提供一致的判断依据，Workflow 负责组织执行步骤。

Workflow 告诉系统怎么走，Ontology 帮助系统理解当前是什么情况，以及哪些路在业务上走得通。

## Ontology 与知识图谱：有了关系，还缺什么？

接下来要区分另一个容易混淆的概念：知识图谱。因为从表面上看，Ontology 和知识图谱都涉及实体、属性和关系，很容易被理解成同一件事，或者把 Ontology 简单理解为“知识图谱升级版”。这种理解并不准确。

1、知识图谱解决的是知识如何连接

假设企业建立了一张客户关系图谱：

张三

│ 任职于

▼

销售部

│ 负责

▼

客户 A

│ 下达

▼

订单 001

│ 包含

▼

商品 P

知识图谱可以把分散的数据和知识连接起来，让系统能够沿着关系检索信息。例如：

客户 A 由哪个销售团队负责？

客户 A 最近下了哪些订单？

这些订单涉及哪些商品？

某个商品关联哪些供应商？

它解决的是知识之间如何关联，以及如何从已知事实中发现相关信息。需要说明的是，知识图谱并不只是画一张关系图。成熟的知识图谱可以具有丰富的模式定义、约束和推理能力。W3C 的 OWL 标准就支持对类别、属性、个体及其关系进行形式化表达，并允许在形式语义规定的范围内进行逻辑推导。所以，不能把知识图谱简单理解成只能存储关系的数据库。

2、企业需要的不只是知道关系

假设知识图谱已经知道：

客户 A

↓ 拥有

订单 001

↓ 包含

商品 P

↓ 存放于

仓库 W

当 Agent 接到“优先发货”的任务时，这些关系能够帮助它找到相关对象。但它仍然需要进一步判断：

订单 001 当前能不能发货？

仓库 W 的库存是否已经分配给其他订单？

客户 A 的优先级是否允许改变发货顺序？

改变顺序是否违反企业的交付承诺？

如果允许调整，应该执行什么动作？

谁可以批准这个动作？

知识图谱能够参与其中，甚至可以通过扩展的规则和推理机制解决一部分问题。但如果企业要把这些能力组织成可供业务应用和 Agent 共同使用的运行体系，就需要进一步定义业务对象、业务状态、执行动作、权限和治理机制。这就是本文讨论的 Ontology 所强调的方向。

Knowledge Graph

描述事实、实体及其关系，并可支持知识检索和推理

面向业务运行的 Ontology

在对象和关系的基础上，进一步组织业务状态、规则、动作、权限和治理，让业务语义能够被应用与执行主体使用

这里的 Ontology 不是在所有知识图谱技术之上再增加几个字段就算完成了。它的重点是面向企业实际运行，把语义、逻辑和执行能力组织起来。因此，我更愿意用一个稍微准确一点的说法：

「知识图谱帮助我们连接和理解知识，面向业务运行的 Ontology 则进一步尝试把这些知识变成可用于判断和执行的业务模型。」

两者可以共存，也可以相互支撑。企业完全可以使用知识图谱技术来实现 Ontology 中的一部分对象关系和推理能力。

## 真正关键的变化，是规则不再只是散落在流程和代码里

前面讨论了四种建模方式，现在可以把问题再往前推进一步。为什么这些区别在 AI Agent 时代突然变得重要？因为传统软件大多由人明确规定执行逻辑，而 Agent 开始尝试根据目标自主选择下一步行动。

当执行主体从人编写的固定程序，扩展到能够动态规划的 AI 时，业务规则放在哪里，就变成了一个非常实际的工程问题。

1、过去：规则藏在不同的地方

一个企业可能同时存在：

数据库中的约束和状态字段

领域服务中的业务判断

Workflow 中的条件分支

API 中的校验逻辑

权限系统中的角色与访问控制

操作手册中的人工规定

老员工经验中的隐性规则

这些东西可能分别正确，却不一定能够相互对齐。例如，订单服务规定订单只有在“待发货”状态下才能取消；另一个自动化流程却只检查付款状态；客服操作手册则规定某些特殊订单需要主管审批。

只要这些规则没有被一致地表达和落实，系统就可能出现行为不一致。人类员工遇到这种情况，通常会去问业务负责人、查操作手册，或者根据经验判断。Agent 如果没有可靠的业务上下文，就可能只根据它能够访问的信息作出推测。

2、未来：让业务规则拥有明确的归属

这里的关键不是把所有规则搬到同一个地方，而是让每项规则都有明确的定义、责任人、适用范围和执行方式。例如：

业务问题

适合承载的职责

订单金额如何计算

订单领域逻辑或领域服务

当前订单能否取消

订单业务规则与状态约束

某个用户能否取消该订单

权限系统结合对象、动作与用户身份判断

取消后是否需要退款

业务规则与相关领域服务

退款需要经过哪些审批步骤

Workflow 与审批策略

取消后是否真正完成退款

执行结果核验与审计记录

Ontology 可以为这些规则建立统一的业务语义入口，但不需要亲自实现每一项底层逻辑。这是一种职责上的分工，而不是简单地把所有东西集中存储。

3、状态比流程分支更接近业务事实

例如，企业可能把“允许紧急发货”定义为一项业务能力。它不应该只取决于流程当前走到了哪个节点，还可能取决于订单状态、库存分配、客户承诺、仓库能力和审批结果。可以将条件抽象为：

urgent_allowed =

order_is_eligible

AND inventory_is_validly_allocated

AND delivery_constraints_are_satisfied

AND required_approval_is_granted

这只是一个示意表达。真实企业需要定义各项条件的精确含义、数据来源、计算方式以及异常时的处理规则。但它展示了一种不同的思路：把“是否允许紧急发货”定义为一个可被多个流程和应用复用的业务判断，而不是让每条流程都自己维护一套相似的分支。

当业务规则变化时，相关组件可以在明确的治理机制下更新，而不是依靠人工逐条寻找所有流程中的重复逻辑。

流程决定执行顺序，业务规则决定什么条件成立，状态描述业务当前的事实。三者需要配合，但不应该混成一件事。

## Ontology 为什么要把“动作”和“权限”纳入模型？

讲到这里，可能有人会问：前面说的对象、关系和规则，传统知识建模也能做到。为什么还要把 Action 和 Security 放进 Ontology？

原因很简单：企业 AI 的目标正在从“找到正确答案”，逐渐扩展到“在正确的条件下完成正确的事情”。这两者之间，隔着一道很大的工程鸿沟。

1、知道怎么做，不等于有权去做

假设 Agent 已经查明：

订单已经延迟三天

仓库 A 没有足够的可用库存

仓库 B 有一批符合要求的商品

从仓库 B 调拨可以缩短交付时间

从推理角度看，Agent 似乎已经找到了解决方案。但它能不能直接执行？不一定。企业可能规定，跨仓调拨必须由仓储主管批准；涉及特定金额的订单，需要销售负责人确认；库存已经被其他订单占用时，任何人都不能直接重新分配。

这里至少有三个不同的问题：

1. 事实问题：当前库存、订单和仓库的状态是什么？

2. 决策问题：在当前条件下，什么方案符合业务规则？

3. 授权问题：当前执行主体是否有权发起、批准或执行该动作？

即使 AI 的推理完全正确，也不意味着它自动获得了操作权限。因此，企业 Agent 的设计不能只考虑模型能否找到正确答案，还必须把业务规则和授权边界落实到真正执行操作的系统中。

2、Action 不应该只是一个 API 的别名

传统 Agent 的工具调用通常长这样：

Agent

↓

调用 update_order_status（）

↓

API

↓

修改订单状态

这在技术上没有问题，但从企业业务角度看，仍然不够完整。一个简单的 API 可能只接受 order_id 和新的状态值，却没有充分表达这次修改的业务目的、适用条件、审批要求和后续影响。如果 Agent 能够随意调用这个 API，甚至直接把订单从“待付款”改成“已发货”，那么系统的风险就非常大。

更合理的做法，是提供具有明确业务语义的动作：

Action： RequestInventoryTransfer

输入：

- 目标订单

- 来源仓库

- 目标仓库

- 调拨商品及数量

- 调拨原因

校验：

- 订单状态是否允许调拨

- 库存是否可以分配

- 是否影响其他订单承诺

- 当前用户是否有权发起

- 是否需要主管审批

执行：

- 创建调拨申请

- 进入审批流程

- 审批通过后执行调拨

结果：

- 记录动作状态

- 核验库存变化

- 更新相关业务对象

- 保留审计记录

这是一种概念性设计，具体执行方式取决于企业的系统架构。Palantir 的 Action Type 也不仅仅是一个 API 名称。官方文档将其描述为一组对对象、属性和关系进行修改的操作定义，并允许配置动作提交后的副作用。与此同时，Ontology 的权限机制可以覆盖对象类型、关系类型、动作类型以及具体对象和关系。

这说明，在面向企业运行的 Ontology 中，动作和权限并非附带的装饰，而是业务模型与实际执行之间的重要连接。

3、从 Tool Calling 到 Object + Action

可以把这两种设计思路放在一起看：

传统 Tool Calling

Agent

↓

Tool / Function

↓

API / Enterprise System

重点是：Agent 能够调用什么能力。

Ontology 驱动的业务执行

Agent 理解业务目标

↓

Object + Relationship + State

↓

Business Rule + Action

↓

Permission + Approval + Execution

↓

Result Verification + Audit

重点是：Agent 在什么业务条件下，可以对哪个对象执行什么动作，以及如何确认结果。

这里有一个值得注意的区别：Tool 是技术能力，Action 是带有业务语义的操作定义。一个 Action 最终完全可以通过 API、函数或领域服务执行。两者并不冲突。

真正重要的是，Agent 不应该只知道某个函数可以被调用，还应该理解它操作的是什么业务对象、需要满足什么条件，以及执行之后会产生什么影响。权限校验也不能只依赖模型的自觉——必须由可信的执行环境和后端系统实施，不能因为 Agent 在推理过程中认为“应该允许”，就直接放行。

## 一个完整案例：重新建模订单系统

前面的概念如果只停留在定义层面，很容易让人觉得 Ontology 只是另一套抽象术语。我们还是回到订单系统，把 ER、DDD、Workflow、知识图谱和 Ontology 放在同一个案例里。

假设一家企业有 ERP、CRM、WMS 和物流系统，现在希望构建一个能够处理订单延迟、分析库存、提出调拨方案，并在授权范围内推动发货的企业 Agent。

1、ER：先把数据结构设计清楚

传统数据库可能包括：

Customer

Order

OrderItem

Product

Warehouse

Inventory

Shipment

它们通过主键、外键和其他关联字段建立联系。这一层需要解决数据一致性、字段类型、索引、约束以及查询效率等问题。如果基础数据存在重复、编码冲突或者关联错误，后面的模型也会受到影响。

2、DDD：把领域逻辑组织起来

在业务代码中，可以划分为多个领域或限界上下文：

Order Domain

├── Order Aggregate

├── OrderPolicy

└── OrderService

Inventory Domain

├── Inventory

├── AllocationPolicy

└── InventoryService

Shipping Domain

├── Shipment

├── ShippingPolicy

└── ShippingService

这里的划分只是示例，不代表所有企业都应该采用同样的聚合和服务边界。订单领域负责订单规则，库存领域负责库存分配，物流领域负责发货业务。各个领域可以独立维护自己的模型，同时通过明确的接口、事件或其他集成机制协作。

3、Workflow：把任务组织成可执行流程

例如：

接收订单延迟事件

↓

查询订单与库存

↓

判断是否需要调拨

↓

生成调拨申请

↓

主管审批

↓

执行调拨

↓

重新检查库存

↓

安排发货

↓

核验最终结果

Workflow 负责管理步骤、超时、重试、审批等待、异常处理和任务交接。如果审批没有通过，流程应当停止或转入相应的处理分支，而不是继续执行原计划。

4、知识图谱：把跨系统的业务关系连接起来

通过客户、订单、商品、仓库、库存和发货单之间的关系，系统可以追踪订单涉及的业务对象。例如：

Customer A

↓ owns

Order 001

↓ contains

Product P

↓ available at

Warehouse B

↓ fulfills

Shipment 001

实际关系会更复杂。例如，订单可能包含多个商品，每种商品可能分布在多个仓库，发货单也可能与部分订单明细相关联。知识图谱可以帮助系统跨越单一表结构，理解这些对象之间的联系。

5、Ontology：把它们组织成一个可供业务使用的世界模型

在这一层，我们需要进一步定义：

Object / Property

订单、客户、商品、仓库、库存和发货单分别是什么，有哪些业务属性

Link

订单属于哪个客户，包含哪些商品，哪些库存分配给了哪个订单

Logic / Function

订单是否符合发货条件，调拨是否违反库存承诺，如何计算可分配数量

Action / Security

允许发起什么操作，需要什么审批，哪些用户或 Agent 可以执行

Audit / Result

动作由谁发起，经过哪些校验，实际执行了什么，最终业务状态是否符合预期

这时，Agent 收到“尽快处理延迟订单”的请求，就不必从零开始猜测整个企业的业务结构。它可以先定位订单对象，再沿着关系查找库存和仓库；根据业务规则评估调拨方案；判断是否需要审批；在获得授权后调用相应动作；最后核验库存和订单状态。

但这里仍然有一条重要边界：Ontology 负责提供业务语义和受控执行能力，不代表所有业务决策都应该交给 AI。涉及不可违反的业务约束、法规要求和权限边界时，应当由确定性的规则与后端控制机制保证。Agent 可以负责理解目标、组织信息、提出方案和选择允许的动作，但不能绕过这些控制。

这个案例也说明了为什么 Ontology 不等于另一套数据库——它可以建立在原有数据、领域服务、工作流和权限体系之上，把它们组织成一套共同的业务语义与操作接口。

## 为什么企业 Agent 可能需要 Ontology？

到这里，文章的重点就从传统建模转向了企业 AI。普通 Chatbot 主要处理信息输入和输出。企业 Agent 则可能需要跨系统查数据、做判断、执行操作，并对结果负责。这两种应用面对的工程问题并不一样。

1、普通 Agent 架构中的隐含假设

我们经常看到这样的架构：

LLM

↓

Prompt

↓

RAG

↓

Tools / MCP

↓

Enterprise Systems

这个架构没有问题。LLM 负责理解和推理，RAG 提供相关上下文，Tools 或 MCP 提供外部系统的访问能力。但这套架构有一个需要特别注意的地方：

「能够访问企业信息，不等于已经拥有统一的企业业务模型。」

RAG 检索到一份订单说明、一条库存记录和一份审批制度，并不意味着 Agent 已经知道这些信息分别对应哪个业务对象、彼此有什么关系，以及这些规则在当前状态下如何适用。MCP 可以让 Agent 通过标准化协议发现和调用工具，但协议本身并不会自动定义企业的业务语义，也不会天然解决数据一致性、业务授权和执行后的核验问题。这些能力仍然需要企业在架构层面设计。

2、Ontology-driven Agent 的工作方式

在一个由 Ontology 支撑的企业 Agent 架构中，Agent 可以围绕统一的业务对象开展工作：

User Goal

↓

Agent

↓

识别业务对象与目标状态

↓

Ontology

┌─────────┼─────────┐

↓ ↓ ↓

Data Logic Action

↓ ↓ ↓

Facts Rules Operations

└─────────┼─────────┘

↓

Permission / Approval

↓

Enterprise Execution

↓

Verification / Audit

它不再只是找到一个 API，然后尝试调用它。它需要围绕业务对象理解当前状态，利用规则判断允许的操作，再通过受控的执行接口推动业务变化。例如，Agent 不应该仅仅知道有一个 transfer_inventory（） 工具，而应该知道：

哪些库存对象可以参与调拨

库存分配和库存总量有什么区别

目标订单对交付时间有什么要求

调拨动作有哪些前置条件

哪些条件必须由后端进行校验

调拨申请由谁审批

调拨执行后，应该检查哪些业务状态

Ontology 的价值就在于，企业可以把这些定义组织成多个应用和 Agent 能够共享的业务基础，而不是每次开发新 Agent，都从头拼接一遍业务语义。

3、但 Ontology 不是 Agent 的全部

这一点必须说清楚。Agent 仍然需要模型、上下文工程、工具调用、任务规划、错误恢复、评估和安全机制。Ontology 不会自动解决模型幻觉，也不会保证模型每次都选择正确的业务动作。如果数据过时、对象关系错误、规则定义不完整，Agent 仍然可能得到错误结论。如果底层系统的接口没有正确实施权限检查，Ontology 中定义的权限也不能凭空保证执行安全。因此，更准确的理解是：

「Ontology 为企业 Agent 提供业务世界的语义与执行边界，Agent 则利用模型的理解和规划能力，在这些边界内完成任务。两者各自解决不同的问题。」

## Ontology 会不会成为新的复杂性陷阱？

讲到这里，很容易得出一个过于乐观的结论：既然 Ontology 可以统一对象、关系、规则、动作和权限，那企业只要建设一套 Ontology，所有系统和 Agent 的问题就都解决了。显然不是。

Ontology 本身也可能变成新的信息孤岛，甚至成为一个更难维护的复杂系统。我认为，至少需要警惕三种情况。

1、Ontology Fragmentation：每个团队各建一套

销售团队定义自己的客户，财务团队定义自己的客户，供应链团队又建立一套供应商与客户关系模型。每套模型在局部看来都合理，但相互之间缺少明确的映射和治理机制。最终，企业又回到了原来的状态：每个系统都有自己的业务语义，Agent 仍然需要在不同定义之间猜测和转换。

解决办法不是强迫所有团队使用一个巨大的统一模型，而是明确哪些业务概念需要共享，哪些概念应该保留在各自领域内部。对于客户、订单、商品等跨领域的核心概念，需要统一标识、关键属性和必要的关系定义；对于领域内部的细节，则可以通过清晰的边界和映射机制协作。

统一语义，不等于所有模型必须相同。

2、Model Drift：模型已经不再代表现实

企业业务一直在变化。客户等级规则会变，仓库布局会变，审批制度会变，产品和服务也会不断调整。如果 Ontology 建立后缺少持续维护，就会出现一个问题：现实业务已经变了，模型却还停留在过去。

最危险的情况，是模型看起来非常完整，字段、关系、规则和动作一应俱全，但实际上已经无法准确描述真实业务。这时，Agent 越是依赖这套模型，错误就越可能被放大。因此，Ontology 必须有明确的业务负责人、变更流程、版本管理、测试机制和持续验证方式。模型的正确性不是一次设计的结果，而是长期治理的结果。

3、Over Modeling：什么都想建模

还有一种情况，是团队把 Ontology 当成一项建模竞赛。所有业务对象都要抽象，所有关系都要显式表达，所有规则都要进入模型，甚至一些只在单一应用中使用的内部字段，也被当作企业级对象来管理。最后，模型越来越复杂，维护成本越来越高，而真正能够复用的业务能力却没有增加多少。

对此，我的建议是：不要从“企业所有对象有哪些”开始，而是从一个具体的业务问题开始。例如，先解决订单延迟后的跨系统查询、库存判断和受控调拨问题。明确这个场景需要哪些对象、关系、规则和动作，再决定哪些定义值得沉淀为共享能力。

！踩坑提示 🕳

Ontology 最大的挑战，不是把它建出来，而是确保它长期代表真实业务，并且值得被多个应用和 Agent 共同使用。

## 企业什么时候真的值得引入 Ontology？

并不是每个企业 AI 项目都需要一套完整的 Ontology。如果你只是做一个内部知识问答机器人，能够检索文档、回答问题，暂时不需要修改业务系统，那么做好数据治理、RAG、权限控制和评估，可能已经足够。如果业务流程固定、数据集中、业务规则简单，使用现有数据库、领域服务和 Workflow 也可能是更合适的选择。

我更建议从下面三个条件判断——企业是否需要认真考虑 Ontology？

条件一 · 跨系统共享业务语义

CRM、ERP、仓储、财务等系统需要围绕统一的客户、订单、商品等对象协同工作，多个应用或 Agent 需要复用这些业务定义

条件二 · 动作需要严格的权限和审计

AI 不只是查询信息，还需要修改业务状态、发起审批、调整资源或执行其他有业务影响的操作

条件三 · AI 开始参与决策与执行

Agent 需要跨多个业务领域理解状态、应用规则、选择动作，并核验最终结果，而不只是回答问题

如果暂时没有勾选这些条件，对于简单的问答或单一系统自动化，可以先使用更轻量的方案。这三个条件不是一个必须满足的标准，更不是说勾选两个就一定要上 Ontology。

它们真正想帮助我们识别的是：企业是否已经遇到传统数据模型、领域代码和流程编排难以独立解决的跨系统业务问题。如果这些问题已经影响到多个应用和 Agent 的协作，那么 Ontology 就值得进入架构讨论。

## 把几种建模方法放回同一套企业架构

最后，我们可以把全文讨论的内容整理成一张架构图：

这是一个职责划分示意，不是强制的技术依赖顺序。实际架构中，各层可以通过 API、事件、函数和数据映射双向协作。这张图里，每一层都有自己的价值：

ER / Database：保证数据结构清楚，数据能够被可靠地存储和访问

DDD / Domain Services：保证领域模型与业务规则能够在代码中得到正确实现

Workflow：保证任务可以按规定的步骤推进，支持审批、重试、超时和异常处理

Knowledge Graph：帮助企业连接实体、事实与关系，并支持知识检索和推理

Ontology：让业务对象、关系、状态、规则、动作和权限形成可供多个应用与 Agent 共同使用的业务语义基础

它们之间不是谁取代谁的问题，而是谁负责什么，以及这些职责如何协同的问题。对于已经有成熟 ERP、CRM、DDD 服务和工作流平台的企业，Ontology 更合理的切入方式，往往不是推倒重建，而是从一个跨系统业务场景入手，逐步把真正需要共享的业务语义和操作能力沉淀下来。

## 企业 AI 真正缺的，可能不是更大的模型，而是一个可计算的世界

回到文章开头的问题。为什么企业已经有了 ER、DDD、Workflow、知识图谱，还要讨论 Ontology？因为这些技术虽然都在描述企业的一部分，却不一定能单独为 AI 提供一套完整、统一、可执行的业务上下文。

一个数据库知道订单的字段，却不一定知道这个订单在企业中的完整业务含义。一个领域服务能够正确处理订单，却不一定能够独自提供跨客户、库存、仓库和物流的统一视图。一个 Workflow 能够规定任务怎么推进，却不应该成为所有业务规则的唯一载体。一张知识图谱能够连接客户、商品和订单，也不意味着企业已经建立了完整的动作、权限和执行治理机制。

当 AI Agent 真正进入企业，问题开始发生变化。我们不再只关心模型能否生成一段正确的答案，而是要问：这个客户是谁？这笔订单当前是什么状态？它与哪些商品、库存和交付承诺有关？什么条件下可以修改？谁有权执行？执行之后，如何确认业务真的发生了预期的变化？

这些问题，既需要数据，也需要领域逻辑、流程编排、知识关系和安全控制。它们之间需要有一种能够围绕真实业务对象建立共同语义的组织方式。这正是 Ontology 值得讨论的地方。

但我并不认为，企业未来只需要 Ontology 就够了。没有可靠的数据、清晰的领域边界、可执行的流程和严格的权限机制，Ontology 也只是另一套定义。真正值得关注的，是这些技术能否形成一套协同工作的体系，让 AI 不必每次都从数据库、文档和 API 中重新猜测企业的业务规则，而是能够在明确的业务语义和受控的执行边界内工作。

过去几十年，我们一直在给数据建模、给代码建模、给流程建模。企业 AI 带来的新问题是：我们能不能把企业正在运行的世界，也变成一个可以被软件理解、推理和执行的模型？

最后，如果全文太长记不住，你至少要知道：

「ER 管数据，DDD 管代码，Workflow 管流程，知识图谱管关系，而 Ontology 开始尝试把企业世界统一起来。」

这不是对过去技术体系的替代，而是企业从“让软件处理数据”，走向“让 AI 在业务世界中受控地行动”时，需要认真思考的一次架构变化。
