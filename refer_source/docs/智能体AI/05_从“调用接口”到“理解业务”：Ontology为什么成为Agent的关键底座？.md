企业 AI 的下一站，不是更准的检索，而是一个能观察、能计算、能推演、能行动的世界模型。

过去两年，企业做 AI 基本都在做同一件事：把 PDF、Word、制度文档、FAQ 接进来，然后让 AI 去检索。RAG 确实解决了很多问题，但最近我发现一个很奇怪的现象——RAG 做得不错的企业，遇到复杂业务问题时，AI 还是回答不好。

比如制造企业问：“供应商晚交 3 天，会影响哪些订单？”

这个问题看起来简单，但 AI 要回答，得先找到供应商对应的采购订单，再看这些订单用的物料，然后查库存够不够，接着看生产计划有没有排，哪条产线在用这批料，最后才能判断哪些客户订单会延期。

更麻烦的是，你还得知道现在的库存是多少，哪些订单已经排产了，有没有替代方案，切换产线会不会引发新问题。

这已经不是“搜索一段资料”能解决的了。它需要的是对一个正在运行的企业世界的理解。

我越来越觉得，企业其实早就有 Ontology（本体），只不过以前是隐式的。现在 AI 时代要做的，是把这个隐式本体变成显式的、可计算的、可推演的世界模型。

## 企业的本体一直都在，只是藏得很深

很多人觉得 Ontology 是个新概念。其实不是。你打开任何一家企业的数据平台，会看到各种表名：customer、customer_dim、crm_customer、customer_master。这些表名本身就在定义：“客户”这个东西在我们的世界里存在。

再看字段：customer_id、cust_id、party_id、account_id。这些 ID 字段在表达对象之间的关系。

再看 SQL：SUM(order.amount)。这里藏着一条业务规则：收入可以由订单金额聚合得到。

再往深了看，指标平台里“活跃客户”的定义，又是一套业务口径。而真正决定“这张 Customer 表财务能不能用”的，可能是某个干了十年的老员工——他会告诉你：“这张表销售用，财务别用，财务认另一个客户主体。”

所以企业不是没有本体，而是本体被拆散了，藏在数据库、SQL、ETL、指标平台、BI、API、流程、Excel、文档，甚至某个人的脑子里。

这就是 隐式 Ontology。它有三个问题：

1. 分散。同一个“客户”，CRM 叫 Account，ERP 叫 Customer，财务系统叫往来单位，风控系统叫风险主体。大家嘴上说的是同一个词，实际谈的根本不是一回事。

2. 隐含。很多规则没有正式记录下来。比如什么情况下客户可以被冻结？什么情况下订单可以取消？这些规则散落在 SQL、代码、流程和员工经验里。

3. 不可运行。传统数据字典能告诉你 customer_id 是客户 ID，但它回答不了：这个客户现在是什么状态？关联了哪些合同？如果冻结它，哪些流程会被阻断？

「数据越来越多，但企业世界本身并没有被真正建模出来。」

## RAG 解决了“找知识”，但企业问题已经变成“找路径”

RAG 出现后，这个问题被改善了不少。以前 AI 不知道企业内部的事，现在可以把文档放进去让它检索。

比如问：“合同变更后，发票应该怎么处理？”如果答案就在某份制度里，RAG 很合适。它会把问题转成向量，在知识库里检索相关文档，然后让 LLM 总结答案。

但复杂业务问题不一样。比如问：“这个合同变更，会影响本月哪些发票？”

答案不在任何一段文字里。你得先找到合同，然后找客户，再找计费规则，接着找账单，最后才能定位到发票。而且还得看当前版本和历史变更记录。

这时候问题已经从“哪段文字和我的问题最像”变成了我应该沿着哪条业务关系走。这两个问题完全不是一回事。

向量擅长的是相似度，但业务世界里大量重要信息是关系：谁属于谁、谁依赖谁、谁影响谁、谁替代谁、谁调用谁、谁受谁约束。

所以我认为，企业 RAG 的下一阶段不是被淘汰，而是位置会变化：RAG 负责“找内容”，Ontology 负责“限定世界”。简单说就是——

图决定去哪找，向量决定找哪句话，LLM 决定怎么理解

## 知识图谱够吗？还不够

有人会说，那就上知识图谱。方向没错，知识图谱最大的价值是把原来藏在文本里的实体和关系显式化。比如：供应商→供应→物料→使用于→生产线→生产→订单。这样多跳查询就容易多了。

但问题很快出现。传统知识图谱解决的是“这个世界是什么样的”，而企业真正关心的问题越来越是：现在发生了什么？接下来会怎么样？谁会受到影响？我应该怎么做？

比如，围绕“设备 A 故障”这件事，图上要表达的远不止一条静态关系：

1. 设备 A 属于生产线 B——这是 事实。

2. 设备 A 现在故障了——这是 状态。

3. 设备 A 故障后，生产线 B 产能下降 30%——这是 计算。

4. 生产线 B 产能下降后，订单 C 可能延期——这是 影响传播。

5. 把订单 C 切换到生产线 D——这是 行动。

「图上不能只有对象和关系，还需要状态、规则、函数、动作、事件、时间。」

这就是我认为现代 Ontology 和传统知识图谱最大的区别。

## 从“第三人称”到“第一人称”

传统 Ontology 更像个旁观者。它站在世界外面描述：“这里有一台设备，这台设备属于某条产线，这条产线生产某种产品。”这是第三人称视角，它在描述世界。

但如果我们把 Ontology 再推一步，会出现另一种设计：让对象本身参与世界运行。

比如一个 ProductionLine 对象，不只是有 name、capacity、status 这些属性，它还应该知道：我现在是什么状态？我有哪些设备？我正在生产哪些订单？哪些订单依赖我？我的实时产能是多少？如果我停机，会影响谁？有哪些替代产线？切换到替代产线需要满足什么条件？切换后成本会增加多少？

这时候 Ontology 就不再只是“描述对象”，而是在表达：这个对象在业务世界里如何存在、如何变化、如何影响其他对象，以及它能够做什么。

这就是第一人称 Ontology

## 给业务对象装上六个“器官”

如果用最简单的方式理解现代 Ontology，可以把它拆成六件事：

1、Object：世界里有什么

Customer、Order、Supplier、Equipment、ProductionLine、Warehouse、Contract。这是世界的基本组成。

2、Relationship：它们怎么连接

供应商供应物料，物料被产线使用，产线生产订单，订单属于客户。这里的关系不能只是为了画图好看，它得能被查询、计算、传播。

3、State：现在发生了什么

这是很多传统知识图谱容易缺失的一层。设备有运行、降额、故障、维修、停机这些状态。订单有待确认、生产中、延期、部分交付、完成、取消。客户有正常、关注、冻结、流失。对象没有状态，就很难表达一个正在运行的业务世界。

4、Rule：什么情况下发生什么

比如库存低于安全库存时产生补货风险，设备故障时重新计算产能，合同逾期时触发风险规则进入复核流程。规则开始成为 Ontology 的一部分。

5、Function：怎么算

风险评分、预计到货时间、产能利用率、库存覆盖天数、交付及时率、客户价值、供应商风险。这些都不是简单属性，它们是可以计算出来的业务语义。

6、Action：可以做什么

这是最关键的一层。冻结账户、调拨库存、切换产线、调整生产计划、创建复核任务、审批合同、替换设备。一旦 Action 进入 Ontology，世界就从“可观察”变成了“可操作”。

Palantir 当前的 Ontology 体系已经把 Object、Link、Function、Action 这些能力组合在一起，并通过 Ontology MCP 向 Agent 开放。这个产业变化值得关注。

## 本体应该进入运行层

过去很多企业的架构是：

数据 → 数据平台 → 知识库 → RAG → LLM → Agent

现在可以换个思路：

Enterprise Data → Ontology → Business World → State/Rule/Function → Simulation → Action → Agent

两种架构最大的区别是什么？第一种架构里的 AI 在知识里找答案，第二种架构里的 AI 在业务世界里做事情。

「Ontology 最终不应该只是个 Knowledge Layer，它更像一个 World Runtime——企业世界的运行层。」

## 为什么 Simulation 会越来越重要

假设现在有条生产线故障，AI 发现可以把订单切到 B 产线。听起来不错，但企业不会因为 AI 说了一句话就直接执行，因为切换后可能出现：B 产线产能不够、工艺不兼容、原材料不够、成本增加、质量风险上升、其他订单被挤占。

所以真正成熟的系统，应该允许 AI 先做一件事：不要直接改生产，先在副本里试一次。

具体来说就是：克隆当前的 Production World，在 Simulation World 里切换产线，看状态如何传播，重新计算，查看影响，对比差异，确认后再在生产环境执行真正的 Action。

这就是“先演后决”

如果要调整一个审批阈值，也一样。先别直接修改生产环境，而是问：这个规则会影响哪些客户？哪些订单会被拦截？哪些流程会变化？风险是增加还是降低？然后在隔离副本里跑一次，看完结果再决定是否执行。

这时候 Ontology 就不再只是语义层，它已经开始承担 业务模拟器 的角色。

## Agent 缺的不是 Context，是 World

这也是为什么我越来越觉得，Agent 时代的 Context Engineering 会发生一次变化。

以前大家理解 Context，更多是：

Prompt + Conversation + RAG + Tools

以后可能越来越接近：

Entity → Graph → State → Permission → Version → Relevant Context → Vector Retrieval → LLM

比如 Agent 收到“这个订单还能不能按时交”，它第一件事不应该是“去向量库搜一下”，而应该先定位：到底是哪一个订单？然后沿着下面这条路径，根据当前状态进行计算：

Order → Production Plan → Production Line → Inventory → Supplier → Logistics

这时候向量检索仍然有价值，比如查“这个产品的特殊交付规则是什么”，但它已经不是整个 Context 的边界。

「Ontology 负责定义“我正在看哪个世界”，RAG 负责补充这个世界里的文本知识。」

想象一下，一个 Agent 被问三个问题：

这张订单能不能按时交？

它需要订单、库存、产能、设备、物流、供应商、时间。

供应商晚 3 天会发生什么？

它需要沿着供应商→物料→库存→生产→订单→客户这条路一路传播。

换一条生产线能不能救回来？

它需要当前状态、约束、计算、模拟、行动。

这时候你就会发现：Agent 需要的根本不是一个无限大的 Facts 仓库，它需要的是一个可以观察、推理、计算、模拟、行动的 World。

「没有 Ontology 约束的时候，Agent 只能猜。有了可运行 Ontology 以后，Agent 才有机会在一个受约束的业务世界里行动。」

## Agent Action 和 Ontology Action 的区别

很多企业现在已经有 Agent 了，Agent 可以调用：查询客户、创建订单、修改订单、发送邮件、调用 ERP 接口。看起来已经能“行动”了。

但这里有个区别。普通 Agent Action 更像：

Agent → API → System

Agent 知道“这里有个接口”。但 Ontology Action 应该进一步表达：

Object → Action → Precondition → Permission → Impact → State Change

比如“冻结客户”这个动作，真正的业务语义应该包括：当前客户是什么状态？谁有冻结权限？什么情况下允许冻结？冻结后哪些订单受影响？哪些流程会被阻断？是否需要审批？冻结之后客户状态如何变化？

这时候 Action 已经不是一个 API，它是一个 业务动作。

「Agent Action 是工具调用，Ontology Action 是业务语义。」

这也是 Ontology 能成为 Agent 底座的关键原因之一。

## 落地时千万别从“建 Ontology”开始

这是企业最容易踩的坑。很多项目一开始就组织一批人：“我们要建设企业级 Ontology。”然后开始设计 Customer、Supplier、Product、Contract、Order、Employee、Organization、Region……Class 越画越多，关系越画越复杂。

半年后得到一张非常漂亮的架构图，然后问：“这个东西现在解决了什么问题？”大家突然不知道了。

「Ontology 建设最小的单元，从来不应该是 Class，也不应该是 Table，而应该是 Business Loop——一个真正跑得起来的业务闭环。」

九步走通一个最小闭环

第一步：找一个值得解决的问题

适合 Ontology 的场景一般有三个特点：单表解决不了、有业务上下文（不是简单查“今天有多少订单”，而是“哪些订单存在交付风险，为什么”）、最终存在行动。比如设备故障影响订单、供应商延迟影响交付、客户流失风险、库存异常、生产计划调整。

第二步：画业务闭环，不要画 Class 图

比如设备故障场景：设备故障→确认状态→判断影响→识别受影响订单→计算交付风险→寻找替代方案→切换产线→重新计算→验证结果。

然后反过来问：这个闭环需要哪些对象？于是得到 Equipment、ProductionLine、Order、Alarm、Metric、Risk、Action。再问这些对象之间有什么关系，每个对象有哪些状态，哪些东西需要计算，哪些动作可以执行。

这和传统的“先设计 Class，再想业务怎么用”是反过来的。由业务行为反推 Ontology，而不是由 Class 反推业务。

第三步：只建一个“最小世界”

比如设备故障场景，一期可能只需要 Equipment、ProcessUnit、ProductionLine、Order、Metric、Alarm、Risk、Action。没必要第一天就把 Supplier、Customer、Contract、Finance、Employee、Region、Warehouse 全拉进来。

「Ontology 真正的价值不是“覆盖了多少实体”，而是“能不能让一个业务闭环真正运行起来”。」

第四步：状态一定要进模型

如果只建 Equipment(name, type, line)，你只是描述了一台设备。但如果增加 status、last_update、capacity、health、maintenance_state，再加入状态转换（运行→降额→故障→维修→恢复），这个对象才开始真正“活起来”。

第五步：关系要能计算，不是为了好看

很多知识图谱项目图很漂亮，节点很多，边也很多，但问一句“这条设备故障会影响哪些订单”就答不出来。这种关系就是 低价值关系。

真正有价值的关系应该能参与查询、计算、推理、传播、Action、Simulation。比如设备→工艺→下游工艺→质量指标，当设备故障时，设备能力下降→工艺能力下降→质量风险上升。这条关系才真正进入了运行世界。

第六步：接真实数据，不只做 Demo

Ontology 最终必须接真实企业系统：ERP、MES、CRM、WMS、IoT、数据库、消息系统、API、文件。经过数据清洗→对象映射→关系映射→状态映射，最后形成 Ontology。

这里有个重要原则：AI 抽取出来的知识只能先当候选知识。比如 LLM 从文档里抽出“A 公司是 B 公司的供应商”，不能因为 AI 说了就直接当企业事实。正确流程应该是：

AI 抽取 → Candidate Knowledge → 业务验证 → Schema 确认 → 版本化 → 正式发布

！AI 猜出来的 Ontology 🕳

Ontology 一旦成为 Agent 行动依据，错误的关系比没有关系更危险。

第七步：先查询计算规则，最后再上 Agent

不要一开始就做“让 Agent 自己决定”。正确的顺序应该是：

1. 第一阶段回答“哪些设备故障”。

2. 第二阶段回答“哪些故障影响关键产线”。

3. 第三阶段回答“哪些订单受影响”。

4. 第四阶段回答“哪些订单高风险”。

5. 第五阶段最后才是“哪些应该优先处理、怎么处理、执行后会发生什么”。

先让世界模型稳定，再让 Agent 进入这个世界。

第八步：做 Action 闭环

如果 Ontology 只能查数据，那它仍然只是个高级查询系统。真正完整的闭环应该是：

识别 → 影响分析 → 决策 → 执行 → 状态变化 → 重新计算 → 验证

比如设备故障，系统发现 3 个订单受影响，推荐 B 产线切换，执行后 ProductionLine 状态变化→产能重新计算→订单交付时间重新计算→风险重新计算。这时候系统才真正闭环。

第九步：从一个闭环长成企业 Ontology

不要一开始建“全企业本体”。可以从设备→工艺→生产→订单开始，跑通后再加入供应商→物料→库存，然后继续加入客户→合同→收入。

最后不同业务闭环开始共享对象。设备既属于生产系统又影响订单，订单既关联生产又关联客户，供应商既关联采购又关联库存。慢慢地：

一个闭环 → 多个闭环 → 共享对象 → 共享关系 → 企业 Ontology

这比一开始画一张巨大的企业本体图，更容易真正跑起来。

## Palantir 在做什么

如果观察最近几年的企业 AI 产业，Palantir 的 Ontology 路线越来越值得研究。它的核心思路不是单纯做 Knowledge Graph，而是把 Object、Link、Function、Action 逐渐组合成一个能支撑业务应用和 Agent 运行的 Operational Ontology。

更值得关注的是，2026 年 Palantir 把 Ontology 对象、查询函数和 Action 能力通过 MCP 暴露给 Agent，让外部 Agent 能在受治理的业务语义之上进行访问和行动。

Microsoft 的 Fabric IQ 也在朝类似方向发展：将 Ontology 用于表达业务实体、关系和语义，并与实时数据和 Operations Agent 结合，用于运营监控和行动。

「这背后其实是同一个变化：Ontology 正在从“语义层”向“Operational Layer”演进。」

这里不一定意味着所有企业都要照搬 Palantir，真正值得学习的是它背后的架构思想：不要把 Ontology 做成一张漂亮的图，而是让 Ontology 真正进入业务运行。

## 从“知识”走向“世界”

回头看过去几年，企业 AI 一直在经历几次变化：

1. 最开始是 Data——企业有什么数据？

2. 后来是 Knowledge——企业知道什么？

3. 然后是 RAG——AI 如何找到企业知识？

4. 再往后是 Graph/Ontology——企业世界由什么对象组成？它们之间是什么关系？

5. 再进一步是 Operational Ontology——这些对象现在是什么状态？遵循什么规则？可以做什么？

6. 最后才是 Runnable World Model——如果我改变一个对象，这个世界会发生什么？

7. 然后是 Agentic Enterprise——AI 能不能在这个世界里观察、推理、推演、行动？

这条路线真正有意思的地方在于，AI 的竞争不再只是谁的模型更大、谁的 RAG 检索更准，未来企业 AI 越来越重要的一个问题可能是：谁能把企业真实世界建模得更完整、更准确、更可运行。

SUMMARY

## 总结

今天很多企业的数据已经非常丰富。数据库有几十年积累，ERP、CRM、MES、WMS 都有，数据仓库有，指标平台有，知识库也有。但这些东西共同组成的，只是一堆“关于企业的数据”。

真正缺少的，是一个能够把这些数据组织成 对象 + 关系 + 状态 + 规则 + 计算 + 事件 + 行动 的统一业务世界。

「Ontology 不是给企业画一张世界地图，而是把企业真实世界变成一套 AI 可以理解、可以计算、可以推演、可以行动的运行模型。」

RAG 不会消失，知识图谱也不会消失，它们会进入一个更大的体系。未来更完整的企业 AI 架构可能是：

RAG 补充知识 → Graph 连接关系 → Ontology 定义世界 → Runtime 计算状态 → Simulation 推演后果 → Action 改变世界 → Agent 在世界中工作

「过去的 AI 在知识库里寻找答案，下一代企业 AI 要进入一个真正可以运行的世界。从隐式本体到显式 Ontology，再到可运行世界模型，这可能才是企业 AI 从“会回答”走向“会做事”的关键一步。」
