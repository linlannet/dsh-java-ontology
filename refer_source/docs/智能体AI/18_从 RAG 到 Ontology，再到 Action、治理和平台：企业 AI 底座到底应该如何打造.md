不要一上来就复制 Palantir，也不要一上来就建所谓「企业级 AI 大平台」。真正应该做的，是先判断——你的业务到底需要 AI 走到哪一层。

最近跟不少企业团队聊 AI 落地，发现一个有意思的变化。前几年大家问的问题是：「哪个大模型最好？」后来变成：「RAG 怎么做？」再后来是：「Agent 怎么做？」现在越来越多企业问的是：「我们到底应该怎么落地？」

这其实比选模型难得多。因为企业真正进入生产环境以后，很快就会发现，模型只是其中一环。你可能已经有了国产大模型，有了知识库，有了 RAG，有了 Agent，有了 MCP，甚至已经搭了一个看起来非常漂亮的 AI 平台。但是业务部门还是会问：

「它为什么不知道我们公司的客户是什么？」

「为什么同一个客户，在销售、财务和客服那里说法不一样？」

「为什么它能查到订单，却不能判断这个订单为什么延期？」

「为什么它知道应该修改订单，却不知道自己有没有权限修改？」

「为什么 POC 的时候什么都能跑，一上线就不敢让它碰真实业务？」

这些问题其实都指向同一个地方：企业 AI 的难点，已经不是让模型「会说话」，而是让 AI 真正进入企业的业务世界。

有些企业做到 RAG + Workflow 就够了。有些企业需要增加一层业务语义。再往上，才是完整的语义、行动、治理一体化。真正成熟的路线，不是所有企业最终都走到同一个终点，而是：需要哪一层，就建设哪一层。

## 先把一个误区说清楚：国产化 AI，不等于「国产版 Palantir」

这几年研究 Palantir，很多团队最后都会得出一个结论：Palantir 的核心好像就是 Ontology、Object、Link、Action、Agent、Workflow、Permission、Audit。于是很自然地会产生一个想法：「既然这些东西我们都能找到开源替代品，那我们把它们拼起来，是不是就能做一个国产版 Palantir？」

从技术组件的角度看，确实可以拼出相当一部分能力。但是，这个问题本身就问错了。因为 Palantir 真正难复制的地方，从来不是某一个组件，而是：这些组件长期运行在一个统一的业务语义、操作和治理体系里。

Palantir 官方现在对 Ontology的描述已经非常明确：Ontology 不只是把数据变成对象和关系，还把 Actions、Functions 和动态安全能力放在同一个业务操作层中。它的目标并不是简单做一个数据目录，而是把企业里的数据、逻辑、动作和安全组织成一个能够支持真实业务决策的运行层。

这件事情如果拆开看，其实一点都不神秘。企业可以分别拥有：大模型 + 知识库 + 图数据库 + 工作流 + API + MCP + 权限系统 + 审计系统。每一个东西都可以找到替代品。真正困难的是：

谁定义业务对象？谁定义对象之间的关系？谁定义什么动作可以执行？谁定义谁可以执行？动作执行以后如何回写业务系统？业务变化以后谁负责维护？权限变化以后谁负责同步？模型回答错了以后怎么追溯？

这才是成本。所以我更愿意把 Palantir 的价值理解成一句话：

它不是把企业需要的零件全部发明了一遍，而是把这些零件变成了一辆可以长期运行的车。

这也是为什么企业自己拼装时，真正花钱的地方通常不是买软件，而是：集成、建模、治理和长期维护。

## 真正应该问的问题：我的企业到底需要哪一层？

企业 AI 可以粗略理解成五个阶段：AI 能回答问题 → AI 能结合企业知识回答问题 → AI 能调用企业工具完成工作 → AI 能理解企业业务对象和业务关系 → AI 能在权限和治理边界内，自主参与业务决策和执行。

对应起来就是六个 Level：

Level 0

模型 + Prompt

Level 1

模型 + RAG

Level 2

模型 + RAG + Workflow / Tool

Level 3

模型 + Agent + Tool + Workflow

Level 4

Agent + Business Object + Relation + Action

Level 5

Semantic + Operational + Governance + Agent + Audit

这里最容易犯的错误就是：所有企业都按照 Level 5 去建设。实际上，大量企业连 Level 2 都没有真正跑通。如果你只是希望 AI 帮销售生成周报，那么完全没必要先做一套企业 Ontology。

如果你的需求是：「帮我从制度库里找到差旅报销标准。」RAG 基本就够了。但如果你的需求变成：「找出最近三个月采购金额增长最快、同时交付延期率最高的供应商，并判断它影响了哪些重点订单，然后给采购经理创建风险工单。」事情就完全不一样了。

这时候 AI 不只是找一段文字，它必须理解：供应商 → 供应关系 → 产品 → 订单 → 客户 → 重点订单。还需要知道：什么叫重点订单？什么叫延期？谁能看采购金额？谁可以创建工单？什么情况下需要人工审批？这时候，你就开始进入 Ontology 的世界了。

## 判断企业走哪条路，我建议只看三个维度

不要先讨论 Dify，也不要先讨论 UModel，更不要先争论到底是 GraphRAG 还是 Knowledge Graph。先回答三个问题。

第一维：你的数据到底有多复杂？

第一档 · 简单

比如一个 CRM、一个知识库、一个业务数据库，数据结构比较统一。这种情况下，AI 主要是查、总结、生成、分类，不需要复杂语义建模。

第二档 · 中等

系统开始多起来：CRM、ERP、OA、财务、客服、数据仓库。问题也开始变化。比如销售说「客户」，财务说「客户主体」，客服说「服务对象」，数据仓库里面又叫 customer_id。这时候 AI 如果没有统一的业务语义，很容易出现一个问题：每个系统都能查，但是查出来的东西拼不起来。

第三档 · 复杂

集团型企业通常会出现：多组织、多区域、多业务系统、多数据中心、实时数据、历史数据、多种权限、跨部门协同、跨系统操作。这时候，问题已经不再是「怎么把文档塞进向量数据库」，而变成：「企业世界应该如何被 AI 表达？」

第二维：AI 到底需要做什么？

这个问题比「是不是 Agent」更加重要。我通常把 AI 的能力分成四个层次：

1. 回答　用户 → AI → 答案。例如：「公司的年假制度是什么？」这就是典型知识问答。

2. 分析　用户 → AI → 多个数据源 → 分析 → 结论。例如：「为什么这个区域本月销售额下降？」这时候 AI 已经开始跨数据源工作。

3. 决策辅助　例如：「哪些供应商存在较高履约风险？」AI 需要：订单 + 供应商 + 交付记录 + 质量数据 + 历史数据，然后进行判断。

4. 真正执行　例如：「把高风险供应商加入重点关注名单，并通知采购负责人。」这时候 AI 就必须：查询 → 判断 → 调用 Action → 修改业务系统 → 通知相关人员 → 记录审计。

这已经不是普通的 RAG 应用了。所以有一个非常重要的判断：

「当 AI 从『回答』进入『执行』，企业的技术架构会发生质变。」

因为回答错了，最多是一段错误答案。执行错了，可能就是：修改错订单、发错邮件、删除数据、错误审批、泄露敏感信息。因此：AI 一旦进入 Action 世界，治理就不再是附加功能。

第三维：企业有没有「桥梁型人才」？

这是我认为国内企业最容易忽略的问题。很多公司说有业务部门、有数据团队、有 AI 团队、有开发团队，但是项目还是推进不下去。为什么？因为这几个团队说的不是一种语言：

业务团队说：「这个客户不能这么处理。」

数据团队问：「具体是哪张表？」

AI 团队问：「有没有 API？」

开发团队问：「接口定义在哪里？」

最后大家开了三个月会。真正缺少的，是一个人能够把下面几件事串起来：业务问题 → 业务对象 → 数据对象 → 技术接口 → AI 能力 → 业务动作。这就是前面文章里反复讲的 FDE。FDE 的核心价值，从来不是「会不会写代码」，而是：能不能把客户现场的问题翻译成一个可以运行的技术系统。

到了语义建模阶段，这个角色的重要性反而更高。因为语义模型不是 DBA 把表结构重新画一遍。

## 于是，企业 AI 就有了三条完全不同的路线

现在可以正式做判断了。

路径 A：RAG + Workflow

这是大多数企业真正应该从这里开始的地方。不是因为它最先进，而是因为：很多业务根本没有复杂到需要 Ontology。

典型场景：企业制度问答、产品知识库、客服 FAQ、销售资料查询、招投标文件分析、周报生成、会议纪要、合同摘要、简单数据查询、报告生成。这些需求共同特点是：知识多，但业务关系并不复杂。

最小架构：

用户 → AI 应用 → RAG / Workflow → 企业知识 → 企业数据库 / API

模型可以根据企业要求选择国产模型或私有部署模型。编排层可以采用 Dify 等开源平台，也可以自己构建。这里需要特别注意一个变化：Dify 已经不能简单理解成几年前那个「做个 RAG Demo 的工具」。截至 2026 年 9 月，Dify 的公开版本已经持续扩展 Agent、工具、MCP、Human Review、Skill、Sandbox 等能力，产品形态正在明显向 Agent 应用平台演进。所以今天拿 Dify 做企业 AI，已经可以覆盖相当一部分从知识检索 → Workflow → Tool → Agent → 人工确认的场景。

「路径 A 的关键，不是把 AI 做出来，而是：两周之内让真实用户用起来。」

这是很多企业 POC 最大的问题。第一周搭知识库，第二周优化 Prompt，第三周换模型，第四周换 Embedding，第五周做 UI，第六周开始讨论平台架构，第七周老板问：「谁在用？」没有人。所以路径 A 最重要的指标不应该是「我们的 RAG Recall 达到了多少」，而应该是：「有没有真实业务人员愿意每天使用？」

比如做销售周报。第一版可能很粗糙，但是只要销售真的开始用，你马上就会发现：哪些数据不准、哪些字段缺失、哪些规则没有写清楚、哪些报告格式不符合习惯。这些真实反馈，比你在会议室里讨论三个月架构有价值得多。

路径 A 什么时候开始撞墙？通常会出现三个信号：

信号一 · 用户开始问关系问题

例如「这个供应商影响了哪些订单？」这不是简单搜索，它需要 Supplier → Product → Order。

信号二 · AI 开始执行动作

例如「查一下订单，然后把延期订单创建成工单。」这时候 Read + Reason + Write 已经出现。

信号三 · 同一个概念出现多个答案

销售说客户有 10 万家，财务说客户只有 8 万家，CRM 又是 12 万家。AI 说「根据不同系统的数据，客户数量分别是……」看起来很诚实，但业务真正需要的是：到底什么叫客户？

这时候，企业开始需要语义层。

路径 B：给 AI 增加一层「业务语义」

路径 B 是我认为未来几年国内企业 AI 真正会大量出现的一条路线。它不是直接复制 Palantir，而是：先给现有 AI 系统补一层业务语义。

什么叫业务语义？举个最简单的例子。数据库里可能有：customer_id、order_id、supplier_id、product_id。对于数据库来说，这些只是字段。但是业务世界里，它们对应的是：客户、订单、供应商、产品。而且它们之间存在关系：客户拥有订单，供应商供应产品，产品出现在订单。这就是语义。

RAG 和语义模型到底有什么区别？假设你问：「华东地区有哪些高风险供应商影响了重点订单？」

RAG 的典型思路

问题 → Embedding → 检索相关文本 → LLM → 答案

语义模型的思路

问题 → 识别业务对象（Supplier、Order、Region、Risk）→ 识别关系（Supplier impacts Order）→ 执行查询 → 判断风险 → 返回结果

一个主要在寻找「相关内容在哪里」，另一个主要在回答「企业世界里的这些东西是什么关系」。这就是本质区别。

2026 年值得关注的一个变化：UModel

阿里巴巴开源的 UnifiedModel，也就是 UModel，目前已经把自己的定位明确为：面向企业 AI、数据治理和运营智能的 vendor-neutral semantic runtime。它不是简单的数据目录。官方项目目前支持：企业对象、业务对象、数据集、Link、Topology、Query、REST、CLI、SDK、AgentGateway、MCP、Agent Skills。并且提供了可以本地运行的服务、Web UI、MCP Server 和示例工程。

这个方向为什么值得关注？因为它实际上代表了一种变化——过去企业的数据体系更多是：数据表 → 数据仓库 → BI；现在开始出现另一种需求：业务对象 → 业务关系 → 语义运行时 → Agent。也就是说：数据不再只是给人查，也开始成为 Agent 可以理解和操作的业务世界。

！踩坑提示 🕳

不要把 UModel 当成「国产 Palantir」。UModel 可以解决的是：语义如何表达、对象如何组织、关系如何查询，以及 Agent 如何进入这个语义世界。但一个企业级 AI 系统真正运行起来，还需要：语义 + 模型 + Agent + 工具 + 业务 API + 权限 + 审批 + 审计 + 运维。所以不要因为出现了一个语义运行时，就认为「企业 AI 平台已经解决了」——远远没有。它只是把其中最麻烦的一层抽象了出来。

路径 B 最小怎么做？我的建议非常简单：不要从「企业 Ontology」开始。先找一个业务对象，比如「供应商」，然后只回答五个问题：

1. 供应商有什么属性？　供应商名称、供应商等级、所属区域、合作状态、风险等级。

2. 供应商和谁有关系？　供应商供应产品、供应商影响订单。

3. 哪些动作和供应商有关？　创建风险工单、修改风险等级、通知采购负责人。

4. 谁可以看？　采购全部可见、销售只看影响订单、财务可以看金额、普通员工不可查看敏感信息。

5. 谁可以操作？　普通采购只能查看、采购经理可以调整风险等级、部门负责人可以关闭风险工单。

你会发现，一个非常小的业务对象模型已经出来了。

真正有价值的不是「建了一个图」

很多团队一听到 Ontology，就开始画图。最后得到客户、供应商、产品、订单、合同、发票、员工、部门、组织、区域、项目、渠道……连起来像一张巨大的蜘蛛网。看起来非常专业，实际上可能没什么用。因为：

「图不是目的，业务动作才是目的。」

比如「为什么这个订单延期？」如果 AI 能沿着：订单 → 产品 → 供应商 → 交付记录 → 异常记录查出原因，然后「创建风险工单」，这时候语义模型才真正产生价值。所以建模最重要的一条原则就是：从业务问题倒推对象，而不是从数据库表正向堆对象。

这也是为什么「谁来建模」比「用什么工具」更重要

因为语义建模不是 DBA 的简单工作。DBA 会告诉你 customer_id varchar（32），但业务人员真正关心的是：「这个客户是签合同的客户，还是最终使用产品的客户？」财务可能关心「这个客户是不是付款主体」，客服可能关心「这个客户是不是服务对象」，销售又可能认为「只有进入 CRM 的客户才算客户」。这些都不是数据库字段能直接告诉你的。

所以语义建模本质上是一种：业务语言 → 数据语言 → AI 语言之间的翻译工作。这也是 FDE、业务架构师、AI 解决方案架构师真正有价值的地方。

路径 C：深度建模 + 平台化

当企业进入集团级场景以后，问题又变了。假设现在有：20 个业务域、100+ 系统、数千张核心表、几十种角色、大量 Agent。这时候如果每个项目自己维护客户模型、订单模型、权限、Action、API、审计，很快就会出现一个问题：重复建设。于是路径 C 出现了。

路径 C 真正建设的不是「一个大知识库」，而是一套：企业 AI Operating Layer。它至少包含：

Semantic

Object / Link、Business Rule、Metric

Operational

Action / API、Workflow、Agent

Governance

Permission、Audit、Policy

这时候企业开始真正关心：对象标准、关系标准、Action 标准、权限模型、Agent 生命周期、Tool 注册、审计、数据血缘、模型路由、运行监控、版本管理。这已经不是一个普通 AI 项目了。

为什么大多数企业不应该直接走路径 C？

因为路径 C 最贵的地方根本不是第一版开发，而是：未来五年的维护。业务会变、系统会变、组织会变、权限会变、数据会变、政策会变、API 会变、模型会变、Agent 也会变。

比如今天定义「客户」，明年集团统一主数据之后，可能变成：客户主体、客户账号、客户联系人、客户服务对象。那么语义层要不要调整？当然要。再比如今天某个 Agent 可以直接创建工单，明年风险等级规则变化了：低风险自动执行、中风险需要主管确认、高风险必须人工审批。权限和 Action 都得变化。

所以企业真正进入路径 C 后，会出现一个新的组织能力：Semantic Governance（语义治理）。

## 治理为什么一定要从第一天开始？

很多企业做 POC 时喜欢说：「权限先不做，等上线以后再补。」这是非常危险的。因为 AI 和传统软件最大的不同之一，是：AI 会主动组合信息和工具。一个传统页面可能只有三个按钮，Agent 可能同时拥有：CRM 查询、ERP 查询、数据库查询、邮件、工单、审批、文件。

如果权限设计不好，Agent 很容易变成一个：权限放大器。企业真正需要治理的，不只是「数据能不能看」，至少要回答四个问题：

1. 谁能看？　用户 → 数据。

2. AI 能不能看？　用户可以看 ≠ Agent 一定可以看。Agent 需要继承或者明确获得相应权限。

3. AI 能不能操作？　查询订单 √、修改订单 ？、取消订单 ×、删除订单 ×。不能因为 Agent 能调用 API，就默认它拥有完整操作权限。

4. AI 操作以后谁负责？　必须留下用户、Agent、时间、Prompt / Task、工具、对象、Action、结果、审批。这样出了问题才能追溯。

这其实也是 Ontology 最值得学习的地方

Palantir 的公开文档里，有一个非常值得国内企业借鉴的设计：它不是简单在 Ontology 外面放一个权限网关，而是把对象、关系、Action 本身纳入权限体系。对象和链接的数据访问、Action 的执行权限都有对应的授权机制。这背后的思想非常重要：

「治理应该贴着业务对象和业务动作发生。」

而不是 AI 系统 → 统一权限网关就认为安全问题解决了。

国产化环境下，Apache Ranger 可以做什么？

对于很多企业的数据治理场景，Apache Ranger 依然是一个值得考虑的组件。它能够提供：Access Policy、Data Masking、Row Filtering、Audit。并且策略可以结合资源、用户、用户组、资源属性、请求上下文等条件。但是这里有一个非常重要的工程细节：Ranger 给出授权判断，并不意味着业务应用自动完成了执行。官方文档明确说明，应用本身仍然需要执行 Ranger 返回的授权、脱敏和过滤决定。这对 Agent 系统尤其重要。

所以真正的链路应该是：

Agent → Tool → Policy → Authorization → Business API → Audit

而不是：Agent → 直接调用数据库

## MCP 在这里到底是什么？

MCP 最近非常火。但企业最容易出现的误解就是：「我们把系统都做成 MCP，就完成企业 AI 架构了。」其实不是。MCP 更接近：Agent 和外部能力之间的一种标准连接方式。它解决「AI 怎么调用能力」，但它不自动解决「AI 为什么可以调用」，也不自动解决「AI 应该理解什么」，更不自动解决「调用以后谁负责」。

所以：

Semantic Layer

解决：「这是什么？」

MCP / Tool

解决：「怎么调用？」

Policy

解决：「能不能调用？」

Audit

解决：「发生了什么？」

四个问题完全不同。这四层组合起来，才是企业 Agent 真正的基础。最终可以得到一个很简单的模型：

Agent → Semantic / Tool / Memory → Business Objects / MCP → Action → Policy → Audit

如果缺 Semantic，AI 不知道企业里的东西是什么。

如果缺 Tool，AI 知道，但做不了。

如果缺 Policy，AI 能做，但不一定该做。

如果缺 Audit，出了问题不知道发生了什么。

这就是企业 AI 和普通聊天机器人的区别。

## 国产化并不意味着「所有东西都自己造」

这是另外一个很容易走偏的地方。有些企业一谈自主可控，就开始：自研 Agent、自研向量数据库、自研工作流、自研语义引擎、自研模型、自研 MCP。最后一年过去了，平台非常漂亮，业务没有上线。

「真正的自主可控，不是所有东西都自己写，而是：核心抽象、核心数据、核心业务规则和关键治理能力掌握在自己手里。」

其他能力尽可能模块化。比如模型层可以用 Model Gateway，这样今天使用 DeepSeek，明天切换其他国产模型，不至于整个业务系统重做。

模型层也应该「可替换」

这一点在今天尤其重要。模型迭代太快，如果企业把所有业务 Prompt、Agent、Tool、Workflow 都直接绑定某一个模型 API，未来升级模型的时候成本会非常高。比较合理的架构应该是：

AI Application → Agent Runtime → Model Gateway → Model A / Model B / Model C

模型负责推理，企业自己的系统负责业务，语义层负责理解企业世界，治理层负责控制边界。这是一个很重要的分工。

## 所以，真正的国产化 AI 架构应该长什么样？

如果把前面所有内容放在一起，我更推荐这样理解：

用户 → Agent → Semantic Layer / Tool / MCP / Memory → Action → Governance（Data / API / Audit）→ 企业业务系统

这套架构最重要的地方，不是组件名称，而是：每一层都有清晰边界。

但是千万不要第一天就把这张图全部造出来

这是全文最想提醒企业团队的一件事情。如果你现在是一个企业 AI 负责人，周一早上老板问「我们要不要搞企业级 AI 大平台」，我的建议不是马上回答「要」。先问：「准备解决哪个业务问题？」如果对方回答「我们还没想好」，那就不要建平台。

真正正确的顺序应该反过来

错误顺序

先建平台 → 再找数据 → 再找场景 → 最后找用户

正确顺序

真实业务问题 → 真实用户 → 真实数据 → 真实流程 → AI 应用 → 发现瓶颈 → 抽象语义 → 抽象公共能力 → 治理 → 平台化

为什么？因为：第一个真实项目会告诉你，企业到底需要什么。没有第一个项目之前，你设计出来的语义模型，大概率都是猜的。

所以我非常建议企业做「反向平台化」

什么叫反向平台化？不是「我们先建设平台，然后让业务接入」，而是：「先做业务，业务跑通以后，把重复出现的东西抽出来做平台。」

例如第一个项目需要客户、订单，第二个项目又需要客户、合同，第三个项目又需要客户、服务。这时候你才发现「客户」是一个企业级公共对象，于是开始抽象。这时候做出来的模型，是真实业务验证过的。

## 给企业一个非常实用的判断表

可以简单记住下面这个规则：

企业情况

推荐路线

文档问答为主

RAG

报告生成、内容处理

RAG + Workflow

AI 需要调用业务 API

Agent + Tool

AI 开始跨系统理解关系

Semantic Layer

AI 开始修改业务系统

Action + Governance

多业务域、多团队共用

Enterprise Semantic Platform

集团级 Agent 大规模运行

Semantic + Action + Governance + Platform

这不是一个绝对的技术标准，而是一个：防止过度建设的判断框架。

路径 A → B，不应该靠时间决定，而应该靠「撞墙」

这是一个很重要的理念。不要规定「AI 项目做半年以后就建设 Ontology」，没有这种规律。真正的升级信号是，从 A 到 B 时开始出现：

· 跨系统关系查询

· 业务对象不统一

· 数据语义冲突

· AI 需要复杂推理

· AI 需要执行动作

这时候增加语义层。路径 B → C 也一样。什么时候进入平台化？不是因为「我们已经用了 UModel 三个月」，而是出现：多个业务团队开始重复建模、多个 Agent 开始共享对象、Action 越来越多、权限越来越复杂、语义模型开始跨部门复用、需要统一治理、需要统一审计、需要统一运行监控。这时候才开始考虑平台化。

## 最危险的三个坑

最后再讲三个我认为企业最容易踩的坑。

第一个坑：平台先行

这是最典型的。项目一开始就说「我们先做统一 AI 平台」，于是开始架 Kubernetes、建模型网关、建向量数据库、建知识库、建 Agent Runtime、建 MCP Gateway、建权限系统。半年之后，平台全部有了，业务还是不知道做什么。平台没有业务反馈，很容易变成一个技术展览馆。

第二个坑：让 AI 团队独立建模

AI 团队可能非常懂 LLM、Prompt、Agent、MCP、RAG，但不一定理解「客户到底是什么」。语义模型如果错了，后面的 Agent 再聪明也只是：

「在错误的世界里进行正确推理。」

这其实比完全没有语义模型更危险，因为错误的 Context 往往比没有 Context 更难发现。

第三个坑：治理债

很多 POC 都是：权限以后再做、审计以后再做、数据血缘以后再做、Action 审批以后再做。问题是：AI 一旦开始真正调用业务系统，这些「以后」很快就会变成事故。所以路径 B 和 C 至少应该从第一天明确：谁可以看？谁可以操作？什么需要确认？什么必须审批？怎么记录？怎么追溯？哪怕第一版很简单，也必须有。

还有一个经常被忽略的问题：国产化环境会放大工程成本

在普通互联网环境里，Docker + Cloud API + SaaS 很多事情很快。但大型国内企业经常是：国产 CPU、国产 OS、国产数据库、私有云、隔离网络、数据不出域、等保、审计、信创适配、内外网隔离。所以判断一个开源项目能不能用，不能只问「GitHub 上有没有」，真正应该问：「能不能在我的生产环境里稳定运行？」

至少要验证四件事：

1. 功能　能不能解决业务问题？

2. 集成　能不能接现有系统？

3. 治理　能不能做权限、审计、数据隔离？

4. 运维　出问题以后谁维护？

最后一个问题非常现实。很多开源项目 Demo 能跑，不代表企业生产能跑五年。

## 因此，工具选型永远应该晚于场景判断

现在再回头看 Dify、UModel、DataHub、dbt、Ranger、Graph Database、MCP，它们没有谁可以直接被定义成「企业 AI 的标准答案」。它们解决的是不同问题：

DataHub　数据资产与元数据。

dbt Semantic Layer　指标和分析语义。

UModel　企业对象、关系、拓扑与语义运行时。

Graph Database　图数据存储和关系计算。

Dify / Agent Runtime　AI 应用编排与执行。

MCP　Agent 连接外部能力。

Ranger / IAM　数据与访问治理。

它们不是一个维度的产品。真正的架构师，不是从中选一个，而是：根据问题决定需要哪几个。

## 企业 AI 真正的成熟路径

如果把这件事情拉长来看，我认为企业 AI 最终会经历这样一个过程：

阶段 1

模型调用　Prompt → LLM。AI 会说话。

阶段 2

知识增强　LLM + RAG。AI 开始懂企业资料。

阶段 3

工具调用　LLM + RAG + Tool。AI 开始会做事情。

阶段 4

Agent　LLM + Tool + Memory + Workflow。AI 开始自己规划任务。

阶段 5

语义 Agent　Agent + Business Object + Relation + Action。AI 开始理解企业业务世界。

阶段 6

企业 AI Runtime　Semantic + Operational + Governance + Agent + Audit。

这时候，AI 才真正开始从一个应用变成企业运行体系的一部分。

## 那么，周一到底应该做什么？

如果你现在就是一个企业 AI 团队负责人，我建议不要把这篇文章读完，然后第二天组织一个「企业 Ontology 建设启动会」。恰恰相反。周一只做五件事情：

MONDAY选一个真实场景

不要讨论平台。只回答：谁在使用？现在怎么做？最痛苦的地方是什么？数据在哪里？AI 完成之后，业务结果是什么？

TUESDAY画业务对象

不要画一百个。只画 3～5 个核心对象，例如：客户、订单、供应商、产品、合同。

WEDNESDAY找 Action

问一句：AI 最后到底要做什么？不是「AI 最后回答什么」，而是：查订单、创建工单、修改状态、通知负责人、发起审批。

THURSDAY补治理

至少回答：谁能看？谁能操作？哪些操作需要确认？哪些操作需要审批？怎么审计？

FRIDAY让真实用户使用

不要继续优化 Demo。直接交给真实业务人员。然后记录：AI 不知道什么？AI 理解错什么？AI 查不到什么？AI 不敢做什么？AI 做错什么？用户不愿意用什么？

「这些东西，就是下一周最有价值的需求。」

## 每做完一个项目，还要多做一件事情

很多企业项目上线以后：代码进 Git、文档进网盘，然后结束。这是非常可惜的。因为一次 AI 项目，其实会沉淀大量企业知识。我建议每个项目结束后至少留下五样东西：

Objects

业务对象

Relations

业务关系

Actions

业务动作

Policies

治理规则

Evidence

执行证据 / Audit

比如第一次做供应商风险 Agent，你沉淀了 Supplier、Order、Product、Risk。第二次做采购 Agent，就可以直接复用。第三次做供应链 Agent，又可以继续复用。

「一个 AI 项目不再只是一个项目，而成为下一个 AI 项目的基础设施。」

这才是企业 AI 真正产生复利的地方。

## 这也是我为什么一直强调「不要急着建平台」

因为真正的平台，不是一次性设计出来的。它应该从业务中长出来。

第一个项目告诉你哪些对象重要。

第二个项目告诉你哪些关系可以复用。

第三个项目告诉你哪些 Action 是公共能力。

第四个项目告诉你哪些权限必须统一。

第五个项目告诉你哪些语义应该成为企业标准。

到了这里，平台才真正有价值。

## 最后重新回答那个问题：国产化 AI 能不能做出 Palantir 类似的能力？

答案是：从能力组件角度，完全可以组合出相当大一部分。但这并不意味着「把几个开源项目装起来，就得到一个 Palantir」。

真正难的是：语义 + 数据 + 逻辑 + Action + 权限 + 审计 + Agent + 长期治理，能不能长期保持一致。这才是工程难点。

所以，与其问「我们能不能做一个国产 Palantir」，不如问：

「我们今天到底缺哪一层？」

如果只是知识问题，先做 RAG。

如果开始跨系统理解，增加语义层。

如果开始执行，增加 Action 和治理。

如果多个业务域开始共享，开始平台化。

这才是一条现实的路线。

## 不要建设一个「国产 Palantir」，建设你真正需要的那一层

我越来越觉得，企业 AI 落地最怕的不是技术不够先进，而是：

「技术远远超过业务真正需要的复杂度。」

一个几十人的企业，可能只需要 RAG + Workflow。一个大型制造企业，可能需要 Object + Relation + Agent + Action。一个大型集团，最终可能需要 Semantic Runtime + Agent Runtime + Action System + Governance + Audit + Enterprise Platform。它们没有谁「更高级」，只是解决的问题不同。

所以国产化 AI 真正值得走的路线，不是把 Palantir 从头再造一遍，而是：把企业真正需要的能力，一层一层长出来。从知识开始，走向语义，走向行动，最后走向治理。最终形成这样一条路径：

知识 → 语义 → 推理 → 行动 → 治理 → 企业 AI Runtime

这可能才是国内企业在未来几年真正可行的 AI 落地路线。

别急着建平台。

先找到那个值得 AI 真正解决的问题。然后让第一个真实项目告诉你：下一层，到底该建什么。
