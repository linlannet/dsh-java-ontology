企业 AI 最大的障碍不是回答得对不对，而是能不能安全地做事——这层能力，就叫 Ontology。

做过企业 AI 项目的人大概都经历过这样的节奏：第一周说效果不错，第二周业务觉得有意思，第三周开始做 Demo，一个月后小范围上线，三个月后发现使用率不高，六个月后开始怀疑是不是模型能力不够——于是换一个更大的模型再试一轮。

GPT 换成 Claude，Claude 换成 Gemini，国内模型也测一遍。模型越来越强，Demo 越做越漂亮，但真正接入企业核心流程之后，问题往往还是同一批：数据接不上、业务语义不统一、系统之间互相依赖、权限没法控制、AI 不清楚哪些事能做、能做的事又不知道该怎么做。哪怕最后给出一个看起来很合理的答案，也很难真正改变业务的运转方式。

这暴露出一个容易被忽略的事实：企业 AI 最大的障碍，很多时候不是“回答得对不对”，而是能不能在真实的企业环境里安全地做事。这也是我重新研究 Palantir 之后，觉得它最值得琢磨的地方。

多数人第一次接触 Palantir，会先看 Gotham、Foundry、AIP 这几个产品，然后把它理解成一家数据平台公司，或者政府软件公司，或者“把大模型接进企业”的 AI 公司。这些理解都不算错，但都没有碰到核心——Palantir 真正的价值，在于它在数据和 AI 之间，搭建了一层“企业世界”的表示。这层东西就是 Ontology（本体）。

## 企业 AI 缺的不是模型，是“企业世界”

设想一家制造企业：10 个工厂、300 条产线、几万台设备、几千家供应商、数百万条订单，背后挂着 ERP、MES、CRM、WMS、IoT，还有一堆 Excel 和邮件。从数据库的角度看，这就是一堆表、字段、记录和日志。但业务人员脑子里想的完全是另一套东西：某个客户下了一个订单，订单需要某种产品，产品由某个工厂生产，工厂的一条产线出了异常，这条产线依赖某种关键物料，物料来自某个供应商，而这个供应商最近交付能力在下降——照这个节奏，三天后可能就要缺料。

这两种描述说的是同一家企业，却是两个世界：数据库看到的是数据，业务看到的是对象、关系、状态、规则和行动。企业 AI 需要的，恰恰是后面这个世界。

## 传统架构为什么容易停在“答案”这一步

过去做企业 AI，最顺手的架构是“企业数据 → RAG/API/Tool → LLM → 答案”。这套路子很适合解决知识问答、文档检索、制度查询、客服对话这类问题，因为它们的终点就是给出一个答案。

企业数据 → RAG / API / Tool → LLM → 答案

企业真正复杂的问题，终点往往不是答案，而是行动。

比如“为什么华东工厂最近交付率下降”，AI 要先理清是哪个工厂、哪条产线、哪些订单、哪些供应商出了异常，然后还要回答“应该怎么办”——调整生产计划、更换供应商、修改订单优先级、发起采购和审批、通知相关人员。这已经不是聊天机器人能解决的问题，而是一个完整的决策到行动的链条。

Palantir 把 Ontology 放在了这个位置：它不是单纯把数据整理得更好看，而是把企业的数据、逻辑、动作和安全策略组织进一个统一的表示里，官方甚至直接称之为企业的 operational layer。这也是为什么我越来越倾向于用“AI 到底有没有进入企业世界”来判断一个项目的成色，而不是单纯问模型有多聪明。

## Ontology 到底在描述什么

Ontology 这个词在知识工程领域早就存在，一般用来描述一个领域里的实体、属性、关系和概念。但 Palantir 的版本有个关键变化：它不只描述企业“是什么”，还要描述企业能做什么。理解这一点，基本就抓住了 Palantir Ontology 的核心。

对象（Object）是企业世界的名词。 制造业的核心对象可能是工厂、产线、设备、订单、产品、物料、供应商；金融业可能是客户、账户、交易、风险事件。Palantir 官方对 Object Type 的定义，就是用来表示组织中的实体或事件，Property 描述它的特征。这一步的关键不是把数据列出来，而是把数据库里的一行记录，重新理解成一个业务对象——比如把 customer_id = 100238 还原成一个有客户等级、信用等级、历史订单、负责人和风险状态的客户。

链接（Link）把对象连成一张关系网。 客户下单，订单包含产品，产品由工厂生产，工厂使用物料，物料来自供应商——这条链一旦建立，企业的数据就从表变成了世界。数据仓库关心的是“哪张表和哪张表怎么 Join”，业务世界关心的是“这个订单到底属于谁、影响了什么、又和哪些事情有关”。可以简单理解为：数据库记录数据，Ontology 组织企业世界。Palantir 官方文档也把 Object、Property、Link 作为 Ontology 的基础语义元素，强调它们把数据资产映射到真实世界中的工厂、设备、产品、订单等对象。

数据库记录数据，Ontology 组织企业世界。

## 让 Ontology 真正产生质变的是 Action

如果只做到对象和关系，本质上还是一张不错的知识图谱。真正让这套体系值得研究的，是 Action。

企业不是靠名词运转的，是靠动词运转的。“订单”是名词，“创建订单、修改订单、审批订单、冻结订单”是动词；“库存”是名词，“调整库存、转移库存、锁定库存”是动词。当企业世界从“对象 + 关系”变成对象 + 关系 + 动作，AI 才第一次真正有了“手”。Palantir 把 Action 描述为企业的“verbs”，也就是能够改变 Ontology 中数据、或协调外部系统发生变化的动作。

## 真正的企业 Agent 不该直接碰数据库

很多 Agent 项目的第一版架构是 LLM 调 Tool、Tool 调 API、API 碰数据库，看着很灵活。但企业一旦有几百个 API，光是让 Agent 自己判断该调哪个就已经很吃力，更别说谁允许调用、在什么条件下可以调用、失败了怎么办、有没有审计记录这些问题。如果这些全塞进 Prompt 和 Tool Description，系统很快就会失控。

Ontology 的思路，是把这些能力统一收进一层企业语义和执行层，让 AI 不再直接面对底层数据库，而是面对一个结构化的企业世界——上面是 Agent，中间是 Ontology（数据、逻辑、动作三条线并行），再往下依次是权限校验和企业系统本身。

Agent（理解意图 · 编排）

↓

Ontology（数据 · 逻辑 · 动作）

↓

权限校验（Security）

↓

企业系统（ERP / MES …）

## AIP 不是“Palantir 的大模型产品”

很多人第一次看到 AIP，会把它当成 Palantir 自己的大模型。这个理解太浅了。Palantir 对 AIP 的定位，是把 AI 与企业的数据和运营连接起来，并在 Ontology 和开发工具链之上构建 AI 工作流、Agent 和应用。换句话说，AIP 从不孤立存在，它建立在 Ontology 之上，Ontology 又建立在 Foundry 的数据基础之上。

一句话概括三层关系：

「Foundry 管数据，Ontology 管企业世界，AIP 让 AI 进入这个世界。」

## Ontology 不是“语义层”的另一种说法

有人看到 Object、Link、Property 会觉得这不就是语义层（Semantic Layer）吗？如果只看这两个元素，确实很像。但 Palantir 的 Ontology 继续往下扩展到了逻辑、动作和安全，官方架构文档明确把数据、逻辑、动作、安全这四者称为 Ontology 的核心整合，并特别强调它不只是一个“薄语义层”。语义层解决的是“这个东西是什么意思”，企业还需要解决“应该怎么判断”“应该怎么做”“谁可以做”——这已经不是同一个层级的问题了。

## 企业真正要的是“数据到行动”的闭环

传统 BI 是数据到大屏，人看完自己决定怎么办；RAG 是检索加生成，给出一个答案；Agent 往前一步，是目标到推理到工具到行动。企业 Ontology + Agent 的路线则试图打通整条链路：从数据到对象、关系、业务逻辑、决策、行动，最终落到结果。

数据 → 决策 → 行动 → 结果

「企业要的从来不是“生成一段文字”，而是订单有没有处理、库存有没有调整、设备有没有修好、风险有没有降低。」

企业 AI 的价值单位，不该只是 Token 或者回答准确率，而应该越来越接近完成了什么业务动作。

## 一个例子：AI 处理库存预警

假设某种关键物料库存正在快速下降。传统做法是 AI 查库存、发现低于阈值、生成一份报告，建议采购部门补货——看起来没毛病，但离真实的企业流程还差一大截。

！踩坑提示 🕳

传统库存预警只告诉你“库存不足”，却不告诉你“会影响哪些业务”——离真实的企业流程还差一大截。

如果有 Ontology，系统本身就知道库存对应物料、物料用于产线、产线属于工厂、工厂支撑客户订单，同时物料又来自某个供应商。AI 发现库存下降时，不会只看一个数字，而是可以继续追问：未来七天需要多少？哪些生产订单依赖这个物料？哪些订单最重要？当前供应商还有多少交付能力？有没有替代供应商，切换要多久？不补货会影响哪些客户订单？这时候 AI 给出的不再是“库存不足”，而是库存不足会影响哪些业务——这两者的价值完全不在一个量级。

再往前一步，如果 AI 判断三天后会缺料，传统系统可能就是给采购经理发一封邮件。Ontology + Agent 的路线可以继续走完计算补货量、比较供应商价格和历史交付、生成采购建议、调用采购 Action、权限校验、提交审批、审批通过后创建采购订单并写回 ERP 的全过程——AI 这才真正进入了企业流程。这里的关键分工是：LLM 负责理解和推理，Ontology 提供企业语境，Logic 提供确定性规则，Action 提供执行能力，Security 划定边界，人负责关键决策。这是一套相当合理的人机协作架构。

## Action 为什么比 Tool 更值得关注

Tool 回答的问题是“AI 可以调用什么”，企业真正要问的是企业允许 AI 做什么——这两个问题并不等价。Tool 更像是一种能力，Action 则是被业务规则、权限和对象约束之后的能力。写一个 update_order（） 函数很简单，但企业真正需要的是“修改订单交付日期”这个动作，而且系统还得知道改的是哪个订单、原日期和新日期、修改原因、谁发起谁批准、是否超权限、是否影响客户承诺、要不要同步其他系统、事后怎么审计。企业 Action 本质上不是一个 API，而是一个带业务语义、规则、权限和审计的企业动词。这也是为什么我认为企业 Agent 的 Tool Calling，最终会逐渐走向更强的“业务 Action”抽象。

## AIP Logic：让模型和确定性逻辑混在一起

AIP Logic 不是单纯让 LLM 生成文本。按官方文档的说法，它可以把 LLM、Ontology 查询、函数、Action、条件和循环组合起来；Logic Function 既能读取 Ontology 对象，也能产生对象、字符串，甚至通过 Action 反过来修改 Ontology。这很符合企业的真实需求——订单金额等于单价乘数量，没必要让 LLM 猜；订单金额超过 100 万需要二级审批，也没必要让 LLM 自由判断；但“为什么这个客户最近突然减少订单”这种问题，确实需要 LLM 去分析。合理的架构从来不是把所有事情都交给大模型，而是让确定性问题走规则和代码，复杂认知问题交给 LLM，最终业务执行落到 Action——让模型只做它擅长的事，把不该交给它的事拿回来。

这也是企业 Agent 和 Chatbot 的根本分野。Chatbot 是问题到答案；企业 Agent 要走完理解企业对象、获取上下文、分析关系、执行逻辑、制定方案、调用 Action、权限校验、人工审批、执行、观察结果、继续调整这一整条链。两者的差别不在于会不会调用 Tool，而在于有没有真正进入一个结构化、可执行的世界。少了 Ontology、业务对象、规则、权限和 Action，很多所谓的 Enterprise Agent，本质上还是一个会调 API 的 Chatbot。

## 重新理解 Foundry / Ontology / AIP 三层架构

Foundry 解决企业数据从哪里来、怎么接入清洗、怎么计算治理、怎么追踪血缘；Ontology 解决企业有哪些对象、对象之间什么关系、业务规则是什么、谁可以做什么；AIP 解决 AI 怎么理解意图、读取上下文、调用逻辑、选择 Action、编排 Agent、评估和观察结果。三句话可以概括：Foundry 管数据从哪来，Ontology 管企业怎么运行，AIP 管 AI 怎么进入这个世界。这句话，我觉得比记住 Palantir 的几十个产品名更有用。

这也是整个行业正在经历的一条演进路径。企业 AI 最早的问题是“怎么把公司文档喂给大模型”，对应的是文档切片、Embedding、向量数据库、RAG，解决的是“AI 知道什么”；后来大家开始做知识图谱，解决“这些东西之间有什么关系”；但企业真正的问题还要再往前一步——对象、关系、状态、逻辑、动作、安全合在一起，解决的已经不是“企业知道什么”，而是企业世界是什么，AI 能对这个世界做什么。这就是 Ontology 的意义，我更愿意称它为 Enterprise World Model。当然这不是说所有企业都要照搬 Palantir 的做法，也不是说 RAG 会被取代——RAG、知识图谱、Workflow、Tool Calling、Agent、Ontology 解决的是不同层次的问题，关键是把它们放在正确的位置上。

## 企业如果今天想做 Ontology，该从哪里开始

不建议一上来就喊“我们也要建一个企业级 Ontology”，这句话太大了，真正应该从一个具体业务场景切入，而且顺序要反过来：先找到高价值业务流程、关键决策、关键对象、关键关系、关键规则、关键 Action，最后才选模型——而不是先定模型，再找场景。

拿供应链举例，不要先问 SAP 有多少张表，而要先问这个业务世界里最重要的东西是什么。答案大概率是供应商、物料、库存、采购订单、仓库、工厂、客户订单、运输，然后再理清它们之间的关系：供应商供应物料，物料存放在库存，库存位于仓库，仓库属于工厂，工厂生产产品，产品满足客户订单。做完这一步会发现很多数据问题突然变清楚了——以前讨论的是“A 表和 B 表怎么 Join”，现在讨论的是“供应商和物料到底是什么业务关系”。问题从技术语言回到了业务语言。

接下来要把业务规则从 Prompt 里搬出来。 “订单金额超过 100 万需要审批”这种规则写进 Prompt 当然可行，但 Prompt 终究不是企业规则系统。真正重要的规则应该变成 Rule、Function、Action、Permission，让模型专心理解复杂问题，系统负责执行确定规则，这能大幅降低 Agent 的不确定性。

然后是定义真正的 Action，这是整个项目最值得花时间的地方。 不能只有“查询订单”，还要有创建、修改、取消、审批、调整订单，并且把每个动作的权限边界、触发条件、所需参数、影响范围、是否需要审批、是否需要同步外部系统、失败如何处理都定义清楚。这些问题被回答完之后，AI 才真正获得了手。

最后才是让 Agent 进入这套已经搭好的企业世界。它不需要重新理解整个企业，因为企业的基本语义已经被系统表达出来了——这正是 Ontology 对 Agent 最大的意义：把企业的复杂性，从 Prompt 里搬到了系统里。

## 难的不是本体软件，是本体工程

Ontology 看上去很漂亮：对象、链接、动作、函数、角色、接口一应俱全。但真正做起来一点都不轻松，因为你必须先回答几个问题——

客户到底是什么

不同部门可能有完全不同的答案

订单什么时候算完成

销售、财务、仓储、生产的口径可能都不一样

供应商风险由什么决定

采购、质量、财务又各有一套标准

真正困难的从来不是有没有一个 Ontology 工具，而是企业能不能把自己的业务世界说清楚。

这也是 Palantir 的 FDE 模式值得研究的原因。FDE 不是简单派几个工程师过去写代码，而是深入业务现场，观察业务、理解流程、识别对象、梳理关系、理解规则、定义 Action，做成应用后持续迭代——这其实是本体工程、软件工程和业务工程混在一起的活儿。

## 写在最后

理解 Palantir 有一个很容易走偏的地方：只看 Gotham、Foundry、AIP，容易把它当成一家产品很多的企业软件公司；只看 AI，又容易把它当成一家做 Agent 的公司。但把这些拆开来看，会发现一个更有意思的结构——AI/Agent 在最上层，往下是 AIP 和各种应用，中间是承载对象、关系、逻辑、动作、安全的 Ontology，最底层是 Foundry 打通的 ERP、CRM、MES、IoT 数据。

Foundry 解决企业的数据从哪里来，Ontology 解决这些数据在企业世界里意味着什么、企业能对它做什么，AIP 解决 AI 如何进入这个世界参与决策和执行。如果只用一句话概括，我会说：

「Foundry 管数据，Ontology 管企业世界，AIP 让 AI 进入这个世界。」

这可能也是企业 AI 接下来几年最值得关注的事——

竞争正在从“谁的模型更聪明”，转向“谁能让 AI 真正理解并安全地操作一个真实的企业世界”。

因为企业最终需要的，从来不是一个更会聊天的 AI，而是一个知道企业发生了什么、理解为什么发生、知道下一步该做什么，并且能在权限和规则约束下把事情真正做完的 AI。
