本体不应该只是 Agent 启动时读一遍的说明书，而应该成为查询、判断、执行时持续使用的一层运行时服务。

这两年做企业 AI，Ontology（本体）越来越火。特别是 Palantir 的技术架构被越来越多人研究之后，不少企业也开始建设自己的本体平台。

但我发现一个挺有意思的现象。很多团队花了不少时间研究 Object、Property、Link、Action，设计了一套完整的业务对象模型，甚至做出了很漂亮的可视化界面。客户有哪些属性，订单和客户是什么关系，工单属于哪个部门，哪些对象可以关联，全部定义得清清楚楚。

然后呢？本体建好了，Agent 到底怎么用？

模型什么时候读取这些定义？怎么根据本体查询数据库？如何把查询结果还原成业务对象？如果模型想修改业务数据，谁来判断这个操作是否合法？操作成功之后，本体又怎么知道企业的业务状态发生了变化？

这些问题如果回答不清楚，本体很容易变成一张更高级、更漂亮的数据字典。数据字典当然有价值，但它解决不了企业 Agent 真正开始干活时遇到的问题。

我一直觉得，理解 Ontology 有一个很重要的视角：

「不要只看它在设计阶段定义了什么，更要看它在运行阶段参与了什么。」

本体不应该只是 Agent 启动时读一遍的说明书，而应该成为 Agent 查询数据、理解业务、判断规则和执行操作时持续使用的一层运行时服务。

当然，这是一种以 Ontology 为核心的企业 Agent 架构设计，并不是说所有本体系统都必须采用完全相同的实现方式。

今天不讲太多抽象概念。我们用一个非常普通的企业业务场景，把这件事从头到尾走一遍。

找出华东区逾期超过 30 天的客户，并为其创建跟进任务。

总共17 个步骤。走完这 17 步，基本就能理解：一个真正进入企业业务流程的 Ontology，到底应该做些什么。

## 先别急着调用模型，企业世界得先定义清楚

假设我们有一家企业，内部运行着三个业务系统。CRM 管客户资料和客户经理；计费系统管理账单、应收款和付款状态；任务系统负责创建跟进任务，并分配给相应的客户经理。

现在销售负责人提出一个需求：

帮我找出华东区逾期超过 30 天的客户，并给对应的客户经理创建跟进任务。

如果只是做一个 Demo，事情看起来很简单。让大模型理解需求，生成 SQL，查数据库，拿到客户和账单，再调用任务系统的 API 创建任务。几分钟就能演示出来。

但真放到生产环境里，问题马上就来了。

客户的“地区”到底取哪个字段？是工商注册地、销售归属地，还是客户当前服务区域？

逾期 30 天怎么算？账单到期日加 30 个自然日，还是 30 个工作日？

如果客户有三张账单，其中一张逾期 42 天，另外两张正常，算不算待跟进？

如果账单已经结清，只是数据同步有延迟，还要不要创建任务？

客户经理已经离职了怎么办？

还有一个更麻烦的问题：如果模型查到了一个客户 ID、一个账单 ID、一个客户经理 ID，它怎么确定这三个对象真的属于同一条业务关系？

这些问题不能指望模型每次临场发挥。企业需要有一个明确、稳定、可治理的业务定义。这就是 Ontology 首先要做的事情。

1．定义对象：企业里到底有什么

在这个场景中，至少需要四类对象：Customer（客户）、Bill（账单）、CustomerManager（客户经理）、FollowUpTask（跟进任务）。

每类对象有自己的属性。例如 Customer 有客户 ID、名称、地区、状态；Bill 有账单 ID、到期日期、未结清金额、结清状态；FollowUpTask 有任务 ID、负责人、创建时间、任务状态。

这些东西看起来和数据库 Schema 很像。但区别在于，Ontology 里的 Customer 不必等于 CRM 里的某一张客户表。一个业务对象可能来自多张表，也可能由多个系统共同提供数据。

比如客户的基本资料在 CRM，信用等级在风控系统，账单信息在计费系统，跟进记录在任务系统。从业务角度看，它们描述的可能都是同一个客户。

本体定义的是业务对象，不是数据库表的另一种写法。

2．定义关系：这些对象怎么联系起来

有了对象，还需要定义关系。在我们的案例中，至少有三条关系：

账单属于客户：Bill → Customer

客户由客户经理负责：Customer → CustomerManager

跟进任务关联客户、账单和负责人：FollowUpTask → Customer / Bill / CustomerManager

这些关系不是为了把图画得更好看，它们决定了后续操作能否成立。例如客户 C018 有一张账单 B036，负责人是 M007，那么系统需要知道：B036 属于 C018，M007 当前负责 C018，将来创建的跟进任务 T105 应该关联 C018、B036 和 M007。

注意，这里不是简单地把几个 ID 放在一起。业务关系本身就是需要验证的事实。

3．定义规则：什么叫“待跟进客户”

接下来是业务规则。我们可以定义一条规则 PendingFollowUp，规则内容是：

账单尚未结清，并且截至业务计算时间，逾期超过 30 天，则该账单命中待跟进条件。

如果企业的跟进策略是“客户只要存在一张符合条件的账单，就进入待跟进名单”，那么还需要定义从账单到客户的聚合规则。

这里有一个细节很重要。用户说的是“逾期超过 30 天”，模型不能自己决定到底是大于 30 还是大于等于 30，也不应该随意选择日期计算方式。这些都应该由业务规则明确。

💡 以后企业把跟进标准从 30 天调整到 45 天，也应该修改经过治理的规则定义，而不是到处修改 Prompt。

4．定义行动：AI 到底可以做什么

最后定义一个 Action CreateFollowUpTask，它表示创建跟进任务。输入参数可能包括：

CreateFollowUpTask

customerId

billId

assigneeId

reason

idempotencyKey

但定义一个 Action，不只是声明一个函数名，还需要明确：

谁有权调用？参数必须满足什么条件？

账单是否必须属于对应客户？负责人是否必须有权处理该客户？

当前账单状态是否允许创建任务？是否需要人工审批？

调用哪个业务接口？执行失败怎么办？如何避免重复创建？

这些约束共同构成 Action 的业务契约。到这里，我们才算把这个场景需要的最小业务世界定义出来：对象、属性、关系、规则、行动，以及对应的权限和系统映射。

还有一点必须强调。这些定义是在系统设计、配置和发布阶段建立的。运行时 Agent 只是按照权限获取和引用它们，不需要每次收到请求都重新生成一套本体。

否则今天模型认为逾期 30 天应该跟进，明天换个模型认为 35 天才需要跟进，企业的业务规则就失控了。

## 读的过程：模型不直接写 SQL，而是先理解业务对象

现在正式进入运行时。用户输入：“找出华东区逾期超过 30 天的客户，并为其创建跟进任务。”我们先只看查询部分，也就是图中的第①步到第⑨步。

第①步：用户提出的是业务目标，不是技术指令

用户不会关心客户在哪张表，账单在哪个数据库，客户经理通过什么外键关联，他只关心业务结果。这也是企业 Agent 和传统数据查询工具的一个区别：用户表达的是意图，系统需要把意图转化为能够执行、能够验证的业务请求。

但是，模型理解了这句话，并不代表它已经具备查询权限，更不代表它可以直接访问所有数据库。中间还需要一个受控的转换过程。

第②③步：编排层先向本体索取定义

Agent Harness 或编排层接到任务之后，首先要做的不是让模型猜数据库结构，而是向 Ontology Runtime 请求当前任务需要的业务定义。比如：

GetOntologyContext（

user = 当前用户，

intent = 查询逾期客户并创建跟进任务

）

本体服务根据用户身份、权限和任务范围，返回一份可用的定义片段，其中可能包括：Customer 对象及其允许访问的属性、Bill 对象及其关联关系、CustomerManager 对象、PendingFollowUp 规则，以及 CreateFollowUpTask Action 的定义和参数要求。

这里有两个特别重要的设计。第一，返回的是定义，不是实际数据。模型此时知道有哪些对象、有哪些属性、有哪些关系、可以引用哪些规则，但还没有拿到具体客户资料。第二，返回的定义需要经过权限裁剪。

如果当前用户无权访问客户的银行账户、身份证号或者某些敏感属性，那么这些属性不应该出现在提供给模型的定义片段里。

！仅仅隐藏定义还不够 🕳

真正查询数据时，仍然必须实施独立的字段级、行级和租户级权限控制。不能因为模型看不到某个字段的定义，就认为系统已经安全了。

第④⑤步：模型输出的是逻辑查询请求

拿到本体定义后，编排层才调用大模型。模型现在有了明确的业务上下文，它知道 Customer 是客户，region 是地区，PendingFollowUp 是已经定义好的业务规则。于是可以生成类似这样的结构化请求：

{

＂objectType＂： ＂Customer＂，

＂filter＂： {

＂and＂： [

{ ＂property＂： ＂region＂， ＂operator＂： ＂eq＂， ＂value＂： ＂华东＂ }，

{ ＂rule＂： ＂PendingFollowUp＂， ＂operator＂： ＂matches＂ }

]

}，

＂include＂： [＂overdueBills＂， ＂accountManager＂]

}

这段内容有一个非常关键的特点：它不是 SQL。它描述的是业务对象上的查询条件。模型没有写 SELECT * FROM customer JOIN bill，也没有自己写一段逾期计算公式。它只是在表达：我要找 Customer，地区是华东，并且命中 PendingFollowUp 规则，同时需要相关账单和客户经理。

至于 Customer 映射到哪张表，Bill 来自哪个系统，PendingFollowUp 如何计算，都由后续的受控服务处理。

为什么要这么设计？因为模型擅长把自然语言转换为结构化意图，但不应该成为企业数据库结构和业务规则的最终权威。如果让模型直接生成 SQL，至少会遇到三个问题：

1. 数据库结构会暴露到模型上下文中，系统耦合非常严重。

2. 业务规则容易散落在各种 Prompt 和 SQL 里。

3. 权限控制和查询合法性很难统一治理。

所以我更倾向于让模型面向稳定的业务接口工作，而不是直接面向底层数据库工作。

！并不是说 SQL 一定不能由 AI 生成 🕳

在分析型场景、受限沙箱或经过严格校验的查询系统中，Text-to-SQL 完全可以有价值。但对于需要跨系统、带权限、带业务规则、最终还要执行写操作的企业 Agent，直接把 SQL 当作主要业务接口，通常不是一个好的长期架构。

第⑥⑦步：本体服务把逻辑查询转换成真实查询

模型生成逻辑请求之后，本体查询服务开始工作。它首先要验证请求：Customer 是否是当前用户可访问的对象类型？region 是否是允许查询的属性？PendingFollowUp 是否是已经注册的规则？include 中引用的关系是否合法？

然后根据对象映射，生成实际的数据访问计划。例如 Customer 的地区来自 CRM，Bill 的到期日期和结清状态来自计费系统，客户经理关系来自 CRM 的负责人记录。

如果这些数据都在一个数据库里，查询服务可能生成 SQL；如果分布在不同系统里，则可能先调用 CRM API，再调用计费系统 API，最后在受控服务中完成关联；也可能使用预先维护的索引、物化视图或者统一查询引擎。具体采用什么实现，取决于企业的数据架构。

💡 Ontology 并不要求所有业务数据都搬进一个本体数据库。它可以通过映射和服务适配，把分散的数据组织成统一的业务对象视图。

同时，查询时还需要注入真正的数据访问权限。比如当前用户只负责华东区域的一部分客户，即使逻辑请求写的是“华东区”，最终也只能查询其被授权的数据范围。模型不能通过改变查询条件绕过这些限制。

第⑧步：把数据库记录还原成业务对象

业务系统返回数据之后，事情还没结束。假设查询结果里有这样几条记录：

CRM

cust_id = C018

region = 华东

owner_id = M007

计费系统

bill_no = B036

cust_id = C018

overdue_days = 42

settled = false

对于数据库来说，这些就是字段和值。但对于 Agent 来说，我们希望它看到的是：客户 C018 属于华东区，账单 B036 属于该客户且尚未结清、逾期 42 天，客户经理 M007 负责该客户。这就涉及对象映射和关系解析。

在这个过程中，本体服务需要解决一个很现实的问题：不同系统中的 ID，不一定天然代表同一个业务身份。CRM 可能使用 cust_id，计费系统可能使用 account_no，任务系统可能使用 customer_code。如果三个系统没有统一的身份映射机制，那么简单地根据字符串相等去关联数据，很容易出错。

因此，成熟的本体运行时通常还需要对象身份解析、稳定 ID、关系映射和来源追踪等能力。本体不是把数据库查询结果换一个 JSON 格式就完事了，它要把数据组织成有明确业务身份、关系和来源的对象。

第⑨步：按照业务规则推导结论，并保留依据

现在我们有了业务对象：客户 C018，账单 B036，账单逾期 42 天、尚未结清。根据 PendingFollowUp 规则，系统推导出 C018 符合待跟进条件。

这里我认为有一个非常重要的工程设计：事实和结论必须分开。

事实：B036 属于 C018，B036 当前未结清，B036 截至查询时间已经逾期 42 天。

结论：根据当前生效的 PendingFollowUp 规则，C018 应当进入待跟进名单。

这两者不能混为一谈，因为事实可能变化，规则也可能变化。今天逾期 42 天，明天客户付款了，结论就可能失效；今天规则要求超过 30 天，未来企业调整成 45 天，同样的账单也可能不再命中。

因此，一次可靠的规则推导，最好能够记录：使用了哪些事实、事实来自哪个系统、采用了哪个规则版本、计算发生在什么时间、最终得出了什么结论。这些信息以后可以用于解释、审计和重新计算。

！需要说清楚的边界 🕳

普通语义层、规则引擎甚至数据仓库同样能够提供部分计算和解释能力。Ontology 的价值不是独占“规则计算”这件事，而是把对象身份、业务关系、规则、权限和后续可执行动作放到统一的业务语义契约中。

到这里，我们完成了读链路：模型提出查询意图，本体提供定义并校验请求，查询服务访问真实业务系统，返回的数据被组织成对象和关系，规则服务给出结论及其依据。

但整个任务还没有完成，因为用户要求的不只是找出客户，还要创建跟进任务。接下来才是真正考验企业 Agent 的地方。

## 写的过程：三个 ID 都合法，不代表这次操作合法

很多企业 AI 项目，读数据时效果很好，一旦开始写数据，问题就变复杂了。原因并不神秘：查询错了，通常是答案错；写入错了，可能直接改变企业的真实业务状态。

而且很多错误不是简单地撤销一条记录就能解决：

错误的任务可能触发通知。

错误的客户归属可能影响考核。

错误的审批可能导致资金、库存或者合同状态发生变化。

Agent 从查询走向行动，中间必须有一条明确的控制边界。

第⑩步：模型提出 Action Request

模型根据查询结果，决定为客户 C018 创建跟进任务。它提出：

{

＂action＂： ＂CreateFollowUpTask＂，

＂parameters＂： {

＂customerId＂： ＂C018＂，

＂billId＂： ＂B036＂，

＂assigneeId＂： ＂M007＂，

＂reason＂： ＂PendingFollowUp＂

}

注意，这仍然只是一个请求，模型并没有真正创建任务。它引用的 C018、B036、M007 应当是此前已经查询、解析和授权的业务对象，而不是模型随手编出来的字符串。

这一步需要严格区分三个概念：

模型想做什么，是 Intent。

模型提出什么操作，是 Action Request。

业务系统最终做了什么，是 Action Execution。

这三件事不是一回事。尤其是最后一件事，不能由模型自己宣布成功。

第⑪步：真正动手之前，必须重新核验

这一部分是整个流程里我最想强调的地方。假设模型提出的三个 ID：C018 是一个真实存在的客户，B036 是一张真实存在的账单，M007 是一个真实存在的客户经理。看起来都没问题。

但如果 B036 实际上属于客户 C026，而不是 C018 呢？如果 M007 已经不再负责 C018 呢？这时候三个 ID 全部合法，但整个操作是错的。

「对象合法，不代表对象之间的关系合法。」

这也是为什么企业 Agent 不能只做参数类型校验。customerId 是字符串，billId 是字符串，assigneeId 也是字符串，就算全部通过 JSON Schema 校验，也完全不能说明这次业务操作成立。真正需要验证的是业务关系：

B036 是否属于 C018？

M007 是否仍然负责 C018？

当前用户是否有权给 M007 分配这项任务？

但这还不够，因为还有第二类问题：业务状态可能已经变了。我们在第⑨步查到 B036 逾期 42 天、尚未结清，模型分析用了几秒，用户审批又用了两分钟。就在这段时间里，客户可能已经完成付款。如果系统拿着两分钟前的查询结果直接创建任务，就可能产生一个已经没有必要的催收任务。

在软件工程里，这类问题属于典型的 TOCTOU（Time of Check to Time of Use），也就是检查时和真正使用时，系统状态已经不一致。解决办法不是简单地再问模型一次，而是让执行链路具备真实的状态校验能力：在写入前重新读取账单状态，检查版本号，使用条件写入，或者通过业务系统的事务机制保证关键前置条件成立。

！本体不能替代事务保障 🕳

如果在检查和执行之间仍然存在并发窗口，最终的业务系统接口也必须再次保护关键约束。本体可以定义和组织校验，但不能替代业务系统本身的事务与一致性保障。

第⑫步：高风险写操作，先让人确认

在我们的例子中，可以把创建跟进任务设置为需要人工确认的操作。系统给用户展示：

准备创建跟进任务

客户：C018

账单：B036

逾期天数：42 天

当前状态：未结清

负责人：M007

命中规则：PendingFollowUp

操作：创建跟进任务

[确认执行]　[取消]

这里最重要的不是界面有两个按钮，而是用户看到的是业务对象、业务依据和操作后果。不是 SQL，也不是模型内部生成的一大段 JSON。这才是合理的人机协作方式。

人应该审批业务决定，而不是替 AI 检查数据库语法。

当然，不是所有 Action 都需要人工审批。例如给自己创建一个低风险提醒任务，完全可以自动执行。但涉及资金、客户权益、合同、库存、生产设备等操作时，就需要根据风险等级设计审批和执行策略。本体中的权限与 Action 契约，可以成为这些策略的重要依据。

第⑬步：按 Action 契约调用业务系统

用户确认之后，系统才真正进入执行阶段。这里要注意一个容易混淆的地方：Ontology 的 Action 不等于模型可以直接操作数据库。更合理的设计是：

1. 模型提出 Action Request。

2. Ontology Action Service 验证对象、关系、权限和前置条件。

3. 业务执行服务按照契约调用任务系统的正式 API。

4. 任务系统负责实际创建任务。

例如：

POST /follow-up-tasks

customerId： C018

billId： B036

assigneeId： M007

reason： PendingFollowUp

实际工程中还需要附带调用者身份、请求追踪 ID、幂等键，以及必要的规则和审批记录。

这里我特别想说一下幂等性。Agent 的执行过程不是永远一次成功：网络可能超时，API 可能返回错误，编排层可能重试。假设第一次创建任务已经成功，只是回执丢了，如果 Agent 再调用一次，就可能为同一张账单创建两个跟进任务。

所以 Action 的设计不能只考虑正常路径，还要考虑重复调用、超时、失败恢复和状态查询。这些都是企业软件工程里很普通的问题。只不过到了 Agent 时代，我们不能因为前面多了一个大模型，就把这些工程约束忘掉。

第⑭步：业务系统执行成功，返回真实回执

假设任务系统成功创建了任务，返回：

Task ID： T105

Status： Created

Customer： C018

Bill： B036

Assignee： M007

这时候，我们才有证据说明任务已经创建。而且最好能够进一步查询确认任务状态，尤其是在接口回执存在异步处理的情况下。这里有一句话值得反复强调：

「模型说成功，不等于业务执行成功。」

模型生成了正确的参数，不代表 API 调用成功。

API 返回已受理，不一定代表最终落库成功。

任务创建成功，也不代表后续跟进已经完成。

每一层都有自己的成功标准，不能混在一起。

## 任务创建成功之后，本体世界发生了什么变化？

很多 Agent Demo 到这里就结束了。界面上显示“已成功为客户 C018 创建跟进任务 T105”，用户看起来很满意。但从企业系统的角度，事情还没有完全结束，因为真实业务世界已经发生了变化，而 Agent 之后还需要继续使用这个世界。

第⑮步：业务变更回流，本体视图更新

任务系统创建 T105 后，需要把这个变化同步给本体运行时。具体实现可以是事件通知、CDC、回调、缓存失效或者按需重新查询，不同架构会有不同做法。

同步之后，本体视图里可以看到一个新的 FollowUpTask 对象，它与三个已有对象建立关系：T105 关联客户 C018，T105 关联账单 B036，T105 分配给客户经理 M007。这意味着，下一次 Agent 查询 C018 时，不仅能够看到客户和账单，还能够看到已经存在的跟进任务。这样可以避免重复创建，也可以支持后续的任务状态追踪。

！不要把动作结果当成业务事实 🕳

创建跟进任务，不会让账单自动变成已结清。账单是否逾期仍由计费系统决定，任务是否创建由任务系统决定，客户经理是否完成跟进也由真实业务记录决定。Ontology 应该反映业务世界，而不是为了让 Agent 的执行结果看起来漂亮，随意改写业务事实。

还有一个工程问题是同步延迟。任务系统已经创建 T105，但本体缓存可能还没有刷新，这时候如果 Agent 立即重新查询，可能暂时看不到新任务。所以生产系统需要明确数据一致性策略：

哪些操作要求强一致性？

哪些视图允许最终一致性？

同步延迟期间如何展示状态？

这些都不是大模型能够凭空解决的。

第⑯步：编排层检查任务目标到底完成了多少

现在回到最初的用户需求：“找出华东区逾期超过 30 天的客户，并为其创建跟进任务。”注意，这是一个包含两个阶段的目标：第一阶段是找出客户，第二阶段是创建任务。

假设查询到了 10 个符合条件的客户，其中 7 个任务创建成功，2 个客户已经存在有效跟进任务、不需要重复创建，1 个客户在执行前完成了付款、因此不再满足创建条件。那么最终结果应该怎么描述？显然不能简单说“成功创建 10 个任务”，也不应该说“任务执行失败”。更合理的结果是：

查询命中 10 个客户。

新建 7 个任务。

2 个客户已有任务，未重复创建。

1 个客户在执行前状态发生变化，未创建任务。

并且附上相应依据。如果有部分任务因为网络错误未完成，编排层还需要判断是否重试；如果需要重新查询，就回到前面的定义获取、查询和校验流程，开启下一轮。

这才是 Agent Loop 真正有价值的地方。

很多人把 Agent Loop 理解成：模型想一下，调用工具，再想一下，再调用工具。这种理解太浅了。真正的企业 Agent Loop，核心是不断对照任务目标和真实业务状态，直到任务完成、需要人工介入，或者明确无法继续。

模型负责推理和提出下一步。

Harness 负责调度、状态管理、重试和终止条件。

Ontology 提供业务对象、规则和可操作边界。

业务系统提供真实执行结果。

它们共同构成一个可以核验的执行闭环。

第⑰步：最终交付的是业务结果，不是一句漂亮的总结

最后，用户应该拿到什么？我认为至少包括三类信息：

1. 清单：哪些客户符合条件，分别关联哪些逾期账单。

2. 依据：为什么这些客户被选中，使用了什么规则，关键事实是什么。

3. 执行结果：哪些任务创建成功，任务编号是什么，哪些已经存在，哪些失败或者需要人工处理。

例如：

客户：C018

账单：B036

逾期：42 天

规则：PendingFollowUp

执行结果：

已创建跟进任务 T105

负责人：M007

状态：待跟进

！待跟进，不是已跟进 🕳

创建任务只是完成了“安排跟进”这个动作。客户经理是否联系客户、客户是否承诺付款、账单是否最终结清，那是后续的业务过程。一个可靠的 Agent，应该准确表达自己完成到了哪一步，而不是把“发起动作”包装成“解决问题”。

## 看完 17 步，再回头看 Ontology 在技术架构中的位置

走到这里，我们可以把整个系统重新整理一下。我更倾向于把它分成五层：

1. LLM / Agent：负责理解自然语言、识别任务意图、生成逻辑查询请求、提出 Action Request。模型负责推理，但不应该成为业务事实和权限的最终权威。

2. Agent Harness / Orchestrator：负责组织上下文、调用模型、管理任务状态、调度工具、处理审批、重试和异常恢复。它关心的是整个任务怎么往前推进。

3. Ontology Runtime：这是本文重点讨论的一层，提供面向业务世界的定义、查询、身份、规则、行动与治理能力。

4. Domain Services / Integration：负责领域服务、复杂业务逻辑、事务处理、接口适配和事件发布。

5. Data / Business Systems：真正保存和管理业务事实的系统，如 CRM、ERP、计费系统、任务系统、数据库等。

其中第三层 Ontology Runtime 至少需要提供几类能力：

Definition Service：让 Agent 获取当前允许使用的对象、属性、关系、规则和 Action 定义。

Object Query：根据业务对象和关系执行受控查询。

Identity / Link：解析对象身份，建立和验证对象之间的关系。

Rule / Function：按照确定的业务规则计算状态、推导结论。

Action Service：验证业务操作请求，并通过受控接口执行。

Security / Governance：管理权限、规则版本、访问策略和审计信息。

这些能力在具体产品中不一定由同一个服务实现，也不一定全部由 Ontology 平台自己实现。重要的是，它们在架构上形成一套一致的业务契约。

这样分层之后，有几个容易混淆的问题就清楚了。

1．Ontology 和 Agent Harness 不是一回事

Harness 解决的是 Agent 怎么运行，Ontology 解决的是 Agent 面对的企业业务世界如何被定义、访问和操作。一个更关注执行过程，一个更关注业务语义和业务边界。

当然，二者之间会有交叉。例如权限校验，Harness 可以控制工具调用权限，Ontology 可以控制业务对象和 Action 权限，底层业务系统还需要执行最终授权。真正可靠的架构不是只在某一层做权限，而是让各层职责清晰、约束一致。

2．Ontology 不应该替代 DDD 和领域服务

这也是我认为非常需要警惕的一点。有些团队理解 Ontology 之后，容易产生一个新想法：既然本体能定义 Object、Rule 和 Action，那是不是以后所有业务逻辑都放进 Ontology？我不赞成这种做法。

复杂的事务逻辑、库存扣减、订单状态机、财务记账规则，本来就有成熟的领域服务和业务系统承载。如果为了引入 Ontology，把这些逻辑全部复制一遍，就会产生两个问题：一是规则重复维护，二是业务权威不清晰。比如库存能不能扣减，到底由 Ontology 判断，还是 ERP 的库存服务判断？如果两个地方的规则不一致，听谁的？

「Ontology 应该为 Agent 提供稳定的业务语义和受控操作入口，而不是把企业现有业务系统全部重写一遍。」

对于某些跨系统、查询型、推导型规则，本体运行时可以直接执行；对于涉及复杂事务和领域不变量的规则，则应该引用和调用真正的领域服务。Action 也是一样，它可以定义业务操作的语义、参数、前置条件和权限要求，但真正的事务执行仍然交给负责该业务的系统。这样才不会把 Ontology 做成一个新的超级单体。

3．MCP 和 Ontology 也不是替代关系

现在做 Agent，MCP 已经是绕不开的技术。但 MCP 解决的核心问题，是工具和上下文能力如何以标准方式提供给模型应用。它本身并不自动解决企业对象语义、跨系统身份映射、业务规则和操作合法性。

假设通过 MCP 暴露了三个工具：query_customer、query_bill、create_follow_up_task，Agent 当然可以调用。但仅仅拥有这三个工具，并不意味着 Agent 就知道：账单和客户的真实归属关系是什么、什么叫待跟进客户、哪些客户经理有权负责哪些客户、创建任务之前需要验证哪些业务条件。这些仍然需要业务语义和规则体系来提供。

反过来，Ontology Runtime 完全可以通过 MCP 向 Agent 暴露查询和 Action 能力。所以我更愿意把两者理解为不同层面的基础设施：

MCP 解决能力怎么连接，Ontology 解决连接之后如何理解和约束业务。二者可以结合，而不是二选一。

## 真正做项目时，最容易踩的几个坑

上面这 17 步看起来很完整。但如果真正落地，最难的往往不是把流程图画出来，而是处理几个非常具体的工程问题。

第一个坑：对象建了很多，但没有稳定的身份体系

业务部门认为客户只有一个，但 CRM 有一个客户 ID，ERP 有一个客户编码，计费系统还有一个账户编号。到了本体层，三个系统的记录究竟是不是同一个客户？如果这个问题没有解决，后面的关系、规则和 Action 都可能建立在错误的对象身份上。所以对象建模不能只定义字段，还需要明确对象主键、来源标识、跨系统映射、合并规则和冲突处理方式。

第二个坑：把业务规则全部写在 Prompt 里

在 System Prompt 里写“逾期超过 30 天且未结清的账单需要跟进”，模型就能理解，初期很快。但企业规则一旦变复杂，问题马上出现：不同 Agent 使用不同 Prompt，不同业务线有不同阈值，规则变更后有些 Agent 更新了、有些没更新，最终企业根本不知道哪一套规则才是正式生效的版本。Prompt 可以帮助模型理解规则，但不应该成为核心业务规则的唯一存储和执行位置。

第三个坑：只验证参数类型，不验证业务关系

三个 ID 都合法，不代表三个 ID 组合合法。如果 Action 只验证 JSON Schema，就很容易把格式正确的错误请求送进业务系统。真正需要校验的是对象身份、关系、权限、状态和业务前置条件；对于重要写操作，这些校验还应该在最终执行接口处再次得到保障。

第四个坑：只考虑调用成功，不考虑并发和重试

Agent 调工具不是一次性脚本，真实运行环境里会有超时、重试、重复调用、状态变化和异步回执。如果 Action 没有幂等设计，一次超时就可能创建两个任务；如果没有状态复核，Agent 可能根据已经过期的数据执行操作。Agent 工程不是要绕过传统软件工程，而是要把传统软件工程的约束重新带回 AI 执行链路。

第五个坑：把本体当作所有业务数据的实时真相

本体可以提供统一的对象视图，但这个视图不一定永远实时。有些对象按需查询，有些来自缓存，有些关系通过事件同步，有些数据每天批量更新。如果不区分数据的新鲜度，Agent 就可能拿着昨天的业务状态做今天的决策。对于资金、库存、合同和重要业务写入，往往需要直接向权威系统验证最新状态。

第六个坑：把 Action 执行成功当作整个业务目标完成

调用了创建任务接口，就说任务完成；调用了发送邮件接口，就说沟通完成；调用了审批接口，就说流程完成。其实很多时候只是发起了一个动作。业务目标是否达成，还需要继续观察真实状态。一个成熟的 Agent 不能只有 Tool Calling，还需要目标状态管理、执行回执、结果核验和异常恢复。

## 如果从零开始建设，我会怎么做？

讲了这么多架构，最后回到落地。如果一家企业今天决定建设 Ontology，我不建议一开始就做一个覆盖全公司的超级本体平台。那样很容易陷入无休止的建模：客户模型还没统一，订单模型又开始争论；半年过去，平台里已经有几百个 Object，但没有一个 Agent 真正通过它完成业务操作。

我更建议反过来做：先选一个足够小、但包含完整读写闭环的业务场景，比如本文这个逾期客户跟进。它业务对象不多、数据来源明确、规则容易定义，既有查询也有写入，还有权限、审批、关系校验和状态回流，很适合作为第一个完整的 Ontology Runtime 场景。

1. 先把 Customer、Bill、CustomerManager、FollowUpTask 四类对象建起来。

2. 解决它们与 CRM、计费系统、任务系统之间的身份和数据映射。

3. 定义 PendingFollowUp 规则，确保规则可以独立于模型执行和测试。

4. 提供受控的 Object Query，让 Agent 通过业务对象查询，而不是直接拼接底层 SQL。

5. 封装 CreateFollowUpTask Action，把关系校验、权限、状态复核、幂等和审计补齐。

6. 接入 Agent Harness，把定义获取、逻辑查询、规则推导、Action Request、人工确认、执行回执和结果核验串起来。

7. 做端到端测试，而且不能只测正常情况。

测试时还应该故意构造一些异常场景：

账单属于另一个客户；客户经理已经变更。

账单在审批期间结清；任务接口调用超时但实际创建成功。

本体视图同步延迟；用户没有权限访问某个客户。

模型生成了不存在的属性或 Action。

如果这些情况都能够被正确拒绝、恢复或者如实反馈，那么这套架构才开始具备进入真实业务环境的基础。至于以后要不要扩展到订单、库存、采购、合同、设备、工单，可以在第一个场景稳定之后逐步推进。

本体平台的成熟度，也不应该只用对象数量衡量。我更关心几个指标：

有多少业务操作已经通过统一的语义契约运行？

多少规则能够被集中管理和验证？多少跨系统对象关系可以被可靠解析？

多少高风险操作具备执行前校验和完整审计？Agent 的错误请求有多少被成功拦截？

任务的实际完成率、重复执行率和异常恢复率怎么样？

这些指标，比“我们已经建了 500 个 Object”更能说明本体的实际价值。

## 最后再看这张图：Ontology 真正改变了什么？

现在回头看最开始的需求：“找出华东区逾期超过 30 天的客户，并为其创建跟进任务。”如果没有本体运行时，这个任务很可能是这样执行的：模型理解需求、生成 SQL，数据库返回数据，模型分析结果、调用创建任务接口，最后告诉用户任务完成。

这条链路不是完全不能用。对于简单、低风险、数据结构稳定的场景，它甚至可能非常高效。但一旦进入复杂的企业环境，问题就会暴露出来：模型对业务字段的理解是否正确？查询结果是否符合权限？业务规则到底来自哪里？对象关系是否可信？执行前状态有没有变化？操作是否合法？执行结果是否真实？后续状态如何同步？

引入 Ontology Runtime 之后，我们希望把这条链路改造成一个可核验的闭环：用户提出业务目标，编排层获取经过权限裁剪的本体定义，模型根据定义提出逻辑查询请求，本体服务验证请求并访问真实业务系统，数据被映射为业务对象和关系，规则服务根据事实推导结论并保留依据，模型基于已有对象提出 Action Request，系统验证对象关系、权限和最新业务状态，必要时交给人审批，Action Service 通过受控接口执行操作，业务系统返回真实回执，变更同步回本体视图，编排层核验最终业务状态，用户得到清单、依据、任务编号和未完成事项。

如果只从技术组件看，里面没有多少特别神奇的东西：对象映射、规则引擎、权限控制、API、事务、事件同步、审计、工作流，这些技术企业软件早就在用了。

「Ontology 的价值，不是突然发明了这些能力，而是尝试把它们组织成一套面向企业业务世界的统一语义与操作契约，让 Agent 能够稳定地使用。」

这也是为什么我不太认同“本体就是知识图谱加几个 Action”这种说法。知识图谱、语义层、规则引擎、Workflow、API 都很重要，也都不会因为 Ontology 出现就失去价值。但对于企业 Agent 来说，真正的挑战是把它们连接起来，让模型面对的是一个有对象、有关系、有规则、有权限、有可执行动作的业务世界，而不是一堆互不相干的数据库表、接口文档和工具描述。

说到底，企业 AI 正在经历一个变化。过去我们主要关心模型能不能回答问题，后来开始关心模型能不能调用工具；现在，当 Agent 真正进入企业核心业务流程之后，我们不得不继续追问：它凭什么认为自己的判断是对的？它凭什么认为自己有权执行？它怎么证明操作真的成功了？

这些问题不可能只靠更大的模型解决。我认为一个合理的分工应该是：模型负责理解意图和提出请求，本体负责提供业务定义、对象关系、规则依据和受控操作契约，业务系统负责执行真实操作并维护自己的权威业务状态，编排层负责推进任务、处理异常、核验结果。

模型的输出是请求，不是结论。

模型说这个客户需要跟进，要有事实和规则支撑；模型说要创建任务，要先验证对象关系和当前状态；模型说任务创建成功，要有业务系统的真实回执；模型说整个目标已经完成，还要核对最终的业务状态。

本体的价值，不是让 AI 看起来更懂企业，而是让 AI 每一次查询、每一次判断、每一次动手，都有定义、有依据、有边界，并且能够被验证和追溯。企业 Agent 真正需要的，不是一个可以随意操作企业系统的聪明模型，而是一个有能力、懂业务、守规则，并且知道自己做到了哪一步的执行系统。

这才是我理解的 Ontology Runtime，也是企业 AI 从“能够回答问题”，真正走向“能够参与业务”的关键一步。
