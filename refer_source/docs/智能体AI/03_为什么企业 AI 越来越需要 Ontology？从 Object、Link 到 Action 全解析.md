AI 知道该调用哪个接口，不代表它理解这件事在企业里意味着什么。

做企业 AI，很多团队已经走过了这样一段路。

先接大模型，再接知识库，然后开发一批 Tools，最后用 Agent 把它们串起来。Demo 看起来不错，问答也能跑通，但一旦进入真实业务，问题就开始冒出来了。

让 AI 查询客户信息，它可以调用 CRM 接口；让它分析订单，它也能查数据库；可当你进一步要求它处理一笔退款、调整一次库存，或者重新安排一项生产任务时，事情就没有那么简单了。

「AI 知道该调用哪个接口，不代表它理解这件事在企业里意味着什么。」

它需要知道操作的对象是谁，对象当前处于什么状态，相关业务规则是什么，哪些条件必须满足，当前用户有没有权限，以及执行之后会影响哪些系统。

这些问题，恰恰是企业 AI 从“能回答问题”走向“能参与业务”时绕不开的难点。

这也是为什么，过去两年，一个原本并不算大众化的技术概念开始受到越来越多关注：Ontology，本体。

尤其是 Palantir 将 Ontology 放在其企业数据与 AI 平台的重要位置之后，很多人开始重新思考一个问题：企业已经有了数据库、数据仓库、知识图谱、RAG 和业务系统，为什么还需要 Ontology？

它究竟是知识图谱的升级版，还是一种新的数据建模方式？更关键的是，它和 Agent 到底有什么关系？

要回答这些问题，不能只看概念定义，还得把它放进企业真实的业务流程里。

## 企业不缺数据，缺的是描述业务世界的模型

先看一个很普通的业务场景。

一家零售企业，已经建设了 CRM、ERP、订单系统、库存系统和数据仓库。CRM 里有客户，ERP 里有商品和库存，订单系统里有交易记录，财务系统里有应收账款。每套系统都运行正常，数据也能通过接口或者数据管道进行交换。

从技术角度看，这家企业并不缺数据。

但现在，业务负责人提出了一个问题：

“客户张三最近的订单一直没有发货，帮我查清楚原因，看看能不能从其他仓库调货。”

这个需求看起来很简单，实际上包含了一串需要连续完成的工作：

找到正确的客户及其订单。

确认订单中的商品、数量和交付要求。

查询当前库存以及库存所属仓库。

判断缺货原因，寻找可替代的供货方案。

检查其他仓库是否有足够的可用库存。

确认调拨是否符合业务规则。

检查执行人员是否有相应权限。

发起调拨，更新相关业务状态。

通知相关人员，并记录操作结果。

注意，这里面有几个不同层面的问题：数据在哪里；不同系统里的数据分别代表什么；这些数据之间存在什么业务关系；企业允许发生哪些操作；操作需要满足什么条件，执行后又应该产生什么结果。

传统的数据平台主要解决前面一部分问题。业务系统负责处理具体流程，而业务规则、权限和操作逻辑往往分散在不同的应用、服务和管理制度中。

人可以凭借经验把这些信息串起来，但 AI 并不会因为接入了几个 API，就自动获得这种能力。

「企业 AI 面临的真正难题，不只是如何访问数据，而是如何理解数据背后的业务含义，并在正确的规则下采取行动。」

Palantir Ontology 值得研究的地方，就在这里。

Palantir 将 Ontology 描述为组织的数字孪生：把企业中的数据、业务概念和相关逻辑组织起来，使人、应用以及 AI 能够围绕同一套业务对象进行理解、分析和操作。

这里的数字孪生，不只是给现实世界做一份数字化副本。更重要的是，这份数字化表达能够连接现实业务状态，并在适当的权限和规则下支持业务决策与执行。

## Ontology 到底是什么？先分开几个容易混淆的概念

Ontology 在哲学中讨论的是存在及其基本范畴。计算机科学借用了这个概念，用来表达某个领域中的概念、关系及其约束。

Tom Gruber 有一个经典定义：

“An ontology is an explicit specification of a shared conceptualization．”

简单翻译，就是对某个领域的共同概念理解进行明确、形式化的描述。

放到企业里，可以理解为：

「把企业对业务世界的共同理解，变成一套能够被系统识别、查询和使用的模型。」

为什么需要这样一套模型？因为不同部门对同一个业务概念，可能有完全不同的理解。

例如，什么叫 VIP 客户？销售部门认为，VIP 是消费金额达到一定标准的客户；运营部门认为，VIP 还需要满足活跃度要求；财务部门则可能关注合同等级、回款情况和信用风险。

如果这些口径没有统一，AI 即使能查询所有系统，也可能在不同场景下得出互相矛盾的结论。

Ontology 要解决的，首先就是业务语义的问题。

不过，需要特别说明：Ontology 并不是唯一能够统一业务语义的技术。主数据管理、语义层、领域模型以及知识图谱，也都可以承担其中一部分工作。

Palantir Ontology 的特点，在于它并不止步于概念和关系，而是进一步把业务对象与操作、逻辑和权限等能力连接起来。

为了看清这种区别，我们把几种常见技术放在一起：

技术

主要解决的问题

数据库 Schema

数据按照什么结构存储？

业务领域模型

业务概念、职责和规则应该如何组织？

知识图谱

实体之间有哪些关系，存在什么事实？

语义层

不同数据应该如何按照统一口径理解和查询？

Ontology

如何将业务对象、关系及相关逻辑组织起来，并支持受控的业务操作？

这些技术并不是互相替代的关系。一个企业完全可以同时拥有数据库 Schema、知识图谱、语义层和 Ontology。它们可以承担不同职责，也可以通过集成共同构成企业 AI 的基础设施。

真正需要关注的，不是给现有技术重新起一个名字，而是企业是否需要一个能够贯通业务语义与业务操作的统一模型。

## 从数据库 Schema 到 Ontology，中间多了什么

假设企业有一张订单表：

Order

order_id

customer_id

product_id

amount

status

created_at

数据库 Schema 规定了字段、数据类型、主键以及表之间的关联方式。这是非常重要的基础。没有这些结构，系统甚至无法可靠地存储和查询订单。

但业务人员通常不会只关心表结构。他们关心的是：这笔订单属于谁？订单中的商品来自哪个仓库？库存是否足够？如果不能按时交付，会影响哪些客户？什么情况下可以取消订单？取消之后，库存、付款和物流应该如何处理？

这些问题涉及的不只是数据结构，还有业务语义和业务规则。

我们可以把企业建模的演进粗略理解为四个层次。

第一层：Vocabulary，统一业务词汇

企业定义客户、订单、商品、仓库、退款等概念，解决不同团队使用不同术语的问题。

第二层：Taxonomy，组织概念分类

例如，商品可以分为电子产品、服装、食品；仓库可以分为区域仓、中心仓和门店仓。

第三层：Schema，定义数据结构

例如，订单具有订单编号、金额、状态和创建时间等属性。

第四层：Ontology，组织对象、关系与规则

例如，订单关联客户和商品，商品由仓库供货；订单只有满足相应条件才能发货；库存调拨需要检查可用数量、目标仓库和执行权限。

！别把规则都塞给 Ontology 🕳

业务规则并非一定要由 Ontology 本身实现。它们也可能存在于后端服务、规则引擎或工作流系统中。关键在于，Ontology 能否把相关业务概念与这些规则和操作有效地关联起来。

因此，Schema 和 Ontology 并不是谁取代谁。

「Schema 解决数据结构问题，Ontology 则试图在数据结构之上，建立一套面向业务理解和操作的统一表达。」

## Palantir Ontology 的核心：Object、Property 和 Link

先看最基础的三个概念。

Object：系统理解的业务对象

Object 可以理解为现实业务中值得被系统单独识别和操作的实体或事件。例如：

Customer：客户

Order：订单

Product：商品

Warehouse：仓库

Aircraft：飞机

Flight：航班

MaintenanceOrder：维修工单

这里需要区分 Object Type 和 Object。Object Type 是对象类型，相当于规定某类对象应该具有什么结构。Object 则是某个具体实例。

Object Type

Customer

Object

Customer_1024

name = 张三

level = Gold

再比如：

Object Type

Aircraft

Object

Aircraft_B737_001

model = Boeing 737-800

status = Active

数据库中的表和行，可以帮助我们理解这个区别：Object Type 有点像表的结构，Object 有点像具体记录。但这个类比不能完全等同。

在 Ontology 中，业务对象还可以通过统一的业务身份、属性定义和关系，与其他对象及相关操作建立联系。

数据库里的一条客户记录，可能只是一个 Customer ID 和若干字段；在业务模型中，这个客户还可以关联订单、合同、服务记录、风险信息和可执行的业务动作。

这使得上层应用不必每次都从底层数据库表开始理解业务。

Property：描述对象的属性

有了对象，还需要描述对象的特征。

Customer

├── name

├── level

├── points

└── lifetime_spend

Order

├── amount

├── status

├── created_at

└── delivery_date

Warehouse

├── location

├── capacity

└── status

Property 看起来与数据库字段非常相似，但在实际业务建模中，还需要关注属性的来源、类型、计算方式和业务含义。

有些属性直接来自底层系统，例如订单金额；有些属性则需要计算，例如客户风险评分、库存可用量或距离上次购买的天数。

CustomerRiskScore

= f（

purchase_history，

refund_history，

complaints，

payment_status

）

这个表达式只是示意，具体计算逻辑需要由企业根据业务情况定义。关键在于，系统不再只展示一组原始字段，还可以向上层应用提供经过统一定义的业务属性。

某些平台还支持共享属性、派生属性等机制，使不同对象能够复用定义，减少重复建模。

Link：表达对象之间的业务关系

如果说 Object 是名词，那么 Link 就更接近名词之间的关系。

客户下订单，订单包含商品，商品由仓库供货。这些关系并不只是为了把图画得漂亮，而是为了让系统能够沿着业务关系查询信息。

例如：“如果北京仓库暂停运营，哪些订单可能受到影响？”

系统需要从仓库找到相关商品，再找到包含这些商品的订单，最后识别受影响的客户和交付计划。

传统数据库同样能够完成这类查询，通常会使用 SQL JOIN、视图或其他查询机制。Ontology 的价值不在于数据库不能 JOIN，而在于它可以把这些关联表达为可复用的业务关系。上层应用不必每次都重新理解底层表结构，便能围绕“仓库影响哪些订单”这样的业务问题开展工作。

这对复杂企业尤其有价值。因为真实业务并不是一张张互相独立的数据表，而是由大量对象和关系构成的网络。

但这还不够。我们知道了企业里有什么，也知道了这些东西之间有什么关系，却仍然没有回答最关键的问题：

## 真正的分水岭：从描述业务，到改变业务

假设一家零售企业规定：

订单支付完成后才能正常发货。

退款金额不能超过可退款金额。

库存调拨不能超过可用库存。

超过一定金额的退款必须经过主管审批。

已经完成的订单不能随意取消。

这些规则决定了业务状态是否有效，以及某项操作能否被执行。规则可以存在于数据库约束、后端服务、规则引擎或工作流中。在一个完整的业务架构里，重要的是它们能够得到可靠执行，而不是只写在文档里。

而在 Palantir Ontology 的体系中，另一个特别值得关注的概念是 Action。

「Object 描述业务世界中的对象，Action 则把特定的业务变化定义成可以提交和执行的操作。」

例如：

ApproveRefund：审批退款

CancelOrder：取消订单

TransferInventory：调拨库存

AssignEmployee：分配员工

CloseTicket：关闭工单

为什么 Action 值得单独讨论？因为企业软件中有大量 API，但一个 API 能够被调用，不代表相应的业务操作就应该被允许。

假设系统提供了一个接口：

POST /customer/update

它可以修改客户等级。从程序角度看，这个接口完成了数据写入。但在业务上，仍然需要回答：谁可以修改客户等级？客户是否满足升级条件？是否需要审批？修改之后是否需要通知其他部门？如果操作失败，应该如何处理？整个过程是否留下审计记录？

这些问题并不是每个 API 都会自动解决的。因此，我们需要区分两个层面：

「API 解决系统如何被调用，业务 Action 解决一个业务操作如何被定义、校验和执行。」

当然，API 完全可以实现上述所有控制。两者也不是互斥的技术方案。Action 的意义在于把业务操作作为一个明确的业务单元来管理，而底层仍然可以通过 API、服务或其他机制完成实际执行。

一个完整的 Action 应该考虑什么

以库存调拨为例：

Action： TransferInventory

Parameters

├── product_id

├── source_warehouse

├── target_warehouse

└── quantity

Preconditions

├── 商品存在

├── 来源仓库可用库存充足

├── 目标仓库允许接收

└── 调拨数量合法

Authorization

├── 当前用户是否有调拨权限

└── 是否需要额外审批

Execution

├── 扣减来源仓库库存

├── 增加目标仓库库存

└── 更新相关业务状态

Post-processing

├── 通知相关人员

└── 记录操作结果

Audit

├── 操作主体

├── 操作时间

├── 操作原因

└── 操作前后的状态

这是一种用于说明设计思路的示例结构，并不意味着所有平台都以完全相同的方式组织 Action。它想表达的是：一次业务变化不应该只是修改某个字段，而应当明确输入、前置条件、权限、执行逻辑和结果记录。

在 Palantir 的 Ontology 体系中，Action Type 可以定义参数、对象及属性的修改规则、提交条件，以及与操作相关的副作用等内容。这就使得业务动作能够以相对统一的方式被应用和 AI 使用。

对于企业 AI 来说，这种能力的重要性远远超过多接几个接口。

## 三个容易混淆的概念：Function、Action、Interface

在理解 Action 之后，还有几个概念需要放到正确的位置。

Function：复杂的业务逻辑怎么算

有些业务逻辑不是简单的字段修改，也不是一条固定的判断语句。

例如，企业希望根据客户过去 12 个月的消费金额、退款次数、投诉记录、最近一次购买时间和信用风险，计算客户的流失风险。可以把计算逻辑抽象为：

calculateCustomerRisk（customer）

输入：

Customer

Orders

Refunds

Complaints

输出：

risk_score = 0．83

随后，业务系统可以根据计算结果生成跟进任务，或者由 Agent 提出相应建议。在概念上，可以这样理解：

Function 负责计算和业务逻辑，Action 负责提交和执行业务变化。

这不是对所有企业软件的绝对划分，而是理解 Palantir 相关概念时非常实用的思路。具体 Function 如何运行、如何读取数据，以及是否具有副作用，仍然需要看平台的实际实现和设计约定。

Interface：不同对象能否以统一方式被使用

假设企业有汽车、卡车和摩托车，它们的具体属性不完全相同，但都具有位置、状态和里程等信息。上层应用可能只关心一件事：车辆当前在哪里，状态是否正常，累计行驶里程是多少。

这时，可以通过统一接口抽象出共同的结构或能力。这样，应用就不必为每一种具体对象重复编写完全相同的逻辑。

在 Palantir Ontology 中，Interface 可以用于描述不同 Object Type 共享的结构或能力，使它们能够以一致的方式被建模和使用。

对于 Agent 来说，这种抽象也有意义。如果每增加一种业务对象，都要求 Agent 重新学习一整套完全不同的调用方式，系统的扩展成本就会不断上升。统一的对象能力和接口，有助于减少这种重复。

Role：谁可以执行什么操作

最后是权限。企业里，销售可以查看客户、创建报价；销售经理可能有权审批折扣；财务可以在授权范围内处理退款；管理员负责管理特定权限。

这类职责不能仅仅依靠 Prompt 告诉模型。权限必须由系统可靠地执行。

在 Palantir 的体系中，Role 及相关权限机制可以用于控制用户对 Ontology 资源和能力的访问。实际授权范围还取决于平台配置、应用身份和具体安全策略。

对于企业 Agent，正确的思路不是给它一个能够访问所有系统的超级 API Key，而是让每一次数据访问和业务操作都受到适当的身份、权限和规则约束。

！权限不是万能的 🕳

在 Ontology 中定义了权限，不代表整个 AI 系统就天然安全。如果敏感数据已经被不加区分地导出，并直接放进模型上下文，单靠 Ontology 层面的权限控制并不能挽回所有风险。企业还需要治理数据访问、工具调用、模型上下文、应用入口和执行结果。

## Ontology 与知识图谱，究竟是什么关系

这是另一个容易产生误解的地方。有一种很直观的说法：Ontology 是骨架，知识图谱是骨架加血肉。

这个比喻可以帮助入门，但如果把它当成严格的技术定义，就不够准确了。

在语义技术领域，Ontology 通常用于定义概念、关系、约束以及概念之间的逻辑；知识图谱则通常用于组织实体、关系和事实。实际系统中，知识图谱可以使用 Ontology 作为模式基础，也可以采用其他模式组织数据。

两者存在紧密联系，但并不是所有知识图谱都必须建立在同一种 Ontology 上，也不是所有 Ontology 都一定对应一个知识图谱。

用订单业务举例。Ontology 可以规定：

Order

│ hasAllocation

▼

InventoryAllocation

这定义了订单和库存分配之间允许存在的一种业务关系。实际业务数据则可能是：

Order_A1024

│ hasAllocation

▼

Allocation_001

前者描述模型中的概念和关系，后者描述某个具体订单与某条分配记录之间的事实。

但 Palantir Ontology 又不只是传统意义上的图谱模式。它还可以把业务对象与属性、Action、Function 和权限等能力关联起来，从而为业务应用和受控操作提供统一入口。

因此，更准确的理解是：

「知识图谱主要帮助组织和查询实体之间的关系与事实；Ontology 可以进一步把企业的业务语义、操作逻辑和治理要求组织成可供系统使用的模型。」

两者可以协同工作，而不是非此即彼。

## Ontology 为什么对企业 Agent 特别重要

到这里，我们终于可以把问题拉回 AI。过去开发一个 Agent，常见的做法是：

User

↓

LLM

↓

Tool

↓

API

↓

Business System

这种架构并没有错。对于很多任务，直接调用 API 就足够了。例如查询天气、获取订单状态、读取某个报表，没必要为了使用 Agent 而额外引入复杂的业务模型。

但当任务需要跨系统理解对象、判断状态、执行规则并修改业务数据时，问题就会复杂起来。

假设 Agent 拿到了三个工具：

get_customer（）

get_order（）

update_customer（）

它知道这些工具可以被调用，却不一定掌握完整的业务约束。例如，它可能查到了客户，也查到了订单，但并不知道客户当前是否存在未完成的退款、是否有信用限制，或者某项变更是否需要主管批准。

如果这些约束没有通过可信的系统机制提供给 Agent，模型就只能依靠上下文中零散的信息进行判断。

这正是企业 AI 与普通聊天机器人的一个重要区别。

「Agent 不仅要知道有哪些工具可用，还需要知道这些工具作用于什么业务对象、会产生什么影响，以及在什么条件下可以执行。」

Ontology 可以为此提供一层业务抽象。Agent 不必直接面对每个系统里完全不同的数据结构，而是可以围绕 Customer、Order、Product、Warehouse 等业务对象进行查询，再通过明确的业务 Action 申请执行操作。

至于底层数据来自哪个 CRM、ERP 或数据库，具体由平台及其集成层处理。

！Ontology 不解决所有集成问题 🕳

这并不意味着 Ontology 可以自动解决所有系统集成问题。不同系统之间的身份映射、数据一致性、事务处理和错误恢复，仍然需要工程设计。Ontology 的价值，是为这些工程工作提供一个相对统一的业务表达层。

## 企业 AI 的能力边界正在发生变化

过去几年，企业 AI 的一个主流应用方向是 RAG。典型流程是：

Documents

↓

Chunking

↓

Embedding

↓

Vector Database

↓

Retrieval

↓

LLM

↓

Answer

例如，员工询问：“公司的差旅报销制度是什么？”系统检索相关制度文件，再让模型整理答案。

这个场景中，RAG 很有价值。它能够让模型利用企业资料回答问题，并在合适的实现中提供来源依据。

但如果用户提出：“帮我重新安排下个月的东京客户会议。”任务性质就变了。

Agent 需要了解客户是谁、会议安排是什么、哪些员工参加、日程是否冲突、哪些地点可用、谁有权限修改会议，以及修改后如何通知参与者。如果还需要更新 CRM、日历或其他业务系统，整个任务就涉及真实业务状态的变化。

这不是说 RAG 无法参与这类任务。事实上，RAG 仍然可以提供会议政策、客户背景和相关文档。问题在于：

「检索到正确的知识，不等于获得了执行业务的完整能力。」

一个更完整的企业 AI 系统，往往需要让不同技术各司其职：

RAG 负责从文档和非结构化资料中检索相关信息。

数据平台 负责提供可靠的数据访问和处理能力。

Ontology 或其他业务语义层 负责组织业务对象、关系和相关操作。

Workflow 负责管理多步骤流程、等待、重试和人工交接。

Agent 负责理解需求、组织上下文、推理并选择下一步行动。

权限、规则和审计机制 负责约束真实业务操作。

这些组件不是固定不变的标准答案，企业也不一定需要同时部署所有组件。真正重要的是，不能指望某一项技术包办整个企业 AI 的所有问题。

企业 AI 的能力边界，正在从“能否回答正确的问题”，扩展到“能否在真实业务约束下完成任务”。

Ontology 是其中一种值得认真研究的架构选择。

## 完整案例：让 Agent 处理一笔库存不足的订单

前面讨论了不少概念。现在把它们放进同一个业务场景。假设用户告诉 Agent：

“订单 A1024 的库存不够，帮我处理一下。”

订单需要 100 件商品，但北京仓当前只有 60 件。如果 Agent 只是一个会调用接口的模型，它可能直接搜索一个库存调拨 API，然后尝试修改数据。

真正可靠的处理方式，需要先搞清楚业务状态。

第一步：识别订单和商品

Agent 根据订单编号找到对应的 Order 对象，再通过业务关系找到订单中的 Product。

Order_A1024

│ contains

▼

Product_P001

这一步解决的是：用户说的到底是哪笔订单、涉及什么商品。如果订单编号不存在，或者匹配到了多笔记录，系统应该要求进一步确认，而不是让模型猜测。

第二步：查询库存和供货关系

接着，Agent 找到商品关联的仓库及库存信息。

Product_P001

│ storedIn

▼

Warehouse_Beijing

查询结果：

Required Quantity = 100

Available Quantity = 60

Shortage = 40

！可用库存不等于总库存 🕳

这里还有一个容易被忽略的工程细节：可用库存不一定等于数据库中的库存总量。企业可能需要扣除已分配数量、冻结库存或其他不可用库存。系统必须明确 “Available Quantity” 的业务定义，不能只拿一个数字就让 Agent 自行判断。

第三步：寻找替代方案

Agent 进一步查询其他仓库。假设上海仓有 200 件可用库存，运输安排也允许在规定时间内完成调拨。

此时，Agent 可以提出一个候选方案：从上海仓向北京仓调拨 40 件。但提出方案不等于执行。它还需要检查：

上海仓是否有足够的可用库存。

北京仓是否允许接收这批商品。

调拨是否符合物流和时效要求。

当前用户是否有权限批准或执行调拨。

调拨数量是否超过审批阈值。

这些判断应尽可能由可信的业务规则和系统数据支撑，而不是仅依靠模型的语言推理。

第四步：申请执行 Action

如果业务模型定义了相应的调拨操作，Agent 可以构造参数：

Action： TransferInventory

product = P001

from = Shanghai

to = Beijing

quantity = 40

平台对参数、权限和业务前置条件进行校验。如果需要人工审批，就把任务提交给相应的审批人。如果校验失败，则返回明确的失败原因，让 Agent 继续寻找其他方案，或者向用户解释为什么无法执行。

第五步：执行并验证结果

在所有必要条件满足后，系统执行调拨操作。理想情况下，业务处理会涉及：

按照业务规则更新来源仓和目标仓的库存。

记录调拨单及其状态。

更新相关订单的处理状态。

通知仓库及相关人员。

记录操作主体、时间、参数和结果。

如果操作跨越多个独立系统，还需要考虑部分失败、重复提交、并发修改以及补偿处理等问题。不能因为 Action 有明确的业务名称，就假设底层事务天然具备原子性。

操作完成后，系统应重新读取或核验实际状态，再向用户报告结果。这一步尤其重要。

「Agent 不能把“接口调用成功”直接等同于“业务已经完成”。」

真正的闭环是：理解需求、读取事实、提出方案、校验约束、申请执行、核验结果，再根据真实结果向用户反馈。这才是 Ontology 与 Agent 结合时最值得关注的工程价值。

## Ontology 建得越复杂越好吗？恰恰不是

技术讨论中有一种常见倾向：一个概念越复杂，似乎就越先进。Ontology 也容易陷入这个误区。

对象越建越多，关系越来越密，图越来越漂亮，最后却没有几个真实业务场景能够依靠它完成任务。我更愿意把这种情况称为数字盆景。

看起来枝繁叶茂，实际上与业务运行之间仍然隔着一段距离。

一个有价值的 Ontology，不是把企业里所有表都翻译成 Object，也不是把所有字段都画成 Property。建模之前，至少需要问三个问题。

Object 是否对应真实的业务概念

如果一个对象只对应某张临时中间表，业务人员无法理解它的含义，上层应用也没有复用它的需求，那么就需要重新考虑它是否应该成为核心业务对象。

当然，技术对象并非不能存在，而是应该区分技术实现细节与面向业务的核心模型。例如，Flight 比 FL_TBL_001 更适合作为面向业务的对象名称。名称不是全部，但业务语义必须清楚。

Link 是否能够回答真实业务问题

不要为了让图谱看起来完整，就在两个对象之间随意添加一个 relatedTo。应该先问：为什么它们存在关系？这种关系在什么条件下成立？业务人员会沿着它查询什么？它是否能够帮助判断影响范围、责任主体或业务方案？

如果一个关系没有明确的业务含义，也没有实际使用场景，那么它未必值得成为核心模型的一部分。

Action 是否对应一个真正的业务动作

UpdateStatus 可能只是一个技术操作。ApproveRefund、TransferInventory 和 AssignEmployee 则更容易对应具体的业务职责和结果。

这不意味着所有底层更新都要包装成复杂的业务流程。简单、低风险的操作可以保持简单。但凡是涉及资金、库存、客户权益、生产安排和其他重要业务状态的操作，就应该明确其前置条件、权限边界和失败处理方式。

「Ontology 的价值，不在于把业务世界画得多完整，而在于它能否帮助系统更可靠地理解和处理真实业务。」

## Action 设计，比很多人想象的更难

当 AI 从只读走向写入，工程上的风险会发生明显变化。读错了数据，可能给出错误答案；写错了数据，则可能直接造成业务损失。

因此，企业不能只关注模型能否正确选择工具，还必须设计好工具背后的执行机制。几个方面尤其值得注意。

单一职责。 一个 Action 应尽可能对应明确的业务意图，避免把多个高风险操作藏在一个难以理解的调用里。

幂等性。 网络超时、Agent 重试或用户重复提交，都可能导致同一请求被执行多次。系统需要明确重复执行时的行为，并在适当场景使用幂等键或其他去重机制。

参数校验。 不能因为参数是模型生成的，就假设它符合业务要求。对象是否存在、金额是否合法、数量是否超限，都应该由可信的系统逻辑检查。

权限控制。 执行权限必须由系统验证，而不是让模型根据 Prompt 自行判断。

状态一致性。 多系统协作时，需要考虑并发修改、部分成功、超时和补偿处理。业务动作不能只定义正常路径。

审计与可追溯。 系统应记录操作主体、请求参数、操作原因、执行结果，以及必要的状态变化信息。

人工介入。 对高风险操作，应明确哪些场景需要审批、哪些情况必须停止、何时应该把决定交还给人。

这些机制不是为了限制 AI，而是为了让 AI 的能力能够真正进入生产环境。

「模型可以有不确定性，但企业不能把不可控的不确定性直接转化成业务风险。」

## 回到 Palantir 的整体架构：Ontology 处于什么位置

理解 Ontology，还需要把它放进 Palantir 的整体平台中。可以用一个简化的结构来理解：

AI Applications / AIP

│

▼

Ontology

业务对象、关系、逻辑、操作

│

▼

Foundry

数据集成、数据处理与管理

│

▼

ERP / CRM / MES / IoT / DB

这张图只是帮助理解职责分工的简化示意，并不代表 Palantir 所有产品组件之间唯一、固定的调用路径。可以先这样理解：

Foundry 等数据平台能力，帮助企业接入、整理和管理不同来源的数据。

Ontology 将相关数据映射为具有业务含义的对象、属性和关系，并在相应机制下连接业务逻辑与操作。

AIP 等 AI 能力，让模型和 AI 应用能够结合企业数据与业务语境开展工作。

因此，常见的概括是：

「Foundry 解决数据如何进入平台，Ontology 解决这些数据如何被组织成业务世界，AIP 则让 AI 能够利用这些能力参与工作。」

这个概括便于建立直觉，但不能理解成三者完全独立，更不能认为 Ontology 一旦建立，底层所有系统的集成、事务和治理问题就自动解决了。

真正困难的工作仍然包括数据质量、对象身份匹配、业务口径统一、规则维护、权限治理，以及跨系统操作的可靠性。Ontology 为这些问题提供了一个重要的组织方式，但它不是免除工程工作的捷径。

## 企业到底应该怎样开始建设 Ontology

如果一家企业准备尝试 Ontology，我不建议第一步就画一张覆盖整个公司的大图。更稳妥的方式，是从一个业务闭环开始。

例如，先选择库存不足订单处理、退款审批、客户风险跟进等具体场景。然后沿着业务流程逐步建设。

第一步：选场景，而不是先选技术

优先考虑那些发生频率高、业务价值明确、数据相对可得、结果能够衡量的场景。同时评估失败成本。

查询一个客户的订单状态，与直接批准一笔大额退款，风险显然不同。两者不应该采用同样的执行策略。

第二步：识别核心业务对象

围绕选定场景，列出真正需要的对象。以库存调拨为例，可能包括：

Order

Product

Warehouse

Inventory

InventoryTransfer

Employee

这里不需要一开始就覆盖整个供应链。只要能支撑第一个业务闭环，就可以先从最小的对象集合开始。

第三步：梳理关系和数据来源

明确每个对象来自哪个系统，如何识别同一个实体，以及不同系统之间的关联如何建立。

例如，ERP 中的商品编码与仓储系统中的 SKU 是否一致？同一个仓库在不同系统中是否使用不同编号？库存数据多久更新一次？

这些问题如果没有解决，再漂亮的业务模型也会建立在不可靠的事实之上。

第四步：明确状态和业务规则

确定什么叫可用库存、什么叫订单已支付、什么情况允许调拨，以及哪些条件必须经过审批。

尽量让关键规则由可验证的系统逻辑执行，而不是只依赖模型理解自然语言制度。

第五步：设计 Action 与权限

先定义业务操作的输入、前置条件、授权方式、执行结果和失败处理。

高风险操作可以先采用“AI 提出建议、人工确认、系统执行”的模式。随着验证结果积累，再决定哪些低风险步骤可以逐渐自动化。

第六步：让闭环真正运行起来

最后，衡量的不应只是模型回答准确率，还应包括：

任务完成率。

操作失败率。

人工介入比例。

平均处理时间。

重复操作和异常操作数量。

业务结果是否达到预期。

只有这些指标真正改善，才能说明这套模型和相关系统为业务创造了价值。这也是为什么，我认为 Ontology 建设应该由业务问题牵引，而不是由建模工具牵引。

## Ontology 是不是企业 AI 的必选项

说到这里，也需要给 Ontology 划清边界。不是所有企业 AI 项目都需要引入完整的 Ontology。

如果需求只是查询文档、总结会议、生成报告，或者调用少数几个边界清晰的 API，现有的 RAG、工具调用和业务服务可能已经足够。

如果任务涉及多个业务系统，需要理解复杂的对象关系，必须遵守统一的业务规则，还要对真实业务状态进行持续、可追溯的修改，那么统一的业务语义与执行模型就会更有价值。

它可以采用 Palantir Ontology，也可以由企业使用领域模型、主数据管理、知识图谱、规则引擎、工作流和权限系统共同构建。关键不是技术名称，而是能力是否完整。

我认为，评估一个企业是否需要 Ontology，最值得问的是：

1. 企业是否存在大量跨系统的业务对象和关系？

2. 不同应用是否反复实现同一套业务口径和规则？

3. Agent 是否需要从查询数据进一步走向修改业务状态？

4. 企业是否需要对这些操作进行统一授权、验证和审计？

如果这些问题都很突出，那么 Ontology 就不只是一个值得了解的概念，而可能成为企业 AI 架构中需要认真考虑的一层。

！别为技术热点而建模 🕳

反过来，如果只是为了追逐技术热点，把原来的几张表重新包装成 Object，却没有解决任何真实业务问题，那么建设它的收益可能并不高。

## 最后：企业 AI 缺的，可能不只是更强的模型

过去几年，企业 AI 的讨论重点经历了几次变化。

一开始，大家关心模型够不够聪明。后来，大家开始关注企业数据能不能接进来，RAG 能不能检索到正确资料。再后来，Agent 和工具调用让模型能够执行更多任务。

但当 AI 真正进入业务系统之后，另一个问题变得越来越明显：

模型知道应该做什么，和企业允许它做什么，是两回事。

企业不仅需要 AI 理解自然语言，还需要它理解业务对象；不仅需要它能够生成方案，还需要它知道方案会改变哪些状态；不仅需要它调用工具，还需要工具背后的规则、权限和执行结果都能够得到可靠管理。

这也是我理解 Palantir Ontology 时，最看重的地方。

它不是简单地给数据库增加一层抽象，也不是把知识图谱换一个名字。它试图把企业的数据映射成业务对象，把对象之间的关系表达清楚，再将相关的业务逻辑、操作和治理机制连接起来。最终，让人、应用和 Agent 能够围绕相对统一的业务世界开展工作。

当然，Ontology 并不能替代大模型，也不能自动解决企业数据治理、系统集成和业务流程设计中的所有问题。它真正的价值，在于为这些能力提供一个可以共同依赖的业务表达基础。

如果把企业 AI 的发展理解成三个阶段，我更愿意这样概括：

1. 第一阶段，AI 能够回答问题。

2. 第二阶段，AI 能够调用工具。

3. 第三阶段，AI 能够在真实业务约束下，参与完成一项工作。

这三个阶段并不是严格的技术演进顺序，也不是说所有企业都必须依次建设。但它们确实代表了不同程度的业务集成与执行能力。

从这个角度看，Ontology 的意义就清楚了。

「企业 AI 的下一步，不只是让模型更聪明，而是让 AI 进入一个它能够理解、系统能够验证、权限能够约束、操作能够追溯的业务世界。」

而 Ontology，正是构建这个世界的一种重要方式。

这可能比 Ontology 这个词本身，值得我们花更多时间研究。
