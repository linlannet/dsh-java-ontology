企业 AI 的下一阶段，竞争的不是 Agent 数量，而是能否把业务世界建成一个AI 真正能参与运行的系统。

过去两年，我一直觉得企业 AI 领域有一个挺奇怪的现象。

一边是技术发展得越来越快。从 RAG 到 GraphRAG，从 Function Calling 到 MCP，从单 Agent 到 Multi-Agent，再到最近大家讨论的 Agent Harness、Skills、Ontology，几乎每隔几个月就会出现一套新的技术叙事。

另一边，企业 AI 的落地却没有想象中那么快。

很多企业已经建了知识库，接入了大模型，开发了几个 Agent，甚至搭建了自己的智能体平台。演示的时候效果都不错，领导问一个问题，AI 能从几十份文档中找到答案；输入一个任务，Agent 能调用工具、生成报告、执行工作流。

但只要再往前走一步，问题就来了。

假设一家制造企业有一笔客户订单，原定下周交付。今天上午，MES 系统发现某台关键设备故障，预计停机八小时。

这个时候，企业真正需要 AI 做什么？

显然不是简单地解释设备故障的原因，也不是从知识库中找出《设备异常处理 SOP》。

它需要知道这台设备属于哪条产线，当前承担哪些生产工单；

这些工单关联哪些客户订单，是否存在替代产能；

库存能否支持重新排产，调整计划会不会影响其他订单；

以及哪些操作需要生产经理审批。

如果最终决定调整排产，AI 还要能够调用真实业务系统执行操作，并确认执行结果。

这才是一个完整的企业 AI 场景。

问题在于，今天很多企业的 AI 架构，并没有为这种任务做好准备。

RAG 知道文档在哪里，知识图谱知道实体之间有什么关系，Agent 知道有哪些工具可以调用，但它们之间往往缺少一个能够统一描述业务对象、实时状态、执行动作和权限规则的中间层。

我认为，这恰恰是最近企业 AI 领域重新关注 Ontology（本体论）的重要原因。

而与 Ontology 一起值得讨论的，还有另一种正在受到关注的工程交付模式：FDE（Forward Deployed Engineering，前线部署工程）。

把这两个概念放在一起看，会发现企业 AI 的架构和交付方式，正在出现一种值得重视的变化。

过去我们主要考虑如何把模型接入企业系统。

现在更需要考虑的是，如何让 AI 真正进入企业的业务运行体系。

📌 本文看点

1. RAG 加 Agent 为何撑不起执行

2. 可执行本体的五类能力

3. FDE 的五阶段交付方法

## 企业 AI 的问题，可能从一开始就被定义错了

先说一个比较常见的项目。

某企业希望建设一个采购智能体。

需求听起来很明确：让 AI 帮助采购人员分析供应商、检查库存、识别采购风险，并给出采购建议。

按照现在常见的技术路线，团队大概率会这样设计：

先把采购制度、供应商资料和历史合同放进知识库，通过 RAG 提供知识检索能力；

然后接入 ERP 的库存查询 API、采购订单 API；

最后开发一个 Agent，通过 Prompt 和工具调用完成采购分析。

这套架构能不能工作？

当然可以。

但它通常只能覆盖采购流程中的一部分。

例如，Agent 查询发现某种物料库存不足，于是建议补货。

问题是，库存不足是否一定需要采购？

也许某个生产订单已经取消，只是 ERP 里的需求计划还没有同步；

也许其他仓库存在可调拨库存；

也许这批物料已经有在途采购订单；

也许供应商交期已经发生变化；

也许某个客户订单的优先级被临时提高。

这些信息可能分散在 ERP、MES、WMS、SRM 等不同系统中。

更麻烦的是，即使 Agent 获取了所有数据，也不代表它理解这些数据之间的业务约束。

例如：

库存数量是 100，是否意味着可用库存就是 100？

采购订单状态为 Approved，是否意味着供应商已经确认交付？

某个物料可以替代另一个物料，是否意味着所有产品都允许使用这个替代方案？

这些问题不是靠增加几段 Prompt 就能彻底解决的。

因为它们涉及的不是语言理解，而是企业业务语义。

这里有一个经常被忽略的区别：

数据告诉 AI 系统里记录了什么，业务语义告诉 AI 这些记录意味着什么，以及在什么条件下可以采取行动。

企业 AI 要从问答走向执行，就必须跨过这道门槛。

这也是为什么我越来越倾向于认为，企业 AI 架构设计不能永远围绕模型展开。

模型可以替换，Agent 框架可以替换，工具协议也可能继续演进，但企业的订单、客户、设备、工单、库存、审批、交付这些业务概念，不会因为底层模型升级就消失。

真正应该成为企业 AI 架构稳定部分的，是业务世界本身。

## RAG、知识图谱、Ontology，解决的其实不是同一个问题

本体论不是一个新概念。

它在知识工程、语义网、信息系统等领域已经存在很多年。今天重新受到关注，并不是因为企业突然发现了某种全新的知识表示技术，而是大模型和 Agent 让它有了新的工程价值。

不过，现在围绕 Ontology 的讨论存在一个问题：很多人把它理解成了知识图谱的升级版。

这个理解不能说完全错误，但如果只停留在这里，就容易忽略企业 AI 真正需要的能力。

我们不妨把几种技术放到具体业务中看看。

假设企业想知道：

“客户 A 的订单为什么延期了？”

如果使用 RAG，系统可能从生产日报、会议纪要、异常报告中找到相关信息，然后由大模型组织答案。

如果使用知识图谱，系统可以沿着客户、订单、生产工单、设备、供应商等实体关系，找到可能影响交付的节点。

如果引入 Ontology，系统除了理解这些对象及其关系，还可以进一步定义订单状态、延期规则、风险计算、可执行动作和权限约束。

例如：

订单 O-101 关联工单 W-207；

工单 W-207 依赖设备 M-08；

设备 M-08 当前处于故障状态；

工单预计完成时间比计划晚八小时；

→ 根据当前排产和客户交期约束，订单 O-101 存在延期风险；

→ 如果需要重新排产，系统必须先检查备用设备产能，并由具有相应权限的人员批准。

注意，这里已经不只是回答“为什么延期”。

系统开始具备理解业务状态、判断业务条件和组织业务行动的基础。

但还需要说明一点：Ontology 并不天然等于可执行系统。

传统本体主要关注概念、属性、关系和逻辑约束。它可以用于知识表示和推理，但并不意味着定义了一个 Action，系统就自动拥有事务处理、权限控制和执行回滚能力。

今天企业 AI 所讨论的可执行本体，实际上是在本体建模的基础上，进一步结合业务状态管理、规则引擎、计算逻辑、Action Runtime、事件系统和权限治理等工程能力。

这才是它与传统知识表示体系最值得关注的区别。

我更愿意把这种架构称为：

面向 Agent 的可执行企业业务模型。

它不是为了让知识图谱变得更复杂，而是为了让企业的业务对象能够成为AI 可以理解和操作的统一接口。

## 企业真正需要的，是一个 Runnable World Model

最近在研究企业级 Agent 架构时，我觉得 Runnable World Model（可运行世界模型）是一个很值得讨论的概念。

当然，这里的 World Model 并不完全等同于机器人和强化学习领域用于预测环境变化的世界模型。

在企业软件语境下，它更接近一个能够表示业务对象、关系、状态、规则和操作，并与真实系统保持同步的可执行业务环境。

为什么需要这样一层？

我们先看一个传统的生产线对象。

在一般的数据模型中，它可能是这样的：

ProductionLine

├── id

├── name

├── capacity

├── status

└── factory_id

这没有问题。

对于数据库系统来说，这些字段足以记录一条生产线的基本信息。

但对于需要参与生产调度的 Agent 来说，远远不够。

它还需要理解：

这条生产线当前正在生产什么？

它的产能被哪些订单占用？

发生故障时会影响哪些工单？

能否把某个工单切换到其他生产线？

切换需要满足哪些工艺条件？

谁有权批准切换？

切换成功后，哪些业务对象的状态应该改变？

于是，一个面向 AI 执行的 ProductionLine，就不应该只是几个静态字段。

它至少需要具备五类能力。

第一类 · Objects 业务对象

例如生产线、设备、工单、订单、客户、物料。

每个对象都有明确的业务身份和属性，并能够映射到真实业务系统中的记录。

第二类 · Relationships 业务关系

例如生产线包含设备，工单使用生产线，订单关联工单，工单消耗物料。

这些关系不只是用于查询，还承担影响分析的作用。

当某台设备故障时，系统可以沿着对象关系找到受影响的工单，再追踪到订单和客户。

第三类 · States 业务状态

例如设备可以处于 Running、Idle、Maintenance、Fault 等状态。

工单可以处于 Created、Scheduled、Running、Completed 等状态。

状态之间存在转换条件，而不是任意修改一个字段。

第四类 · Rules 与 Computations 规则与计算

例如：

只有具备指定工艺能力的生产线才能承接某个工单；

如果预计完成时间超过承诺交期，则触发交付风险计算；

如果替代排产方案导致其他高优先级订单延期，则需要重新评估方案。

这里既可以使用确定性的规则和计算，也可以引入模型进行预测和辅助判断。

但二者应该明确区分。

！踩坑提示 🕳

不能把模型生成的一段解释，直接当成企业的正式业务规则。

第五类 · Actions 业务动作

例如：

rescheduleWorkOrder()

assignProductionLine()

requestMaterialTransfer()

approveScheduleChange()

这些 Action 对应的是业务操作，而不是简单暴露底层数据库更新接口。

一个真正可用于生产环境的 Action，至少需要说明：

输入是什么，执行前需要满足什么条件，由谁授权；

调用哪个业务系统，执行后预期改变什么状态；

如何确认执行成功，以及失败后应该怎么办。

举个例子。

Agent 希望执行：

rescheduleWorkOrder(

workOrderId = "W-207",

targetLine = "LINE-03"

)

系统不能因为参数格式正确，就直接调用 MES 修改排产。

它需要先检查 LINE-03 是否具备相应工艺能力，是否有足够产能，物料是否齐套，当前工单是否允许变更，以及操作者是否拥有排产调整权限。

如果这些条件不满足，Action 就应该拒绝执行，或者转入审批流程。

这才是业务语义真正进入执行系统的地方。

在我看来，可执行本体最重要的价值，不是让 AI 多认识几个对象，而是把原本散落在业务系统、接口文档、程序代码和员工经验中的业务约束，逐步组织成一个可以被 Agent 使用的操作环境。

## 为什么我不建议让 Agent 直接操作企业 API

现在不少 Agent 平台都强调工具生态。

接入 MCP 后，Agent 可以发现和调用各种工具。企业内部也可以把 ERP、CRM、MES 的 API 封装成 MCP Server。

从连接能力上看，这确实解决了不少问题。

但工具接入和业务执行是两回事。

例如，ERP 提供了一个修改订单交期的接口：

updateOrderDeliveryDate(

orderId,

newDeliveryDate

)

Agent 知道这个工具存在，也知道如何填写参数。

但它未必知道修改交期会不会触发客户通知，会不会影响财务结算，是否需要销售经理批准，或者是否会破坏某个已经确认的交付承诺。

如果把工具描述写得足够详细，能不能解决？

可以改善一部分问题，但很难形成稳定的企业级治理机制。

因为工具描述通常围绕接口本身展开，而企业业务规则往往跨越多个对象、系统和部门。

更合理的设计，是在 Agent 和底层业务系统之间增加一个业务语义执行层。

Agent 不必直接理解每一个 ERP 字段，也不应该自行拼装复杂的数据库操作。

它面对的是具有业务含义的对象和 Action。

例如，Agent 提出的是“申请调整订单交期”，而不是“更新 ERP 某张表的某个字段”。

语义执行层负责完成对象映射、状态检查、规则校验、权限控制和系统调用。

底层可以通过 API、MCP 或其他受控连接方式完成执行。

这里还涉及一个重要的架构边界。

💡 Ontology 不应该取代 ERP、MES、CRM，成为所有业务数据的新主库。

订单的权威记录可能仍然在 ERP，设备运行状态的权威来源可能仍然是 MES 或 IoT 平台。

Ontology 要解决的是统一业务语义和对象访问，而不是强迫所有系统放弃原有的数据所有权。

如果没有把这个边界设计清楚，本体平台很容易变成又一个数据孤岛。

甚至比原来的数据孤岛更复杂。

## Agent 接入本体之后，企业 AI 的执行方式会发生什么变化？

这里可以用一个完整的业务过程来说明。

还是前面那个制造企业。

上午十点，设备 M-08 发生故障。

在传统架构中，MES 产生一条设备异常记录，生产主管收到告警，然后开始协调设备、计划、仓储和销售部门。

如果已经建设了 Agent，系统可能自动分析故障原因，并给出处理建议。

但如果企业建立了可执行本体，处理过程可以进一步向业务闭环演进。

① 事件映射

MES 的故障事件被映射到本体中的设备对象，设备状态从 Running 变为 Fault。

② 影响分析

系统根据设备与工单之间的关系，找到当前受影响的生产任务；随后根据工单与客户订单的关联关系，计算哪些订单存在交付风险。

③ 上下文计算

这里的计算可以结合当前排产计划、预计维修时间、库存、备用产能和客户交期。Agent 在获得这些上下文后，不需要重新从多个系统中猜测业务关系，而是可以围绕已经定义好的对象和状态进行推理。

④ 方案生成

它可能提出三个方案：等待设备修复，调整部分工单顺序，或者把紧急工单转移到备用生产线。

⑤ Simulation 评估

这里的 Simulation 不一定是复杂的数字孪生系统。在早期项目中，它可能只是基于确定性规则、产能约束和历史数据建立的方案评估器。系统分别计算三个方案对交付时间、生产成本、物料消耗和其他订单的影响。

⑥ 审批与受控执行

Agent 可以根据评估结果提出推荐方案，但不应直接把推荐当成最终决策。如果方案涉及跨产线调整、加班或额外采购，就进入相应审批流程；审批通过后，通过受控 Action 调用 MES 或 ERP 执行操作。

⑦ 结果校验与回写

执行完成后，还需要读取业务系统中的实际状态，确认排产是否真的改变。最后，将执行结果和相关事件同步回本体。

整个过程形成：

业务事件发生 → 对象状态变化 → 关联影响分析 → Agent 生成方案

→ Simulation 评估 → 权限审批 → Action 执行 → 结果校验 → 状态更新

这与简单的“用户提问—Agent 调用工具—返回答案”已经不是同一类系统。

前者是一个参与企业业务运行的系统。

后者更多还是一个具备工具能力的智能助手。

当然，这套流程也不能完全依赖大模型自由发挥。

哪些判断由规则引擎完成，哪些方案由优化算法生成，哪些环节需要 Agent 推理，哪些操作必须人工审批，都应该在架构设计阶段明确。

我甚至认为，在不少高风险企业场景中，Agent 最重要的能力不是自主执行，而是知道自己什么时候不应该执行。

## 架构画得再漂亮，为什么企业 AI 还是很难交付？

讲到这里，问题似乎已经解决了。

只要建立 Ontology，接入 Agent，再配置好 Action，企业 AI 就能真正落地。

实际情况远没有这么简单。

因为本体建模本身就是一项非常复杂的工程。

以“订单”为例。

销售部门理解的订单，生产部门理解的订单，财务部门理解的订单，可能并不是同一个概念。

销售关注客户承诺与交付时间；

生产关注工单、物料和产能；

财务关注收入确认、开票和结算。

ERP 中的订单状态，也不一定能完整表达真实业务过程。

如果一个工程团队坐在办公室里，根据几份需求文档就开始设计企业级 Ontology，很容易得到一个逻辑上完整、实际却没人愿意使用的模型。

！踩坑提示 🕳

更现实的问题是，企业业务规则经常不在系统里。

它可能存在于某个车间主任的经验中，某个采购经理的判断中，或者某份已经很久没有更新的 SOP 中。

这些规则甚至可能彼此冲突。

例如，系统规定某类物料必须提前七天采购，但实际业务中，紧急订单经常通过特殊审批缩短周期。

如果只按照制度文档建模，系统就无法处理真实业务。

如果完全按照现场习惯建模，又可能把历史遗留问题固化到新系统里。

这时候，仅靠一个远程 AI 开发团队，通常很难把事情做好。

也正是在这里，FDE 的价值开始显现。

## FDE 的核心不是驻场写代码，而是把业务问题变成可运行系统

FDE，Forward Deployed Engineering，可以理解为一种深入客户真实业务环境、同时承担工程实现和交付责任的工作模式。

这个概念并不是随着大模型才出现的。

Palantir 等企业很早就在复杂企业软件交付中采用类似模式。今天 AI Agent 的发展，让这种工程角色重新受到关注。

不过，我觉得现在有必要重新理解 FDE。

如果只是把开发工程师派到客户现场，按照需求写代码，那它与传统驻场开发没有本质区别。

真正有价值的 FDE，应该能够同时处理四件事：

1. 理解业务问题；

2. 识别业务系统中的真实事实；

3. 设计可运行的技术方案；

4. 通过生产结果验证交付价值。

这里最重要的是最后一点。

过去很多 AI 项目是按照功能交付的。

例如，完成知识库建设、上线三个 Agent、接入十个业务 API、支持五种工作流。

这些指标当然可以用于项目管理，但它们并不能直接说明 AI 是否改善了业务。

如果企业希望减少订单延期风险，真正应该衡量的是异常识别时间是否缩短，风险评估是否更准确，跨部门协调是否更高效，订单交付表现是否改善。

所以，我认为 FDE 的工作起点不应该是功能清单，而应该是业务闭环。

这也是为什么我比较认同一种交付思路：

先找到一个值得解决的业务问题，再围绕它建立最小可运行的业务世界。

而不是先建设一个覆盖全公司的宏大本体模型，然后再去寻找应用场景。

## 企业本体建设，最容易犯的错误就是一开始做得太大

假设一家制造企业决定建设 Ontology 平台。

项目启动后，团队开始梳理整个集团的组织架构、客户、供应商、设备、产线、物料、工单、订单、仓储、财务、质量、采购等业务对象。

随后定义几百种关系，设计复杂的本体 Schema，建设统一数据接入层。

几个月过去，模型越来越完整，但第一个真正运行的 Agent 还没有上线。

！踩坑提示 🕳

这种项目风险很高。不是因为企业不需要统一业务语义，而是因为业务语义的正确性，往往需要通过真实场景才能验证。

我更推荐从 Minimum Viable Ontology，也就是最小可用本体开始。

例如，企业首先选择生产异常处置场景。

第一版只需要建模：

设备 · 生产线 · 工单 · 订单 · 物料

关系也不必一次设计几十种。

先把设备与生产线、工单与设备、订单与工单、工单与物料之间的关键关系打通。

状态只覆盖异常处置所需的部分。

Action 先实现故障登记、影响查询、排产调整申请、审批和执行结果确认。

当这条链路真正运行起来后，再根据业务需求扩展供应商、库存调拨、质量检验等对象。

这种方式有两个好处。

1. 每增加一个本体能力，都能够找到明确的业务价值；

2. 本体模型可以在真实业务中不断校准。

毕竟，企业业务不是静止的。

组织会调整，流程会变化，系统会升级，业务规则也会改变。

一个不能持续演进的本体，最终只会成为另一套过时的企业知识文档。

## 我更看好一种五阶段的 FDE 交付方法

结合企业 AI 的实际工程特点，我倾向于把 FDE 交付组织成五个阶段。

STAGE 01业务诊断，找到真正值得自动化的闭环

这个阶段最重要的不是问客户想要什么 Agent。

而是进入业务现场，观察任务如何发生、信息如何流转、决策由谁做出、系统在哪里断开。

需要回答几个问题：

业务结果是什么？

当前瓶颈在哪里？

数据是否能够获取？

关键动作是否有系统接口？

哪些环节可以自动化？

哪些环节必须由人承担责任？

这里有一个很实用的判断标准。

！踩坑提示 🕳

如果一个场景只能证明 AI 能生成更好的文字，却无法衡量它对业务流程的影响，那么它未必适合作为企业 AI 平台的第一个突破口。

STAGE 02本体建模，把业务事实转化为对象、关系和动作

这一步不是简单画 ER 图。

而是围绕具体业务任务，把对象身份、数据来源、关系、状态、规则、权限和 Action 定义清楚。

尤其要关注业务系统中的事实来源：

订单交期以 ERP 为准；

设备状态以 MES 为准；

审批权限以企业 IAM 或相应业务权限系统为准。

如果多个系统的数据不一致，还需要定义冲突处理策略。

不能简单让大模型自行判断哪个数据更可信。

STAGE 03应用组装，把 Agent 放进业务上下文

本体建立后，才开始配置 Agent 的具体能力。

这里可以使用 MCP、Skills、Workflow、Agent Framework 等技术。

但我建议尽量保持职责清晰：

Skills 负责沉淀可复用的任务操作方法；

MCP 等工具协议负责连接和调用外部能力；

Workflow 负责确定性较强的流程编排；

Agent 负责处理需要理解、推理、规划和动态决策的任务；

Ontology 则负责提供业务对象、语义关系、状态和受控动作的统一模型。

它们并不是相互替代的关系。

也不应该把所有逻辑都塞进 Agent 的 Prompt。

STAGE 04影子运行与验证，先证明可靠，再进入生产

我认为这是企业 Agent 工程最容易被低估的一步。

很多团队验证 Agent，主要看它能否完成几个测试任务。

但企业生产系统不能只靠演示案例验证。

至少应该准备一组覆盖正常流程、异常状态、权限边界和执行失败的测试案例。

在正式授权 Agent 执行高风险操作之前，可以先让它以影子模式运行。

也就是 Agent 生成判断和操作建议，但不真正修改生产系统。

团队把它的结果与人工处理结果进行比较，逐步评估准确率、执行可行性、权限合规性和异常处理能力。

💡 对于涉及资金、合同、排产、客户承诺等重要业务动作的场景，尤其需要保留人工审批和明确的回滚或补偿机制。

STAGE 05生产交付与资产沉淀

当系统经过验证后，再逐步进入真实生产。

这个阶段不仅要监控 Agent 的成功率，还要监控业务系统状态是否正确、Action 是否完成、是否产生重复操作、是否存在未处理异常。

更重要的是，FDE 在项目中发现的业务规则、对象模型、工具封装、测试案例和交付经验，应该持续沉淀。

下一次面对类似场景时，团队不需要从零开始。

比如，第一个制造业客户已经建立了设备、工单、订单和生产线的基础模型。

第二个客户可能使用不同的 ERP 和 MES，但其中部分业务概念、状态约束和 Action 设计可以复用。

当然，这种复用不能简单理解成复制 Schema。

不同企业的业务规则可能差异很大。

真正值得复用的是经过验证的建模方法、工程组件、行业对象模板和测试体系。

这也是 FDE 模式能否规模化的关键。

如果每个项目都依赖少数专家现场手工建模、手工写代码，那么交付成本很难持续下降。

只有把项目经验逐步转化为平台能力，FDE 才能从一种高成本的专家服务，发展成可复制的企业 AI 工程体系。

## 本体论驱动的企业 AI，最难的其实不是建模

前面讲了很多架构和方法，但我不想把 Ontology 描述成企业 AI 的万能解法。

实际工程中，它会引入新的复杂度。

而且有些问题，比传统 RAG 项目难得多。

难点一 · 业务语义的一致性

企业中同一个概念可能有多种定义。

比如“订单完成”，销售部门可能认为客户已经收货才算完成，生产部门可能认为产品下线就算完成，仓储部门则可能以出库为准。

如果不明确这些语义边界，Ontology 只是把原有的数据歧义搬到了一个新平台。

难点二 · 实时状态一致性

本体中的设备状态是 Running，但 MES 已经记录设备故障。

Agent 如果基于过期状态制定排产方案，可能做出错误决策。

因此，本体层必须明确数据新鲜度、同步延迟、版本信息和状态冲突处理机制。

难点三 · Action 的可靠性

企业业务动作并不总能像普通函数调用一样，执行成功就返回 True，执行失败就返回 False。

例如，Agent 调用 ERP 创建采购订单。

请求超时了。

但 ERP 实际上可能已经创建成功，只是响应没有返回。

！踩坑提示 🕳

如果 Agent 直接重试，就可能创建重复订单。

这涉及幂等控制、事务边界、异步状态查询、失败补偿等传统分布式系统问题。

这些问题不会因为使用了大模型就消失。

难点四 · 权限与责任边界

Agent 代表谁执行操作？

如果某个销售人员只能查看自己负责的客户，Agent 是否能够跨客户查询？

如果 Agent 使用的是系统级服务账号，如何确保它不会绕过用户本身的权限？

审批通过后，授权是否只对当前操作有效？

这些问题需要明确的身份、授权和审计机制。

难点五 · 本体的维护成本

业务流程调整后，谁负责更新对象模型？

规则发生冲突时，谁有权修改？

某个 Action 升级后，如何判断会不会影响已有 Agent？

企业最终可能需要像管理代码、API 和数据库 Schema 一样，管理本体模型的版本、依赖和变更。

因此，我认为企业本体平台必须从一开始就具备工程治理意识。

否则，今天为了让 Agent 更容易理解业务而引入的 Ontology，明天就可能成为企业系统中最难维护的一层。

## Ontology 也不是所有企业 AI 项目的必选项

这里还需要避免另一个极端。

看到 Ontology 的价值，就认为所有企业 AI 项目都必须先建设本体平台。

我不赞同这种观点。

如果企业只是建设内部制度问答系统，RAG 可能已经足够。

如果只是把邮件内容提取出来，经过人工确认后写入 CRM，一个简单的 Workflow 加工具调用可能更经济。

如果业务对象很少、流程稳定、系统边界清晰，也不一定需要引入完整的本体基础设施。

Ontology 真正值得投入的场景，通常有几个共同特点：

业务涉及多个系统，存在大量相互关联的对象；

状态变化频繁，规则复杂；

操作需要严格权限控制；

Agent 需要持续参与业务运行，而不是只完成一次性任务。

在这些条件下，统一业务语义和执行约束带来的收益，才更有可能覆盖建模与维护成本。

所以，企业是否需要 Ontology，不应该由技术热度决定。

而应该由业务复杂度和执行需求决定。

甚至可以先用轻量的对象模型、规则服务和 Action 接口验证价值，再逐步演进到更完整的本体平台。

技术架构不是越完整越好，而是越能支撑真实业务越好。

## 从 Agent-Centric 到 Business-Centric，企业 AI 的架构中心可能正在改变

回头看这两年的企业 Agent 架构，会发现很多系统都是围绕 Agent 设计的。

先有 Agent，再给它配置 Prompt、Memory、Tools、Knowledge Base 和 Workflow。

当需要更多能力时，就增加更多工具。

当任务复杂时，就拆分成多个 Agent。

这种方式在早期非常有效。

但随着 Agent 开始参与真实业务，问题会逐渐暴露。

假设企业有采购 Agent、生产 Agent、销售 Agent 和财务 Agent。每个 Agent 都维护自己的业务上下文，都通过各自的工具查询系统：

采购 Agent 认为某批物料已经到货；

生产 Agent 看到的库存状态还没有更新；

销售 Agent 根据旧排产计划向客户承诺交期；

财务 Agent 则依据另一套订单状态进行结算。

即使每个 Agent 单独看都工作正常，整个系统仍然可能产生冲突。

这说明一个问题：

多 Agent 协作真正需要共享的，不只是消息和任务结果，更是对企业业务对象及其状态的一致理解。

因此，我认为企业 AI 架构会逐步出现一种变化。

Agent 不再是所有能力的中心。

企业业务对象、状态、规则和 Action 将成为更稳定的基础。

不同 Agent 根据自己的职责，通过统一的业务语义层访问和操作这些对象：

采购 Agent 关注供应商、物料和采购订单；

生产 Agent 关注设备、工单和产能；

销售 Agent 关注客户、订单和交付承诺。

它们可以拥有不同的任务策略，但不应该各自发明一套相互冲突的订单语义。

从这个角度看，Ontology 的价值甚至不只是服务于单个 Agent。

它还可能成为多个 Agent 协作时的共享业务语义基础。

当然，共享语义不等于共享所有数据，更不意味着所有 Agent 都可以操作所有对象。

💡 权限隔离、数据所有权和业务边界仍然必须严格执行。

## FDE 最终要沉淀的，不是项目，而是企业 AI 的可复用能力

再回到 FDE。

我觉得 FDE 模式有一个值得警惕的风险。

如果企业把它理解成“派一批更懂 AI 的工程师到客户现场”，那么它很容易重新走上传统软件定制开发的老路。

客户提出一个需求，FDE 开发一个 Agent；

客户增加一个流程，FDE 再写一段代码；

客户更换一套 ERP，FDE 重新做系统集成。

短期看，项目交付速度可能不错。

长期看，工程成本却很难下降。

真正有价值的 FDE 体系，应该形成两种循环。

第一种 · 业务运行闭环

业务事件触发 Agent，Agent 基于本体理解上下文，生成方案，通过受控 Action 执行，结果回写业务系统，并根据实际结果持续优化。

第二种 · 工程资产闭环

FDE 在项目中发现问题，完善本体模型，沉淀行业规则，封装 Action，补充测试案例，形成可复用的 Skills、连接器和交付模板。

前一种循环，让 AI 在企业业务中真正发挥作用。

后一种循环，让企业 AI 的交付能力持续积累。

这两种循环缺一不可。

！踩坑提示 🕳

只有业务闭环，没有工程资产沉淀，项目很难规模化；只有平台资产，没有真实业务闭环，最终又容易变成一个功能很多、使用率很低的 AI 平台。

所以我更愿意把 FDE 看成连接企业业务世界与 AI 技术体系的工程角色。

它的价值不是单纯解决一个客户的技术问题，而是把复杂业务中的真实需求转化成能够被平台持续复用的工程能力。

## 写在最后：企业 AI 的下一阶段，竞争的可能不是 Agent 数量

我一直认为，企业 AI 和互联网 AI 应用有一个很大的区别。

互联网 AI 应用可以通过改善用户体验、提高内容质量、增加交互能力来创造价值。

但企业 AI 最终还是要回到真实业务结果：

订单有没有按时交付？

库存有没有得到优化？

异常有没有更早发现？

审批效率有没有提高？

人工处理成本有没有下降？

业务操作是否合规、可追踪、可恢复？

这些问题无法仅靠模型能力回答。

企业需要的是一套能够把业务事实、业务规则、业务动作和 AI 推理连接起来的系统。

在这个过程中，RAG 依然重要，知识图谱依然重要，MCP、Skills、Workflow 和 Agent Framework 也都有自己的位置。

Ontology 并不是要取代它们。

它解决的是另一个长期被低估的问题：如何让 AI 对企业业务世界形成稳定、统一、可操作的理解。

而 FDE 解决的，则是如何把这种理解转化为真实生产环境中的业务结果。

如果一定要用一句话概括我对这套架构的理解，那就是：

Ontology 定义 AI 能够理解和操作的业务世界，Agent 在这个世界中进行推理和行动，FDE 负责把这套能力带进真实企业，并通过持续交付让它真正运行起来。

不过，我觉得这还不是最重要的变化。

更深层的变化在于，企业 AI 的架构中心可能正在从模型和 Agent，逐渐转向业务对象、业务状态和业务闭环。

未来一家企业拥有多少个 Agent，未必是衡量 AI 能力的好指标。

真正值得关注的，是这些 Agent 能否围绕同一套可信的业务事实协作，能否在明确的权限和规则下执行操作，能否把每一次执行结果反馈到真实业务系统中。

过去，我们一直在想办法让 AI 理解企业。

接下来，更重要的事情可能是：

把企业的业务世界，建设成一个 AI 真正能够参与运行的系统。

这件事的工程难度，可能远远超过开发一个 Agent。

但它也可能是企业 AI 从 Demo 走向生产、从局部提效走向系统性价值的关键一步。
